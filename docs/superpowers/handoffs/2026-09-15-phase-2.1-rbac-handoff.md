### The review under-rated its own first finding, and that matters

The Sonnet review rated the `ownerless_project_ids` query 🟠 "reachable only through SQL
tampering". That was wrong. Tracing the join chain while fixing it showed a 🔴 reachable with
no tampering at all: the query outer-joined `users` **without tying that join to the owner-role
match**, so the two conditions could be satisfied by different membership rows. Any live member
of any role counted as evidence of a live owner — a project whose only owner was deactivated
but which still had a live *viewer* was reported healthy and never appeared in the
`?ownerless=true` cleanup list, which is the one case that list exists to surface.

It is now `NOT EXISTS` over the same join `count_live_owners` uses, so the two cannot disagree.
`tests/test_user_deactivation_guard.py::test_ownerless_still_finds_a_project_that_kept_a_live_viewer`
was confirmed to fail against the previous query before the fix landed.

**The lesson to carry forward:** a review agent's severity rating is a hypothesis, not a
finding. Re-trace anything you are about to touch anyway.

## Decisions taken this session that are NOT in the spec or plan

1. **`ProjectScope.narrowed_to`** (`app/core/access.py`) is the sanctioned way to combine a
   non-access filter with the resolver's answer. `?ownerless=true` previously *replaced* the
   scope, which put project-id scoping in a second place. Note a plain set intersection is
   **wrong** here: an unrestricted scope carries no ids, so intersecting against it returns
   nothing instead of everything. Three tests in `tests/test_access.py` pin this, because the
   admin-only gate makes the behaviour otherwise invisible.

2. **A widened error body must declare a response model.** `AppError`'s `extra` kwarg (added by
   Task 9 for `409 LAST_OWNER`'s `projects` array) widens `detail` past `code`/`message`.
   `CLAUDE.md`'s "One error shape" section now records the carve-out beside the `422`/`fields`
   one, and `tests/test_error_shape.py` enforces it: `extra=` call sites are an AST-parsed
   allowlist (parsed, not grepped — `extra=` is also `logging`'s keyword and is used all over
   the codebase for structured log fields).

3. **Task 10 before Task 11 was a deliberate reorder**, chosen by the user. Task 11 Step 6's
   invalidation table names `services/role.py` and `cli.py::_restore_system_roles`, which did
   not exist until Task 10. Both exist now, so Task 11's table is fully satisfiable.

## The working pattern — keep it

One fresh subagent per task, reviewed between tasks, nothing batched. Run by hand with the
`Agent` tool. Model tiering (stated by the user, also in agent memory as `tier-subagent-models`):
**Haiku for mechanical/transcription work where the plan contains the literal code; Sonnet for
review passes; Opus only for genuinely hard reasoning.**

Parallel dispatch works when tasks share **no files** — Tasks 7+8 and 9+10 both ran
concurrently. The git index is shared, so every concurrent agent must be forbidden from running
*any* git command and from running the full suite (which is in flux mid-edit). Commit their work
yourself afterwards.

What to preserve in every dispatch brief:

- **Quote `.claude/rules/contradiction-halt.md` explicitly** and say that reporting a defect is
  a success. Eight of ten tasks have found a genuine plan defect this way.
- **Demand verbatim command output**, including the failing run before the passing one.
- **Give measured baselines, not adjectives.** Hand over the current pass count so "zero new
  failures" is checkable.
- **Name the files that belong to other agents** and require staging by name. Never `git add -A`
  — the tree routinely contains the human's plan edits.
- **Verify independently afterwards.** Re-run the suite, read the diff, check the commit's file
  list. Grep the test diff for weakened assertions (`in (403, 404)`, deleted asserts, new
  `is_admin=True`), because the failure mode is a green suite bought by weakening, not a red one.

### Haiku's specific failure mode, now seen three times

Haiku transcribes accurately but **does not volunteer the judgment call**, and it reports
"No Plan Contradictions" while having silently worked around one. Session 2 saw this on Task 7
(copied a snippet that violated a test written two tasks earlier). This session saw it twice:
Task 9's agent fixed two genuinely broken plan tests and reported "Plan Defects Found: None";
Task 10's agent reported the same while missing the `ERROR_RESPONSES` gap entirely.

The work was correct both times. **The reporting was not.** Always diff what a Haiku agent
actually changed against what the plan told it to do, and treat "no defects found" as unverified.
