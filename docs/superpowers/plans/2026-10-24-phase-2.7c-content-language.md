# Phase 2.7 PR C — Answers, Refusals, Shared Content and Email in Other Languages: Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Answer in the asker's language while searching in English, write shared content (checklists, mock data, refinement-chat replies, exports) in a per-project `content_language`, translate the two fixed refusals, and send email in the recipient's language.

**Architecture:** One resolver (`resolve_language`) turns a stored preference plus an `Accept-Language` header into a `Language`. Each `Answerer` caller picks the tiebreak language (Ask: the user; chats: the project; eval: the set) and passes it as `reply_language`, which travels in `TurnState` and fills a fixed-constant `{reply_language}` slot beside `{reader_preferences}`. Generation prompts gain one fixed `CONTENT_LANGUAGE` sentence filled from `LANGUAGE_NAMES`. Refusals, export labels and mail text become `dict[Language, ...]` tables, each with a completeness test.

**Tech Stack:** FastAPI, SQLAlchemy 2 async, Alembic, LangGraph/LangChain, Jinja2, openpyxl, pytest; Next.js 16, next-intl, Vitest.

**Spec:** `docs/superpowers/specs/2026-10-17-phase-2.7-multi-language-design.md`, §1.2–§1.4, §4, §5, §6, §7, §8 (PR C). PR A (#68) and PR B (#69) have shipped. Read the spec alongside this plan.

## Global Constraints

- Seven languages, BCP-47: `en`, `id`, `ja`, `ms`, `zh-HK`, `zh-TW`, `ko`. `Language` in `backend/app/core/language.py` is the only catalogue. Values are a wire contract: add, never rename.
- A language reaches a prompt **only** as a fixed English name from `LANGUAGE_NAMES`, inside a fixed constant from `app/rag/prompts.py`. It never arrives as text a request supplied.
- `projects.content_language`: `String(8)`, not null, server default `'en'`. It is not a Postgres enum. Every write validates against `Language`; anything else answers `422`.
- `PATCH /projects/{id}` body carries `contentLanguage` and nothing else. It is gated by `require_permission(user, project_id, Permission.PROJECT_UPDATE)`: a non-member gets `404 PROJECT_NOT_FOUND`, and a member without the permission gets `403 INSUFFICIENT_ROLE`.
- Audit: a new `project.updated` event with `changed` allowlist `{contentLanguage}`, recorded **after** the commit. `project.created` gains `contentLanguage` in its `changed` allowlist.
- The search query is English, in `classify` and in `grade`'s `better_query`. Identifiers, paths and quoted code stay exactly as typed. The fallbacks are unchanged: a failed `classify` still retrieves on the raw question.
- The `{reply_language}` slot is **always** rendered, English included. It sits directly after `{reader_preferences}` and before the grounding rules. Like the answer-style fragments, it never mentions citing, evidence, confidence or guessing.
- `reply_language` tiebreaks: Ask → the user's `language`, then the request's `Accept-Language`, then `en`. Checklist and mock-data chats → the project's `content_language`. Eval runner → the set's `language`.
- Refusals stay fixed strings, streamed as ordinary `token` events and never generated. `groundingWarnings` and `intent` are unchanged.
- Changing `content_language` never rewrites rows. The prompts say an existing row in another language is never by itself a reason for an `update`.
- `MAP_FILE_SYSTEM`'s per-file summaries stay English and the prompt is unchanged.
- Mail composers gain exactly one keyword-only parameter each, `language: Language`, and no other. `autoescape` and `StrictUndefined` are unchanged. The templates add no asset. `<html lang>` is set.
- Notification email language: the recipient's `users.language`, read at send time, else `en`. Password reset: the account's language, else the request's `Accept-Language`, else `en`.
- No new permission, no change to `app/core/access.py`, no new live-event kind, no new `Settings` field.
- Every non-English string added in this PR (refusals, mail, export labels, frontend keys) is a **machine-assisted draft**. Each table's docstring says so, and the PR description lists them for native-speaker review, alongside PR A's catalogues.
- `make check` must be green at the end. Run **one** pytest process at a time. Local Postgres listens on **5433**, so prefix every pytest run with `DATABASE_URL=postgresql+asyncpg://askrepo:askrepo@localhost:5433/askrepo`.
- Never start Ollama on this laptop. `uv run pytest -m model` is run by the maintainer on another machine (Task 10).

## Decisions this plan makes where the spec is silent

1. **The interface language decides the tiebreak when the user row is `NULL`.** The BFF forwards a valid `askrepo_locale` cookie as `Accept-Language` on every API call (catch-all proxy and public forward). Otherwise the tiebreak would follow the browser's header while the screen shows the language the user picked on the signed-out selector, which contradicts spec §0.1 decision 2.
2. **A cross-project checklist export** (`GET /checklist-items/export` with no `projectId`) uses the projects' shared `content_language` when they all have the same one, and English otherwise. A single-project export uses its project's language.
3. **Export translation covers labels only:** column headers, sheet titles, the cover sheet's headers, and its `(no data)` / `yes` / `no` cells. Stored values (`status`, `kind`, `source`, field keys) stay as stored. They are identifiers, and spec §2.7 keeps stored content as written.
4. **Refinement-chat proposals write in `reply_language`.** The chats set `reply_language` to `content_language`, so the propose nodes read `state["reply_language"]` rather than carrying a second state field.
5. **The English names of the refusals survive** (`NO_CONTEXT_ANSWER = NO_CONTEXT_ANSWERS[Language.EN]`), so existing tests and docs that cite them stay valid.

```python
# Tags that are not an exact match. Simplified Chinese (`zh`, `zh-CN`, `zh-Hans`,
# `zh-SG`) is deliberately absent, matching `frontend/lib/i18n/languages.ts`:
# answering a Simplified reader in Traditional is worse than answering in English.
_CHINESE_ALIASES: dict[str, Language] = {
    "zh-mo": Language.ZH_HK,
    "zh-hant": Language.ZH_TW,
    "zh-hant-hk": Language.ZH_HK,
    "zh-hant-mo": Language.ZH_HK,
    "zh-hant-tw": Language.ZH_TW,
}


def _match_tag(tag: str) -> Language | None:
    """One `Accept-Language` tag as a shipped language: exact, alias, then base."""
    lower = tag.lower()
    for language in Language:
        if language.value.lower() == lower:
            return language
    if lower in _CHINESE_ALIASES:
        return _CHINESE_ALIASES[lower]
    base = lower.split("-")[0]
    if base == "zh":
        return None
    return next((language for language in Language if language.value == base), None)


def _ranked_tags(header: str) -> list[str]:
    """`Accept-Language` tags, highest `q` first; ties keep header order."""
    ranked: list[tuple[float, int, str]] = []
    for index, part in enumerate(header.split(",")):
        tag, *params = part.strip().split(";")
        tag = tag.strip()
        weight = 1.0
        for param in params:
            name, _, value = param.strip().partition("=")
            if name == "q":
                try:
                    weight = float(value)
                except ValueError:
                    weight = 0.0
        if tag and tag != "*" and weight > 0:
            ranked.append((-weight, index, tag))
    return [tag for _, _, tag in sorted(ranked)]


def resolve_language(stored: str | None, accept_language: str | None) -> Language:
    """The one concrete language for a reader: their stored choice, then the request's
    `Accept-Language`, then English (spec §1.2).

    `NULL` means "never chose", so the header decides; a stored tag a later release no
    longer ships reads the same way. Mirrors `resolveLocale` in
    `frontend/lib/i18n/languages.ts`, so the interface and the answers agree.
    """
    chosen = parse_language(stored)
    if chosen is not None:
        return chosen
    for tag in _ranked_tags(accept_language or ""):
        match = _match_tag(tag)
        if match is not None:
            return match
    return Language.EN


def shared_language(values: Iterable[str | None]) -> Language:
    """The one language several projects share, or English when they do not.

    A document spanning projects -- a checklist export with no project filter -- has no
    single owner whose `content_language` could decide it.
    """
    distinct = {parse_language(value) for value in values}
    if len(distinct) == 1:
        (only,) = distinct
        return only or Language.EN
    return Language.EN
```

        Existing checklist and mock-data rows are not rewritten (spec §4.4): the setting

`frontend/lib/auth/forwarded.ts`:

```ts
import { LOCALE_COOKIE } from "@/lib/auth/cookies";
import { isLanguage } from "@/lib/i18n/languages";

function cookieValue(request: Request, name: string): string | undefined {
  const header = request.headers.get("cookie") ?? "";
  for (const part of header.split(";")) {
    const [key, ...rest] = part.trim().split("=");
    if (key === name) return decodeURIComponent(rest.join("="));
  }
  return undefined;
}

/**
 * The language the backend should break ties with when the user row has none — the
 * one this screen is showing. The `askrepo_locale` cookie mirrors the user's choice,
 * or this browser's on a signed-out page; without it, the browser's own header. Sent
 * as `Accept-Language` so the backend has one input to read (spec §4.3, §5.1).
 */
export function localeHeaders(request: Request): Record<string, string> {
  const locale = cookieValue(request, LOCALE_COOKIE);
  if (isLanguage(locale)) return { "accept-language": locale };
  const header = request.headers.get("accept-language");
  return header ? { "accept-language": header } : {};
}
```
