# Phase 2.5 — Measurement: user feedback on model output, and the AI call log: Design

**Date:** 2026-09-27
**Intent:** `docs/PRD.md` §2.1 Phase 2.5; GitHub issues #25 (call log) and #34 (feedback)
**Depends on:** M4/M5 generation, M4.5 provider abstraction, Phase 2.1 access, Phase 2.2 audit trail
**Milestone placement:** `docs/PRD.md` §6 item 10

---

## 0. What this document covers

Phase 2.5 is two instruments pointed at two blind spots the PRD names. Nothing records what a
model call **cost** (tokens, latency, model, outcome), and nothing records whether a
model-authored output was any **good**. The PRD specifies them together because they join on
one dimension — which feature produced the output — and neither answers "is the expensive step
worth it" alone.

This spec covers both. They **ship in two stages**, each its own PR, each leaving `main`
shippable:

1. **Stage 1 — feedback.** Thumbs up/down on every model-authored output, a reason code, an
   optional note, and an admin-only aggregate screen. Postgres only; no new infrastructure.
2. **Stage 2 — the call log.** A self-hosted Langfuse, wired through LangChain's callback
   stream, with every prompt and completion masked.

Feedback ships first because it is cheap and useful on day one; Stage 2's trace links on the
feedback screen switch on when it lands.

What is **not** in scope: a spend cap or budget (the PRD is explicit that a cap is built *on*
the log, never before it); any automated use of feedback by a model; an administrator reading
the question or answer behind a piece of feedback; per-user cost; cost dashboards built inside
AskRepo; project owners reading feedback or cost (§3.4 keeps the data shaped so that is one
permission away).

### 0.1 The decisions, made

1. **One spec, two stages** — feedback, then Langfuse.
2. **Feedback surfaces: every model-authored output.** Every persisted assistant message in all
   three chats (Ask, checklist refinement, mock-data refinement), and every checklist and
   mock-data change set regardless of which producer wrote it.
3. **Interaction: thumbs, then *why*.** Thumbs up records in one click with an optional note;
   thumbs down opens reason codes (at least one required) and an optional note. One vote per
   user per subject, revisable in place, withdrawable.
4. **Administrators see the aggregate and the notes — never the question or the answer**
   (PRD §8's open question, decided as "aggregate-only, plus the note"). The UI tells the user,
   in fixed text beside the note field, that administrators can read it and the model never
   will.
5. **Administrators never see who voted.** A note about a private turn with a name attached is
   most of the way to reading that conversation.
6. **Readers: administrators only, instance-wide** — for both feedback and cost. Every row still
   carries `project_id`, so a per-project reader is one permission and one `require_permission`
   call later.
7. **Reviewers do not see each other's votes on a shared change set** in v1, so a visible
   down-vote does not bias the next reviewer.
8. **Langfuse content is always masked; there is no opt-in** in v1. No setting can make a trace
   carry source code.
9. **The handler is attached once, in `build_chat_model`,** and each call site tags a `Feature`.
   Every call is traced by construction; a new call site cannot silently go untraced.
10. **Trace ids are derived, not stored.** A trace id is `create_trace_id(seed=<subject id>)` —
    the assistant message id or the change set id — so no trace-id column exists anywhere.
11. **No user id is sent to Langfuse.** Cost per project and per feature answers the PRD's
    questions; cost per user is surveillance nobody asked for.
12. **Recording feedback is the audit trail's seventh named exemption** (§2.6). This amends
    `docs/PRD.md` §2.1 and `.claude/rules/audit-trail.md` in the same change.
13. **The Langfuse UI keeps its own login.** Accepted for v1 and recorded in `SECURITY.md` as an
    operator responsibility.

## 1. The invariant that outranks the rest

**Nothing feedback-authored ever reaches a model.** The PRD calls this "the whole of the
design". Feedback is user-authored text about a private repository; concatenated into a prompt
it becomes an instruction, which breaks the property `.claude/rules/rag.md` rests on — the
model's instructions come from the system message and nowhere else. The loop is deliberately
manual: feedback accumulates, an administrator reads it, spots a pattern, and edits
`app/rag/prompts.py` on purpose.

Enforced structurally, not by care: a test (§5.3) fails if anything under `app/rag/`,
`app/checklist/` or `app/mockdata/` imports the feedback model, repository or service.

## 2. Stage 1 — Feedback: data model and lifecycle

### 2.1 What can receive feedback

Five subject types, because the three chats store messages in separate tables:

| `target_type` | Table | `feature` recorded |
| --- | --- | --- |
| `message` | `messages` (Ask) | `answer` |
| `checklist_message` | `checklist_messages` | `refine_checklist` |
| `mock_data_message` | `mock_data_messages` | `refine_mock_data` |
| `checklist_change_set` | `checklist_change_sets` | `generate_checklist` (origin: generator) or `propose_checklist` (origin: chat) |
| `mock_data_change_set` | `mock_data_change_sets` | `generate_mock_data` or `propose_mock_data` |

Only **assistant** messages accept feedback; a user message returns `404
FEEDBACK_TARGET_NOT_FOUND`. A refinement turn that proposes changes shows two independent
controls — one on the reply text, one on the change-set card — because "did it explain well"
and "was the proposal good" are different judgements.

The `feature` is derived server-side from the target, never accepted from the client.

These feedback `feature` values are the **output** dimension. Stage 2's `Feature` enum (§4.2) is
the **call** dimension — one output (an Ask answer) is several calls (classify, grade, answer).
The join between them is the trace (§4.3), not a shared enum value.

### 2.2 The `feedback` table

| Column | Type | Notes |
| --- | --- | --- |
| `id` | uuid pk | |
| `user_id` | uuid fk `users` | never serialized on any admin route (§3.3) |
| `project_id` | uuid fk `projects` | derived from the target |
| `target_type` | varchar(32) | §2.1 |
| `target_id` | uuid | not a foreign key — polymorphic; existence checked by the service |
| `feature` | varchar(32) | §2.1 |
| `rating` | varchar(8) | `up` \| `down` (check constraint) |
| `reason_codes` | `text[]` | validated against the catalogue (§2.4); empty allowed for `up` only |
| `note` | varchar(500), nullable | bounded for storage, not politeness |
| `prompt_version` | varchar(16) | §2.3, stamped at write time |
| `created_at`, `updated_at` | `TimestampMixin` | |
| `deleted_at` | `SoftDeleteMixin` | used by project deletion only |

Unique on `(user_id, target_type, target_id)` where `deleted_at IS NULL`; a vote change is an
update in place. Indexes on `(project_id, created_at)` and `(feature, created_at)` for the
aggregate.

### 2.3 `prompt_version`

Nothing versions prompts today. `prompt_version` is the first 12 hex characters of a SHA-256
over the prompt strings in `app/rag/prompts.py` and the generator prompts
(`app/checklist/`, `app/mockdata/`), computed once at import in a new
`app/rag/prompt_version.py`. Any edit changes it automatically; nobody bumps it by hand.

It is what makes "did the prompt change fix the down-votes?" answerable, and it is the
comparability key Phase 2.6's eval harness needs too. Stage 2 also sends it to Langfuse as
metadata.

The stamp is the version running **when the vote is cast**, not when the output was generated.
For an answer, the two are almost always the same. For a change set voted on days later, they
can differ. This is accepted and stated on the admin screen: storing the generation-time version
would mean a column on every message and change set, and those columns belong to Stage 2's
trace, not to this table.

### 2.4 Reason codes

A fixed catalogue in `app/core/feedback.py`, a wire contract like `ErrorCode`: add members,
never rename. Each code declares the target types it applies to.

| Code | Answers & chat replies | Change sets |
| --- | --- | --- |
| `wrong_file_cited` | ✓ | |
| `missed_something` | ✓ | ✓ |
| `invented_something` | ✓ | ✓ |
| `right_but_unusable` | ✓ | ✓ |
| `wrong_language_or_tone` | ✓ | |
| `duplicate_or_redundant` | | ✓ |
| `wrong_scope` | | ✓ |
| `other` | ✓ | ✓ |

The PRD expects this list to be revised once after the first month of use; adding a code is a
catalogue edit plus a `CHANGELOG.md` line.

**It must not re-surface the grounding warnings.** `unknown_paths` and `uncited_answer` are
already computed, on the wire in `done`, and rendered. There is deliberately no "uncited" or
"unknown path" code.

### 2.5 Lifecycle

| Event | Effect on feedback | Why |
| --- | --- | --- |
| Conversation deleted | Rows on its messages keep `rating`, `reason_codes`, `feature`, `project_id`; `note` set to `NULL`, in the same transaction | The note is the user's words about a private turn and goes with it; the counts still add up |
| Project deleted | That project's rows soft-deleted in the same operation | Same rule as every other project-owned row (`docs/data.md`) |
| Change set discarded, applied, or superseded | Unchanged | The subject still exists; "discarded, and why" is exactly the data wanted |
| User withdraws a vote | Row hard-deleted | An unrecorded personal opinion; no reason to keep a tombstone |
| User deactivated | Unchanged | Consistent with memberships, which also survive deactivation |
| `FEEDBACK_RETENTION_DAYS` elapsed | Hard-deleted by the worker's 60-second tick | Default `0`, keep forever, matching `AUDIT_RETENTION_DAYS` |

### 2.6 Audit: the seventh exemption

`.claude/rules/audit-trail.md` requires every write to record an event, with six named
exemptions. Recording, revising or withdrawing feedback becomes the **seventh**. It carries the
same three reasons as exemption 5 (a user's own notification state): it describes no change to
a shared resource; the `feedback` table is itself the record; and its write rate is proportional
to attention, so auditing it would bury `user.deactivated` under thumb clicks. The note
lifecycle writes in §2.5 are consequences of already-audited events (`conversation.deleted`,
`project.deleted`) and are not audited separately.

`tests/test_audit_coverage.py` learns the exemption so it does not report the feedback write as
unaudited.

## 3. Stage 1 — Feedback: API and UI

### 3.1 Routes

A new router, `app/api/routes/feedback.py`, prefix `/feedback`. It is not in
`GATE_EXEMPT_PREFIXES`, so the forced-password-change gate covers it.

| Route | Caller | Behaviour |
| --- | --- | --- |
| `PUT /feedback/{targetType}/{targetId}` | anyone who can see the target | Upsert own vote. Body `FeedbackWrite {rating, reasonCodes, note}` → `200 FeedbackRead` |
| `DELETE /feedback/{targetType}/{targetId}` | same | Withdraw own vote → `204`. Withdrawing a vote that does not exist is also `204` |
| `GET /feedback/summary` | `AdminUser` | Counts by `feature × rating × reasonCode`, plus down-vote rate per feature and per `promptVersion` |
| `GET /feedback` | `AdminUser` | Paginated `FeedbackAdminRead` rows, newest first |

Both admin routes take `projectId`, `feature`, `rating`, `reasonCode`, `promptVersion`,
`from`, `to` as filters, on a `ListQuery` subclass (`.claude/rules/rag.md`: a query model cannot
share a route with a scalar query parameter). A `projectId` filter narrows the caller's
`resolve_project_scope` via `ProjectScope.narrowed_to`; it never replaces it.

### 3.2 Visibility checks on write

`FeedbackService` resolves the target, then:

- **`message`** — the conversation must be owned by the caller, through
  `resolve_conversation_owner`. Any miss is `404 CONVERSATION_NOT_FOUND`, with no admin bypass —
  the same rule as every route under `/conversations`.
- **everything else** — `require_permission` on the permission that already gates *reading* that
  subject: `Permission.CHECKLIST_READ` for `checklist_message` and `checklist_change_set`,
  `Permission.MOCKDATA_READ` for `mock_data_message` and `mock_data_change_set`. Anyone who can
  read the output can judge it; no new permission. A project the caller holds no membership on is
  `404 PROJECT_NOT_FOUND`; a member lacking the read permission is `403 INSUFFICIENT_ROLE`.
- A target that does not exist inside a project the caller can see, or a user-role message, is
  **`404 FEEDBACK_TARGET_NOT_FOUND`** (new `ErrorCode`).
- `422` for a `down` with no reason code, a code that does not apply to the target type, an
  unknown code, or a note over 500 characters. `fields` is keyed by the `camelCase` field name.

### 3.3 Schemas

All inherit `ApiModel`.

- `FeedbackWrite` — `rating`, `reasonCodes`, `note`.
- `FeedbackRead` — the caller's own vote: `targetType`, `targetId`, `rating`, `reasonCodes`,
  `note`, `updatedAt`.
- `MyFeedback` — `rating`, `reasonCodes`, `note`; embedded as `myFeedback: MyFeedback | null` on
  message reads (all three chats) and change-set reads, loaded in one query per list. Always
  the caller's own row and nothing else.
- `FeedbackAdminRead` — `id`, `projectId`, `projectName`, `targetType`, `feature`, `rating`,
  `reasonCodes`, `note`, `promptVersion`, `createdAt`, `updatedAt`, and `traceUrl` (null until
  Stage 2 and whenever Langfuse is off). **No user field of any kind** — not an id, not a name,
  not an email. `tests/test_feedback_admin_is_anonymous.py` asserts this on the schema.
- `FeedbackSummary` — the counts and rates above.

### 3.4 Future per-project reader

Not built. The shape that would admit it: a `feedback.read` permission in
`app/core/permissions.py`, and the admin routes switching from `AdminUser` to a
`resolve_project_scope`-narrowed read. Nothing in the table changes.

### 3.5 Frontend

**`<FeedbackControl>`**, in `frontend/components/feedback/`, one component used everywhere:

- Thumbs appear under every persisted assistant message in the Ask screen and both refinement
  chats — after `done` or `error`, never while streaming — and on every change-set card.
- Thumbs up records immediately; an "Anything to add?" link opens the note.
- Thumbs down opens a popover: reason chips for that target type, a textarea (500-character
  counter), and fixed text: *"Administrators can read this note. It is never sent to the AI
  model."*
- Clicking the active thumb again withdraws the vote. Optimistic update, rolled back on error.
- Initial state comes from `myFeedback` on the list the screen already loads — no extra request.

**`/settings/feedback`**, admin-only, in the Settings nav (`.claude/rules/navigation.md`):

- Summary tiles: down-vote rate per feature over the selected window.
- Reason-code table: counts per code per feature.
- Down-vote rate by `promptVersion`, so a prompt edit's effect is visible, with the caveat from
  §2.3 stated in a line of help text.
- Notes list with the §3.1 filters; each row links to its Langfuse trace when `traceUrl` is set.

Existing shadcn components only; tokens per `docs/design.md`. Not live-updated — it is a report,
and a page load is fresh enough.

## 4. Stage 2 — The AI call log on Langfuse

### 4.1 Wiring

- `build_chat_model` (`app/rag/chat.py`) attaches a Langfuse `CallbackHandler` to the model it
  returns when `LANGFUSE_ENABLED` is true. The API process and the worker both build models
  through this factory, so answers, both generators and the capability probe are covered.
- The Langfuse client is constructed once per process in a new `app/observability/langfuse.py`
  with a `mask` function that replaces every input and output with `"[masked]"`. It is not
  configurable.
- With `LANGFUSE_ENABLED` false, no client is constructed and no handler is attached — zero
  overhead and zero network.

### 4.2 The `Feature` tag

A `Feature` `StrEnum` in `app/observability/features.py`: `classify`, `grade`, `answer`,
`propose_checklist`, `propose_mock_data`, `map`, `reduce`, `generate_mock_data`,
`capability_probe`. Every call site passes

```python
config={"metadata": {"feature": Feature.X, "project_id": str(project_id),
                     "prompt_version": PROMPT_VERSION, "attempt": attempt}}
```

`attempt` is the delivery attempt from the Kafka retry ladder for worker jobs, so a retried job's
calls are distinguishable and spend includes what the ladder costs; it is `1` on the API path.
`tests/test_llm_call_sites_tagged.py` walks every `.ainvoke(` / `.astream(` call on a chat model
and fails if any omits a `feature`.

### 4.3 Trace grouping

- **An Ask or refinement turn** is one trace, id `create_trace_id(seed=str(assistant_message_id))`.
  Classify, grade and answer are observations within it. The assistant message id is minted in
  `prepare_turn`, before the stream starts, exactly as change-set ids already are
  (`.claude/rules/rag.md`); the row is still written once, at termination, under the shield.
- **A generation job** is one trace seeded from its change set id: a 200-file run is one trace
  with 201 generations, not 201 traces.
- The admin feedback screen computes `traceUrl` from the target id with the same seed function,
  so feedback and cost join without either table knowing about the other.

**Unverified, and the implementation plan's first task settles it:** the exact Langfuse v3
Python SDK mechanism for (a) passing a caller-chosen trace id to the LangChain `CallbackHandler`,
and (b) the `mask` hook's signature. The design depends on both existing; if (a) does not, the
fallback is a `trace_id` metadata key read by a thin subclass of the handler.

### 4.4 Failure behaviour

Tracing never fails a model call. The SDK exports in the background; handler construction and
export errors are additionally caught and logged at `WARNING` — the same fail-open stance as
`AuditRecorder`. Both processes flush the client on shutdown (FastAPI lifespan, worker
teardown).

### 4.5 What reaches Langfuse

Provider, model name, start and end time, input and output token counts, success or failure,
the error's class and its **scrubbed** message, the `feature`, `project_id`, `prompt_version`
and `attempt`. **Never the prompt, never the completion** (masked), **never a user id**, never
the API key. Pricing comes from Langfuse's maintained model price table, which answers PRD §8's
per-call cost question by moving the staleness to a dependency someone else maintains.

### 4.6 Infrastructure

| Container | Role |
| --- | --- |
| `langfuse-web` | UI and ingestion API |
| `langfuse-worker` | Async trace processing |
| `clickhouse` | Trace storage |
| `langfuse-redis` | A **second** Redis, `maxmemory-policy noeviction`, never the one `rate_limit.py` reads |
| `minio` | S3-compatible blob store for event payloads |

Langfuse's Postgres is a separate `langfuse` **database** on the existing Postgres, created by an
init script — not a sixth container.

- **Development:** behind a `langfuse` Compose profile. `make infra` is unchanged;
  `make infra LANGFUSE=1` adds the five. `LANGFUSE_ENABLED` defaults `false`.
- **Production:** the same services in `docker-compose.prod.yml`, same profile, standalone as
  always (never an overlay).
- **First boot:** `LANGFUSE_INIT_ORG_*`, `LANGFUSE_INIT_PROJECT_*` and the init API keys create
  the org, project and keys headlessly, so no manual setup is needed.
- **Sizing:** roughly 4 GB of RAM floor before ClickHouse starts. `docs/deployment.md` states it
  and says to take it together with Phase 3's Neo4j.
- **Ports:** the Langfuse web port is published on the internal network only and listed in the
  compose header comment.

### 4.7 Retention

**Unverified:** whether self-hosted Langfuse OSS exposes a data-retention setting. The plan's
first task checks. If it does, `docs/deployment.md` documents it; if not, a ClickHouse TTL on the
trace tables is documented as the operator's lever. There is no AskRepo setting for it either
way — the data lives in Langfuse's store, not ours.

### 4.8 The second login

Langfuse's UI authenticates separately and does not go through `app/core/access.py`. Accepted for
v1: content is masked, the data is instance-wide operator data, and the intended readers are the
same administrators. `SECURITY.md` records it as an operator responsibility (who holds a Langfuse
account, and that the web port stays internal). Building cost views inside AskRepo through the
Langfuse API is the alternative, deferred.

## 5. Testing

### 5.1 Stage 1 — access

- Voting on another user's Ask message → `404 CONVERSATION_NOT_FOUND`, including as an admin.
- Voting on a change set in a project with no membership → `404 PROJECT_NOT_FOUND`.
- Voting on a user-role message → `404 FEEDBACK_TARGET_NOT_FOUND`.
- Both admin routes → `403` for a non-admin.
- `FeedbackAdminRead` carries no user field (schema test).
- `myFeedback` returns only the caller's row when two users voted on the same change set.
- `/conversations` still has no admin bypass (existing test, unchanged).

### 5.2 Stage 1 — behaviour

- Upsert: a second `PUT` updates in place; `DELETE` then `PUT` recreates.
- Validation: `down` with no code, wrong-target code, unknown code, 501-character note → `422`.
- Lifecycle: deleting a conversation nulls its notes and keeps counts; deleting a project
  soft-deletes its feedback; the retention prune removes only rows past the cutoff.
- `prompt_version` changes when a prompt string changes and is stable otherwise.
- Summary counts and rates over a seeded fixture.

### 5.3 Stage 1 — contracts

- Every new schema inherits `ApiModel` and is covered by `tests/test_api_model.py`'s walk. No
  SSE event is added, so `SSE_EVENT_MODELS` is unchanged.
- Reason catalogue: every code maps to at least one target type; every target type has at least
  one `down` code.
- `tests/test_audit_coverage.py` accepts the seventh exemption.
- **Separation:** `tests/test_feedback_never_reaches_a_model.py` fails if `app/rag/`,
  `app/checklist/` or `app/mockdata/` imports anything from the feedback model, repository or
  service.
- Vitest: `<FeedbackControl>` — optimistic update and rollback, withdraw on second click,
  reason chips per target type, the fixed disclosure text is present.

### 5.4 Stage 2

- Every chat-model call site passes a `Feature` (§4.2).
- Mask: a traced call's exported payload contains none of the prompt's text or the completion's.
- A Langfuse export failure does not fail the call.
- `LANGFUSE_ENABLED=false` attaches no handler and constructs no client.
- Trace ids are deterministic from the subject id, and `traceUrl` on the admin feedback screen
  matches.
- `uv run pytest -m model` still passes (`/rag-check`), since call sites in `app/rag/` change.
