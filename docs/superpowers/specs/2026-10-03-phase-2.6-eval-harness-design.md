## 0. What this document covers

Nothing tells a developer whether answers got better or worse when chunking, a prompt, the
chat model or the provider changes. `pytest -m model` checks that prompts route and cite. It
cannot say whether an answer was *right*. This harness produces that signal.

A user holding `eval.run` generates an **eval set**: up to 50 question/reference-answer pairs,
each grounded in one real chunk of the project's index. The set is then frozen. Running the set
answers every pair through the real Dev Knowledge graph and records two separate per-pair
signals: whether retrieval found the pair's source file, and a judge model's verdict on the
answer against the reference. Runs of the same set are comparable, and each is stamped with
everything that could have changed between them.

What is **not** in scope: "what would break if I changed Y" questions; non-English sets (Phase
2.7 builds them); a judge model separate from the chat model; editing a reference answer;
notifications; run retention; any automated gate in CI.

### 0.1 The decisions, made

1. **A fixed set, many runs.** The PRD's prose reads as "generate and score" in one job. Built
   that way, two scores are never measured on the same questions, so a drop cannot be told apart
   from noise in generation. A set is generated once. Runs are repeated against it.
2. **Two signals, reported side by side and never blended.**
   - **Retrieval hit:** whether the pair's `source_file` came back among the cited sources.
     Deterministic, so it catches chunking and embedding regressions with no noise.
   - **Answer verdict:** an LLM judge compares the answer with `reference_answer` on a
     three-point rubric (`correct` / `partial` / `wrong`) and gives a one-line reason.

   The grounding warnings from `done` are stored beside them. This settles the issue's "how
   rigorous" question: the judge is the noisy half, and it is never the only half.
3. **Question types `explain` and `locate` only.** The PRD's third example, "what would break if
   I changed Y", is reachability. §2.1 Phase 3 says vector retrieval *structurally* cannot
   answer it. Worse, a pair built from one chunk can only carry a reference listing what that
   chunk shows. That reference is incomplete by construction, and the judge would mark a better
   answer `wrong`. The type is a stored string, so Phase 3 adds `impact` with no migration.
4. **Two new permissions.**
   - `eval.read` goes to viewer, editor and owner. A viewer can already ask these questions.
   - `eval.run` goes to editor and owner. It covers generating a set, starting a run, excluding
     a pair and deleting a set.

   Admins pass, as everywhere else. Eval content is code-derived and per-project, so it scopes
   through the access resolver like everything else.
5. **A non-English set is a precondition for Phase 2.7, and Phase 2.7 builds it.** This spec is
   English only and adds no `language` column. Phase 2.7 adds one, defaulting to `'en'`, in the
   change that teaches generation a second language. Recorded in the PRD.
6. **A set covers the project or one indexed path**, chosen with the existing indexed-paths
   picker. A set is not tied to a checklist module.
7. **No notification in v1.** Live events and polling update the screen. Notifying only the
   person who started a job would need `raise_direct`, which `.claude/rules/notifications.md`
   rule 7 reserves for `membership.granted`. Notifying every `eval.run` holder turns one
   developer's experiment into every editor's bell.
8. **Curation is exclusion, never editing.** Anyone holding `eval.run` can exclude a pair or
   re-include it. Future runs skip excluded pairs, stored results keep theirs, and two runs are
   compared on the pairs both answered. Nobody edits a reference: an edited reference is no
   longer grounded in its chunk.
9. **One Kafka topic family carrying two job kinds** (§3). Concurrency is the partition count,
   1 by default: one eval job per instance at a time, the same way checklist generation caps
   itself.

Four tables, one migration. All carry `TimestampMixin` and `SoftDeleteMixin`. Deleting a set
soft-deletes its pairs, runs and results in the same transaction, and deleting a project
soft-deletes all four for that project. **No Qdrant points belong to an eval table**, so the
soft-delete-vs-Qdrant rule has nothing extra to do here. The project's own points are already
hard-deleted by `project.deleted`.

**The answer is stored, and that is deliberate.** A verdict nobody can inspect is a number
nobody can act on. The answer has a chat message's lifecycle: it sits in Postgres beside the
code-derived pairs and is deleted with the project. It never reaches the audit trail, the call
log or a log line.

**An eval set is shared content of record**, like a checklist module. Every holder of
`eval.read` on the project sees the same sets, runs and answers. That is correct: it is the
same Q&A any member could produce by asking, and the persona never touches it (§3.2).

## 2. Generating a set

### 2.1 Request

`POST /projects/{project_id}/eval-sets`, body `{name, sourcePath?, count, mix}` → `202` with
the set (`status: pending`). In order:

1. `require_permission(user, project_id, Permission.EVAL_RUN)`. A non-member gets `404`, and a
   member without the permission gets `403 INSUFFICIENT_ROLE`.
2. The project must be `ready` (`409 PROJECT_NOT_READY`, the existing code).
3. `_require_a_stable_index`: `409 PROJECT_NOT_READY` while a reindex is in flight. This is the
   same guard and the same reasoning as checklist generation: a set generated mid-reindex
   samples a generation that is about to be deleted. Move the guard from
   `ChecklistModuleService` to a shared helper in `app/services/` that both services call.
4. If `sourcePath` is given, it must be indexed: `400 MODULE_PATH_NOT_INDEXED`. Reuse the code
   rather than adding one, for the reason `checklist_module.py:541` gives, and move that check
   to the same shared helper.
5. `count` ∈ {10, 25, 50} and `mix` ∈ {`balanced`, `explain`, `locate`}, enforced by schema
   (`422`).
6. Insert the row, stage the live event, commit, publish an `EvalJobMessage(kind="generate")`,
   then record the audit event `eval_set.generation.requested`.

### 2.2 The job

`app/eval/generator.py`, run by the worker under a lease on the set row:

1. **Scroll** the project's chunks at `active_generation` under `source_path` (or all of
   them). Reuse the scroll in `app/checklist/source.py`, generalised if it is module-shaped.
   The generator **scrolls; it does not search**, for the reason `CLAUDE.md` gives about
   generation.
2. **Sample** deterministically: group chunks by file, sort files by path, and shuffle with a
   `random.Random` seeded from the set id. Take one chunk per file, preferring a chunk with a
   `symbol` and then the longest. With fewer files than `requested_count`, wrap around for a
   second chunk per file. Assign types by `mix`: `balanced` alternates explain/locate, starting
   with explain; the other two are uniform.
3. **One structured call per pair** (`with_structured_output(GeneratedPair)`, feature
   `CallFeature.EVAL_GENERATE`). `GeneratedPair` is `{question: str, reference_answer: str}`.
   The prompt (`EVAL_PAIR_SYSTEM` in `app/rag/prompts.py`, so it is under `PROMPT_VERSION`)
   wraps the chunk in `<excerpt>` delimiters as untrusted data, exactly as the answer prompt
   does, and states per type:
   - `explain`: a question about what the symbol or block does, whose answer is fully contained
     in the excerpt;
   - `locate`: a question asking where some behaviour is handled, phrased without the file
     path, whose reference names the file and symbol.
4. **Validate each pair.** Drop it when the question contains `source_file` or its basename (a
   `locate` question that names its answer measures nothing), or when either field is empty.
   Dropped pairs are not retried.
5. **Write** the pairs in one transaction with `status = ready`, `pair_count` and
   `indexed_generation`, and stage the live event. With zero pairs, `status = failed` and
   `error = "No usable pairs could be generated from this path."`.

Failure classification and retries use the existing chat taxonomy (`classify_chat_error`). A
retryable failure defers the lease and goes up the retry ladder; a terminal one marks the set
`failed`. Per-pair model failures (a malformed structured response) drop that pair, as in
step 4, rather than failing the job. That is the same degrade-don't-fail stance as M4's map
step.

## 3. Running a set

### 3.1 Request

`POST /eval-sets/{set_id}/runs` → `202` with the run (`status: pending`). The project is
resolved from the set, then:

1. `require_permission(..., Permission.EVAL_RUN)`.
2. The set must be `ready`: `409 EVAL_SET_NOT_READY` (**new `ErrorCode`**).
3. No run of this set may be `pending` or `running`: `409 EVAL_RUN_IN_PROGRESS` (**new**).
4. The project must be `ready` with no reindex in flight: `409 PROJECT_NOT_READY`. A run reads
   the live generation and a reindex would delete it mid-run.
5. `project.embedding_model` must equal the configured embedder's model id:
   `409 EMBEDDING_MODEL_CHANGED`, the same guard the Ask path takes and for the same reason.
6. The set must have at least one non-excluded pair: `409 EVAL_SET_NOT_READY`.
7. Insert the run (stamping nothing yet), stage the live event, commit, publish
   `EvalJobMessage(kind="run")`, then record the audit event `eval_run.requested`.

### 3.2 The job

`app/eval/runner.py`, run by the worker under a lease on the run row:

1. **Stamp** `prompt_version`, `chat_provider`, `chat_model`, `judge_model` (= `chat_model`),
   `embedding_model` and `project_generation` from the project row and settings. Set
   `status = running` and `started_at`, and stage the live event.
2. **Build one `Answerer`** over a `CodeRetriever` on `project.embedding_collection`, read
   verbatim and never recomputed (`.claude/rules/rag.md`), with `propose_target=None`. Its
   semaphore is sized by `EVAL_ANSWER_CONCURRENCY`.
3. **For each non-excluded pair**, in `position` order, with up to `EVAL_ANSWER_CONCURRENCY`
   pairs in flight:
   - Drain `answerer.answer(question=pair.question, history=[], project_id=…,
     generation=run.project_generation, message_id=None)`. **No `answer_style`:** the default
     prompt, by construction (persona spec §6).
   - `retrieval_hit` = `pair.source_file` is among the `path`s of the one `citations` event.
     That is first-pass retrieval, which is what chunking and embedding change. It is not the
     re-retrieval's spans, and the spec says so rather than letting the UI imply otherwise.
   - On `done`, take the answer text, `grounding_warnings` and `retrieval_attempts`. On
     `error`, record `verdict = error` and skip the judge.
   - **Judge** (§3.4). A judge failure records `verdict = error` with the answer kept.
   - Write the result row. Results commit in batches of 10, so a crashed run keeps what it
     finished. A redelivered run skips pairs that already have a result for this `run_id`
     (the unique index makes that cheap and safe).
4. **Complete:** compute the summary counts from the result rows, set `status = done` and
   `finished_at`, and stage the live event.

A run whose every pair errored is still `done`, with `errors = pairs_answered`. That is a
truthful result, not a job failure. Infrastructure failures (Qdrant unreachable, the lease
lost) are classified like any other job and end `failed` only when terminal.

### 3.3 Scope and the call log

The run sets `scope_config(trace_seed=str(result_id), project_id=…, attempt=…)` per pair, so
each pair's answer and judge calls share a trace. The trace seed is the result row's id, minted
before the answer starts. `CallFeature` gains `EVAL_GENERATE` and `EVAL_JUDGE`; the answer's
own calls stay tagged `classify` / `grade` / `answer` / `history_answer`, as the graph tags
them. `tests/test_call_sites_tagged.py` lists both new call sites.

### 3.4 The judge

`EVAL_JUDGE_SYSTEM` in `app/rag/prompts.py`. One structured call returning
`JudgeVerdict{verdict: Literal["correct", "partial", "wrong"], reason: str}`. The question, the
reference and the answer each sit inside their own delimiter (`<question>`, `<reference>`,
`<answer>`), all declared to be data. The answer especially: a model-authored answer to a
question about a repository could contain anything the repository did.

The rubric is stated in the prompt:

- **correct**: states everything the reference states that answers the question, and nothing
  that contradicts the reference.
- **partial**: right as far as it goes, but misses something the reference says answers the
  question.
- **wrong**: contradicts the reference, names a different location for a `locate` question,
  or says it could not find the answer when the reference shows it was there.

Extra correct detail beyond the reference is **not** penalised. The reference is built from one
chunk and is a floor, not a ceiling. Citation labels (`[n]`) in the answer are ignored, because
grounding is measured elsewhere. `reason` is truncated to 500 characters before storage.

### 3.5 What a run does not do

- It writes no `conversations` or `messages` row. An eval answer is not anyone's conversation.
- It sends no feedback and is never counted in feedback aggregates.
- It reads no `users.answer_*` column.

## 4. Comparing runs

### 4.1 Same set, common pairs

The detail screen compares any two runs of one set **on the pairs both answered**. It shows:

- the hit rate and the verdict split over that common subset;
- the per-pair flips (hit→miss, correct→wrong and the reverse), each linking to both answers.

Excluding a pair never breaks a past comparison, and a pair excluded after run A but before run
B simply drops out of the A-vs-B subset.

The comparison is computed **client-side** from `GET /eval-runs/{id}` for both runs. At 50
pairs it is two small reads, and a compare route would be a second definition of "common
pairs" to keep in step.

### 4.2 A reindex does not invalidate a set

Re-chunking and re-running the same set is the measurement this feature exists for.
`retrieval_hit` is keyed on the file path, which survives a reindex. Each run records the
generation it read, and the screen shows it.

A set whose `source_file` no longer exists in the index is not refused. It shows up as misses,
which is true. The screen labels a set "generated from generation N; project is now at M" when
the two differ, for information, not as a block.

### 4.3 The judge-model caveat, stated rather than solved

The judge is the instance's chat model. Comparing two chat models therefore compares two
judges as well, and verdict deltas mix both effects. The comparison view shows a fixed warning
whenever the two runs' `judge_model` differ: *"These runs were judged by different models.
Verdict changes may reflect the judge, not the answers. Retrieval hits are unaffected."* A
separate `EVAL_JUDGE_*` provider setting is the fix, and it is out of scope for v1 (§0).

## 5. Wire

All routes resolve the project (directly, or from the set, pair or run) and call
`require_permission`. **Every miss is `404 PROJECT_NOT_FOUND`** for a caller with no membership,
including on a set, pair or run id: an eval id must not confirm that a private project exists.
A member whose role lacks the permission gets `403 INSUFFICIENT_ROLE`. A set, pair or run that
does not exist inside a project the caller can see is `404 EVAL_SET_NOT_FOUND` /
`EVAL_RUN_NOT_FOUND` (**new codes**; a pair miss reports `EVAL_SET_NOT_FOUND`, because a pair is
only addressable as part of a set).

| Method | Path | Permission | Response |
| --- | --- | --- | --- |
| `POST` | `/projects/{project_id}/eval-sets` | `eval.run` | `202` `EvalSetRead` |
| `GET` | `/projects/{project_id}/eval-sets` | `eval.read` | `200` `PaginatedResponse[EvalSetSummary]`, newest first |
| `GET` | `/eval-sets/{set_id}` | `eval.read` | `200` `EvalSetDetail` (set + pairs) |
| `DELETE` | `/eval-sets/{set_id}` | `eval.run` | `204`; `409 EVAL_RUN_IN_PROGRESS` while a run is live |
| `PUT` | `/eval-pairs/{pair_id}/excluded` | `eval.run` | `200` `EvalPairRead`; body `{excluded: bool}` |
| `POST` | `/eval-sets/{set_id}/runs` | `eval.run` | `202` `EvalRunRead` |
| `GET` | `/eval-sets/{set_id}/runs` | `eval.read` | `200` `PaginatedResponse[EvalRunSummary]`, newest first |
| `GET` | `/eval-runs/{run_id}` | `eval.read` | `200` `EvalRunDetail` (run + every result, with pair id) |

Every schema inherits `ApiModel`. `PUT …/excluded` with an unchanged value returns `200` and
writes nothing, including no audit row. New `ErrorCode` members: `EVAL_SET_NOT_FOUND`,
`EVAL_RUN_NOT_FOUND`, `EVAL_SET_NOT_READY`, `EVAL_RUN_IN_PROGRESS`.

All routes sit under existing gated prefixes (`/projects`) or new prefixes (`/eval-sets`,
`/eval-pairs`, `/eval-runs`) that are **not** added to `GATE_EXEMPT_PREFIXES`.
`tests/test_route_coverage.py` covers them.

## 6. Access, audit and live events

### 6.1 Permissions

`Permission.EVAL_READ = "eval.read"` and `Permission.EVAL_RUN = "eval.run"` in
`app/core/permissions.py`. `SYSTEM_ROLES`:

- `viewer` gains `eval.read`;
- `editor` and `owner` gain both.

Two mechanisms carry the grants, matching how Phase 2.1 seeded them:

- **The migration** inserts the `role_permissions` rows for the three system roles in raw SQL,
  with the permission strings written as literals. It must not import application code, for
  the reason `app/core/role_seed.py`'s docstring gives.
- **`ensure_system_roles`** (`app/core/role_seed.py`) reads `SYSTEM_ROLES`, so the test harness
  and the `restore-system-roles` CLI pick the new grants up with no change.

A migration cannot reach Redis, so grant snapshots cached before the upgrade lack the new
permissions until their TTL expires. `docs/deployment.md`'s upgrade step therefore gains one
line: run `restore-system-roles` after `migrate-prod`, which bumps the grant-cache epoch
(`app/cli.py`). Skipping it delays the Eval tab for existing sessions by at most one TTL; it
never grants anything wrongly.

Admin-defined custom roles gain nothing: an admin grants them deliberately.

Still no `conversation.*` permission, so `tests/test_permissions.py` is unaffected on that
point.

### 6.2 Audit

The catalogue in `app/core/audit.py` gains four events, all recorded after their commit:

| Event | Route | `target` | `changed` / context |
| --- | --- | --- | --- |
| `eval_set.generation.requested` | `POST /projects/{id}/eval-sets` | set id, label = name | `changed`: `name`, `sourcePath`, `requestedCount`, `mix` (create shape) |
| `eval_set.deleted` | `DELETE /eval-sets/{id}` | set id, label = name | `changed`: `name`, `sourcePath`; context `pairCount`, `runCount` |
| `eval_pair.updated` | `PUT /eval-pairs/{id}/excluded` | pair id, label = set name | `changed`: `excluded` |
| `eval_run.requested` | `POST /eval-sets/{id}/runs` | run id, label = set name | context `pairCount` |

**No question, reference, answer or judge reason** appears in any of them: the content ban.
Set and run completion are not audited. A job did it, not a person: exemption 4's reasoning,
which `.claude/rules/audit-trail.md` now names for eval jobs as well as ingestion. That
sentence is added to the rule in this change. It extends the stated reason to a new job type,
not the exemption list, so the count of seven is unchanged. The recorder call-site count rises
by four.

### 6.3 Live events

`LiveKind` (`app/live/kinds.py`) gains `"eval_set"` and `"eval_run"`. Stages: set
create / claim / ready / failed / delete; run create / claim (`running`) / done / failed; and
pair exclusion (as an `eval_set` invalidation of its set). Each stages from the repository or
service method that writes the state (`.claude/rules/live-events.md` rule 3).
`live_event_visible_to` needs no new branch: both kinds are project-scoped and follow
`resolve_project_scope`. `tests/test_live_event_sites.py` names the new sites. Every screen
polls as its fallback.

### 6.4 Notifications

None (§0.1 decision 7).

## 7. Worker and configuration

### 7.1 Topics

`askrepo.eval.jobs`, a retry ladder with the same shape as the checklist family's, and
`askrepo.eval.dlq`, created with the others and listed in `ALL_*_TOPICS`.
`EvalJobMessage(kind: Literal["generate", "run"], target_id, project_id, job_id, attempt)`
follows `ChecklistJobMessage`. The consumer pauses its partitions and keeps polling during a
job, like every consumer here. A run of 50 pairs, each with a judge call, can take many
minutes.

### 7.2 Reconcile

The worker's 60-second tick gains `EvalSetRepository.claim_stranded` and
`EvalRunRepository.claim_stranded`, written on the checklist pattern rather than the project
one. A set is `generating` and a run is `running` throughout their claim, so status alone says
nothing about whether a worker holds them. `claim_stranded` stamps `updated_at`, and a failed
run that is coming back calls `defer`. The `CLAUDE.md` section on the checklist sweep applies
verbatim, and §3.2's skip-existing-results step is what makes a re-published run cheap.

### 7.3 Settings

Each lands in `app/config.py`, `backend/.env.example` and `docs/configuration.md` together.

| Setting | Default | Meaning |
| --- | --- | --- |
| `KAFKA_EVAL_TOPIC` | `askrepo.eval.jobs` | The job topic |
| `KAFKA_EVAL_PARTITIONS` | `1` | Concurrency as topology: one eval job per instance |
| `EVAL_SCROLL_PAGE_SIZE` | `256` | Points per scroll page during set generation |
| `EVAL_ANSWER_CONCURRENCY` | `2` | Pairs answered and judged at once inside one run |

There is no setting for the counts (10/25/50): they are a fixed schema enum, as the PRD
specifies.

## 8. Frontend

- **An Eval tab on `/projects/[id]`**, beside Members, shown when the caller holds `eval.read`.
  It lists sets (name, path, pair count, status, latest run's hit rate and verdict split). A
  **Generate eval set** dialog (`forms.md`: a dialog, because it is three fields) offers name,
  path (the existing indexed-path picker), count and mix. The button and dialog are hidden
  without `eval.run`, which is cosmetic: `require_permission` is the control.
- **`/projects/[id]/eval/[setId]`**, a detail route added to `navigation.md`'s breadcrumbs:
  - the pairs table (type, question, file, an expandable reference, an exclude toggle for
    `eval.run`);
  - the runs table (when, stamps, hit rate, split, status) with **Run** (disabled while a run
    is in flight, rather than letting it `409`);
  - **Compare**: pick two runs to see §4.1's view and §4.3's warning;
  - a run's results open in a sheet (question, answer, verdict, reason, hit, warnings).
- Live: `eval_set` / `eval_run` invalidations refetch, with a 60-second poll as the fallback
  while anything is `pending`/`generating`/`running`.
- Tokens, components and dark mode per `design-system.md`; no new shadcn component beyond what
  the profile work installs.
