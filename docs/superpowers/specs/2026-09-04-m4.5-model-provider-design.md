# M4.5 — Model Provider Abstraction: Design

## 0. What this milestone delivers

`docs/PRD.md` §6 names four things a configuration-only OpenAI-compatible endpoint cannot
buy: a native Anthropic adapter (the one provider on the list that is not OpenAI-shaped), a
capability precondition probed at startup rather than discovered on the first generation, retry
classification for hosted-provider failure modes a local Ollama endpoint never produces, and a
spend bound on checklist generation's one-call-per-file cost shape.

This design answers the four points PRD explicitly leaves to whoever specifies the milestone,
plus one scope decision made while writing it:

- The capability probe is a **live test call at boot**, not a name-based registry — no allowlist
  of model prefixes to maintain, no per-release updates as new models ship. It works identically
  for any `CHAT_PROVIDER`/`CHAT_BASE_URL`/`CHAT_MODEL` combination, named or not: an operator
  types a base URL and a model code, and the same one check runs regardless of what is on the
  other end of that URL. This is what actually delivers PRD §6's "an instance should fail to
  boot on a model it cannot use" while staying general — a registry approach (considered and
  rejected during design) could only ever be general for the failure case ("boot fine, discover
  later"), not for the guarantee PRD asks for.
- The spend bound is a per-job file-count cap, not a rolling token/cost budget or a rate limit —
  it bounds the worst single invoice with no new state beyond one setting.
- Chat failures get their own error taxonomy (`TerminalChatError` / `RetryableChatError`),
  separate from `TerminalIngestionError` / `RetryableIngestionError` — naming the failure domain
  accurately rather than continuing the existing (pre-M4.5) reuse.
- **Scope grows beyond the PRD's wording by one item, decided during this design**: the
  embedding provider already supports hosted endpoints today (`EMBEDDING_PROVIDER=openai` or
  `voyage`), and its existing failure classifier has the identical bug PRD calls out for
  chat — a 404 (bad model name) or a 400/422 (context-length) is bucketed as *retryable* today,
  so an instance misconfigured against the embedder retries a failure retrying cannot fix. This
  design fixes that alongside the chat-side work, since it is the same bug in the same shape.
  `docs/PRD.md` §6's M4.5 paragraph gets a line added in the same change to say so.

Two things PRD already settles that this design does not revisit: the embedder stays local even
when the answerer is hosted (`CLAUDE.md`'s "Keep the embedder local" note), and switching chat
providers is configuration, not a migration — no code here touches re-indexing or collection
naming.

## 1. Native Anthropic adapter

`app/config.py`'s `chat_provider: Literal["ollama", "openai"]` becomes
`Literal["ollama", "openai", "anthropic"]`. `app/rag/chat.py`'s `build_chat_model` gets a third
branch:

```python
if settings.chat_provider == "anthropic":
    from langchain_anthropic import ChatAnthropic

    return ChatAnthropic(
        model=settings.chat_model,
        base_url=settings.chat_base_url,
        api_key=settings.chat_api_key or "",
        temperature=settings.chat_temperature,
    )
```

Locally imported, matching the `ollama`/`openai` branches and the embedder's own
`build_embedder` shape — an instance running `ollama` never imports `langchain_anthropic`, so a
broken or absent optional dependency on one provider cannot break another. New dependency:
`langchain-anthropic` in `backend/pyproject.toml`.

`CHAT_BASE_URL` needs no special-casing. Its default (`http://localhost:11434`) is Ollama-shaped,
and `openai` already requires an operator to override it today (there is no code path that
defaults it to `https://api.openai.com/v1` when the provider changes) — `anthropic` follows the
identical convention. `docs/configuration.md` documents the expected value
(`https://api.anthropic.com`) the same way it documents OpenAI's.

`CHAT_API_KEY` and `CHAT_MODEL` are reused verbatim. No new settings for this section.

## 2. Error taxonomy and retry classification

### 2.1 Chat: new error classes

`openai` and `anthropic`'s Python SDKs converge on the same exception names — both were
generated by the same SDK tooling and both raise `RateLimitError`, `AuthenticationError`,
`NotFoundError`, `BadRequestError`, `APIConnectionError`, `APITimeoutError`, and
`InternalServerError` from their respective `openai`/`anthropic` packages. New module
`app/rag/errors.py`, shaped like `app/ingestion/errors.py`:

```python
class ChatError(Exception):
    """Base for every failure a chat-model call raises deliberately."""

class TerminalChatError(ChatError):
    """Retrying will not help: rejected key, unknown model, context-length rejection."""

class RetryableChatError(ChatError):
    """A transient failure: rate limit, provider outage, connection blip."""
```

`classify_chat_error(error: Exception) -> ChatError | None` matches by exception class name
(imported locally, so a process running `ollama` never imports either hosted SDK just to
classify an error it will never see):

| Exception name | Classification |
| --- | --- |
| `RateLimitError`, `APIConnectionError`, `APITimeoutError`, `InternalServerError` | `RetryableChatError` |
| `AuthenticationError`, `NotFoundError`, `BadRequestError` | `TerminalChatError` |
| anything else | `None` — unclassified, falls through to the existing safety net |

This is deliberately *not* exhaustive. An unmapped exception keeps today's behaviour — retried
once, then dead-lettered — per `.claude/rules/ingestion.md`'s existing rule that an unclassified
failure is a safety net, not a design, and the fix for one found in production is to classify it,
not to widen the net speculatively.

### 2.2 Where chat classification is applied

`app/checklist/generator.py`'s two `model.ainvoke(...)` call sites — `_observe` (the per-file map
call) and `_propose`'s reduce call — currently have **no** exception handling. Both gain:

```python
try:
    result = await model.ainvoke(...)
except Exception as error:
    raise classify_chat_error(error) or error from error
```

The "reduce step returned an unusable shape" branch (`generator.py:276`) changes from
`RetryableIngestionError` to `TerminalChatError` — a model that cannot produce the requested
shape will not produce it on a retry either. The boot-time probe (§3) already verifies this
model can do structured output at all; reaching this branch in production means either a real
schema (the checklist's `ProposedChangeSet`, larger and more constrained than the probe's
trivial one — see §3's known limitations) tripped a capability the fixed boot check did not
exercise, or the provider regressed after boot. Either way, retrying will not help, so it stays
terminal.

`app/queue/checklist.py`'s `handle_checklist_message` adds the new types to its existing
branches rather than adding new ones — the handling (`_fail` vs `_defer`) is identical regardless
of which taxonomy raised it:

```python
except (TerminalIngestionError, TerminalChatError) as error:
    ...
except (RetryableIngestionError, RetryableChatError) as error:
    ...
```

No shared base class is introduced for this — two tuple excepts cover it, and inventing an
inheritance hierarchy to unify two categories that already exist under different names would be
the kind of abstraction `CLAUDE.md`'s general rules ask to avoid absent a second concrete need.

**Scope boundary:** this classification applies only where a failure can be retried — the
checklist generation queue. Conversation answering and the checklist refinement chat
(`app/rag/answerer.py`) never retry a model call; a failure there already surfaces as an `error`
SSE event per `.claude/rules/rag.md`'s streaming contract, so `classify_chat_error` is not called
on that path. Its callers are `app/checklist/generator.py` and the boot-time probe (§3).

### 2.3 Embedding: sharpening the existing classifier

`app/ingestion/embedder/openai.py` and `voyage.py`'s `_post` already classify by HTTP status
code into the existing `TerminalIngestionError` / `RetryableIngestionError` — these names are
already correct here, since embedding genuinely is part of ingestion (and of query-time
retrieval, which reuses the same embedder). The current mapping is coarser than it should be:

```python
if response.status_code in (401, 403):
    raise TerminalIngestionError("Embedding provider rejected the credentials.")
if response.status_code >= 400:
    raise RetryableIngestionError(f"Embedding provider returned {response.status_code}.")
```

A 404 (model name does not exist) or a 400/422 (context-length exceeded, malformed batch) falls
into the second branch today and is retried three times for nothing — the identical bug PRD
calls out for chat, already present here before this milestone. Both embedders' `_post` gain an
explicit branch:

```python
if response.status_code in (401, 403):
    raise TerminalIngestionError("Embedding provider rejected the credentials.")
if response.status_code in (400, 404, 422):
    raise TerminalIngestionError(f"Embedding provider rejected the request ({response.status_code}).")
if response.status_code >= 400:
    raise RetryableIngestionError(f"Embedding provider returned {response.status_code}.")
```

No new error classes for this half — `TerminalIngestionError`/`RetryableIngestionError` already
name the embedding-failure domain correctly, unlike the chat case in §2.1.

## 3. Capability probe

Every structured path in the app (`with_structured_output`, used by the checklist's map/reduce
steps and the graph's classify/grade nodes) requires tool-calling or a JSON mode. A model
lacking it fails illegibly — "returned an unusable shape" — on whatever call happens to need it
first, which could be minutes into a generation run. PRD §6 is explicit that this belongs at
startup: "an instance should fail to boot on a model it cannot use, not fail on the first
generation."

### 3.1 One real call, against whatever is configured

A new function, `app/rag/capability.py`:

```python
class TrivialProbeSchema(BaseModel):
    """The smallest schema that proves structured output works: one required field."""
    answer: str

async def probe_structured_output(chat_model: BaseChatModel) -> None:
    """Raise if this model cannot produce a trivially-shaped structured response.

    Provider-agnostic on purpose: it asks nothing about which provider or model is
    configured, so it verifies literally any `CHAT_BASE_URL`/`CHAT_MODEL` pair the same
    way, including a self-hosted endpoint under a name nobody has catalogued.
    """
    model = chat_model.with_structured_output(TrivialProbeSchema)
    try:
        result = await model.ainvoke("Reply with any short string in the `answer` field.")
    except Exception as error:
        raise classify_chat_error(error) or TerminalChatError(
            f"chat model probe failed: {type(error).__name__}"
        ) from error
    if not isinstance(result, TrivialProbeSchema):
        raise TerminalChatError(
            "configured chat model did not return a usable structured response "
            "(no tool-calling or JSON mode support)"
        )
```

No registry, no provider branching, no model-name matching — the exact same function runs for
`ollama`, `openai`, and `anthropic` alike, because `with_structured_output` is the one interface
every `BaseChatModel` this app builds already implements. "General like opencode" falls out of
this for free: an operator's only inputs are `CHAT_BASE_URL` and `CHAT_MODEL` (plus `CHAT_PROVIDER`
to pick the wire protocol and `CHAT_API_KEY` where needed), and the probe verifies whatever that
resolves to without needing to have heard of it.

### 3.2 Where it runs

Called once per process, immediately after `build_chat_model`, in **both** places a chat model is
built — and, deliberately, in only one of the two spots relative to each file's existing structure:

- `app/main.py`'s `lifespan`: **after** the `APP_ENV=test` guard, alongside `ensure_topics` and
  the queue startup — not immediately after `build_chat_model` the way `app.state.chat_model` is
  assigned. `build_chat_model` opens no socket and the test suite needs the object present even
  under `APP_ENV=test`; a live probe does open one and would make every test-suite boot depend on
  a reachable model endpoint. Skipping it under `APP_ENV=test` matches why the Kafka producer is
  already skipped there.
- `app/worker.py`'s startup, at the same point `embedder.dimensions = await probe_dimensions(...)`
  already runs for the embedder — the two probes sit side by side for the same reason, and the
  worker has no test-mode branch to route around.

A failure raises `TerminalChatError` (or lets one propagate from `classify_chat_error`, §2.1),
which is left unhandled at both call sites — an unhandled exception during `lifespan`/worker
startup is exactly "fail to boot," which is the behaviour PRD asks for. The error message names
the exception type so the operator sees "chat model probe failed: AuthenticationError" or "...did
not return a usable structured response," not a generic timeout three layers removed from the
cause.

### 3.3 What this costs, and why it's accepted

One real call per process start (and per worker restart) against whatever `CHAT_BASE_URL` names —
a small, fixed token cost for a hosted provider, and a request Ollama already serves for free.
Boot now also depends on that endpoint being reachable, which is a new failure mode for local
development (an unreachable Ollama blocks the API and worker from starting, not just from
answering) — `make dev`/`make worker`'s existing "warn, never fail, when nothing answers on
:11434" behaviour (`CLAUDE.md`) does not cover this, since a probe failure is a hard `raise`, not
a soft warning. This trade-off is accepted because it is the only design considered that is both
general (§0) and satisfies PRD's boot-time-fail requirement — a registry is general only in the
success case, and a registry-plus-live-fallback (the shape considered earlier in this design's
history) reintroduces the exact allowlist this section removes for the common case.

One retry is not attempted inside the probe itself. A boot failure is loud and immediately
actionable — the operator fixes the setting or the network and restarts the process — so a
retry loop here would only delay a signal that is supposed to be delivered as fast as possible.

The probe's fixed trivial schema (`TrivialProbeSchema`: one string field) is a proxy, not a
guarantee, for every real schema the app sends later — `FileObservations`, `ProposedChangeSet`,
and the graph's classify/grade schemas are larger and more constrained. A model that passes this
check and still fails on a real one raises `TerminalChatError` from `generator.py` (§2.2) instead
of from the boot probe; this is accepted as the best available boot-time signal, not an
exhaustive one, and is a known limitation rather than a defect.

## 4. Spend bound: per-job file cap

`docs/PRD.md` §6 leaves the bound's scope open ("per job, per project, or per instance") and
whether exceeding it fails the job or degrades to fewer files with a coverage note. This design
picks the latter on both counts: a per-job cap on the number of files mapped, with the excess
reported the same way `partial_paths` already reports incomplete reads (spec
`2026-09-01-m4-qa-checklist-design.md` §4.3/4.6) — nothing new to teach the reviewer, one more
line in a coverage note they already read.

New setting: `checklist_max_files_per_job: int = Field(default=200, ge=1)` /
`CHECKLIST_MAX_FILES_PER_JOB`. Rationale for scope: per-job rather than per-instance or
per-project, because the cost driver PRD names is "one model call per file," which is a property
of a single generation run, not of cumulative usage — a rolling budget answers a different
question ("how much could this cost us this month") that nobody asked for in the PRD text, and
would need pricing data per provider/model to convert tokens into a dollar figure, plus a
reset/decay policy. A file-count cap needs neither.

### 4.1 Where it applies

`app/checklist/source.py`'s `ModuleSource` gains a field:

```python
@dataclass(frozen=True, slots=True)
class ModuleSource:
    files: list[ModuleFile]
    partial_paths: list[str]
    skipped_paths: list[str]   # new: entirely uncounted against the per-job file cap
```

`rebuild_files` already produces `files` sorted by path (`for path in sorted(grouped)`), which
gives the cap a deterministic, reviewable cut rather than an arbitrary one. The cap is applied
where the caller has both the settings and the full file list — `generator.py`'s `_propose`,
before the `TaskGroup` maps over `source.files`:

```python
async def _propose(self, *, module_name, source, existing):
    files = source.files
    skipped = source.skipped_paths
    if len(files) > self.settings.checklist_max_files_per_job:
        cap = self.settings.checklist_max_files_per_job
        skipped = [*skipped, *(file.path for file in files[cap:])]
        files = files[:cap]
    ...
```

(`skipped_paths` starts empty from `rebuild_files` today — this reads as if it always existed,
future-proofing `ModuleSource` for a source of skipped files other than the cap, but nothing
else populates it yet; YAGNI does not block adding the field where the dataclass is already
being touched for this exact purpose.)

### 4.2 Reporting

Both existing coverage surfaces gain a second bullet, parallel to `partial_paths`:

- `build_reduce_prompt` (`app/rag/prompts.py`): the model is told which files it never saw, so
  it cannot claim behaviour it was not shown.
- `_summarise` (`generator.py`): `"skipped: N files over the 200-file cap"` appended after the
  existing `"partial: ..."` clause, only when non-empty.

## 6. Testing

- `classify_chat_error`: table-driven, one case per exception name in §2.1's table, plus one
  case proving an unmapped exception returns `None`.
- `probe_structured_output`: a fake `BaseChatModel` whose `with_structured_output(...).ainvoke`
  returns a valid `TrivialProbeSchema` (probe passes, no raise); one that raises an SDK exception
  (probe raises the classified error); one that returns the wrong shape (probe raises
  `TerminalChatError`). No real network or provider needed — the fake stands in for
  `BaseChatModel` the way LangChain's own test doubles already do elsewhere in this codebase.
- `build_chat_model`'s new `anthropic` branch: mirrors `tests/test_chat_model.py`'s existing
  `openai` case — settings in, correct `ChatAnthropic` construction out, no network.
- Both startup call sites (`main.py`'s `lifespan`, `worker.py`'s startup): a test proving the
  probe is skipped under `APP_ENV=test` (no fake network dependency introduced into the existing
  test-mode boot), and one proving a worker startup with a failing probe does not proceed to
  build the ingestion pipeline.
- `handle_checklist_message`: existing tests extended with a case per new tuple-except branch
  (`TerminalChatError` behaves like `TerminalIngestionError`; `RetryableChatError` like
  `RetryableIngestionError`), proving the dispatch and not just the exception's existence.
- `_propose`'s cap: `N + k` files in, `N` processed (`with_structured_output` called `N` times,
  not `N + k`), `k` in `skipped_paths`, and the reduce prompt's coverage note names them.
- Embedder status-code branches: extend the existing `OpenAIEmbedder`/`VoyageEmbedder` tests with
  404 and 400/422 cases asserting `TerminalIngestionError`, proving they no longer fall into the
  `>= 400` retryable bucket.
- No new `integration`- or `model`-marked test is needed: every piece above is classification
  logic, settings wiring, or a bounded-list transform, all reachable with fakes the way the rest
  of the suite already tests these subsystems (`.claude/rules/ingestion.md`'s testing section).

## 8. Known limitations / explicitly out of scope

- **No skip/override setting for the boot-time probe.** An operator who wants to boot without a
  reachable model endpoint (an air-gapped environment, certain CI setups) has no escape hatch
  besides `APP_ENV=test`, which also skips Kafka and is not meant as a general-purpose bypass.
  Deferred until a real need is reported rather than designed speculatively.
- **The probe is a proxy, not a guarantee, for every real schema** (§3.3) — passing the trivial
  check does not prove `FileObservations`, `ProposedChangeSet`, or the graph's classify/grade
  schemas will also succeed. A model that regresses on those still fails as a
  `TerminalChatError` from `generator.py`, just not at boot.
- **The spend bound does not model actual cost.** A 200-file cap says nothing about token count
  per file or price per token across providers — it bounds the *shape* of the worst case (calls
  made), not the dollar figure. A rolling cost budget remains open per PRD §6's framing, if this
  proves insufficient once real hosted usage exists.
- **No retry inside the boot probe itself** (§3.3) — a transient failure at boot (a momentary
  network blip against a hosted provider) fails the process rather than retrying in place; the
  operator restarts. Consistent with treating a boot failure as a loud, immediately actionable
  signal rather than something to paper over.
