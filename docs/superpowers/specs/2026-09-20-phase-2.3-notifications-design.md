# Phase 2.3 — Notifications: the record, and in-app delivery: Design

**Date:** 2026-09-20
**Intent:** `docs/PRD.md` §2.1, Phase 2.3
**Depends on:** Phase 2.1 (per-project RBAC), Phase 2.2 (audit trail)
**Followed by:** Phase 2.4, which adds the email transport against the record defined here

---

## 0. What this document covers

Every long-running operation in AskRepo finishes in silence. A twenty-minute index,
a checklist generation, a mock-data generation — the only way to learn any of them
finished is to reload the screen showing its status column. That is tolerable for the
person who pressed the button and useless for everyone else, which is the wrong way
round for a checklist §4.3 publishes to every member of its project: the reviewer who
has to act is routinely not the person who started the generation.

This sub-phase ships **the record and the in-app transport**. Email ships at Phase 2.4
against the same record, adding no table and no read state.

What is in scope: three tables, a fan-out path at nine call sites, one new function in
`app/core/access.py`, six routes, a bell with a polled unread count, a
`/notifications` page, and a `/settings/notifications` preferences screen.

What is deliberately **not** in scope: any SMTP dependency, any outbound queue, any
socket or server-sent stream for notifications, and any digest or batching. §2.1
settles the last one by implication — the in-app transport is a polled integer, and
digesting is a property of email.

### 0.1 The decisions, made

1. **Six event categories**, expanding to eleven enum members (checklist and mock data
   are separate targets with separate permissions and separate links, and each of
   `pending` / `applied` / `discarded` is its own member). §3.
2. **Two tables for the record, one for preferences.** `notification_events` holds one
   row per occurrence; `notifications` holds one row per recipient and carries read
   state; `notification_preferences` is sparse, absence meaning on. §2.
3. **Recipients are members holding the permission the event is about**, resolved
   through one new function in `app/core/access.py`. §4.
4. **Fan-out happens inside the transaction that made the event true** — approach A.
   The event row, the recipient rows and the state change commit together or not at
   all. §5.
5. **The row is structured, not a rendered sentence.** The frontend owns the wording.
   §2.2.
6. **Preferences snapshot onto the delivery row; they do not gate its creation.** §2.4.
7. **A bell plus a full page**, both reading a polled count. §8.
8. **`NOTIFICATION_RETENTION_DAYS` defaults to 90**, diverging from
   `AUDIT_RETENTION_DAYS`'s `0` for a stated reason. §7.

### 0.2 Three amendments to `docs/PRD.md`, made in this same change

`.claude/rules/documentation.md` requires a decision that changes a documented fact to
update the doc in the same change. Three do.

1. **`membership.granted` is a sixth event.** §2.1 names five. A user added to a
   project has no other way to learn it — the project simply appears in their list with
   no announcement, which is the one case where the notification is not a convenience
   over a status column but the only signal that exists. §3.3.
2. **A fifth audit exemption.** `.claude/rules/audit-trail.md` states that every write
   records an audit event, with four named exemptions. Marking a notification read is a
   write and matches none of them. §6.
3. **The `email` preference column ships stored and inert.** §2.4 explains why storing
   it now is not the same as building email now.

### 0.3 The two constraints that are not negotiable

**Recipient selection must not become a second access resolver.** §2.1 states this
directly, and names the failure: not an empty list, but a notification naming a private
repository to someone who was never given it. Phase 2.1 already decided who may see a
project. This phase asks the same question from the other end and must not answer it
independently. §4 is the mechanism; `tests/test_scoping_is_single_point.py` is the
enforcement.

**`created_by` stays attribution.** §7 restricts that column and Phase 2.1 removed the
last gate that read it. The person who started a reindex is reachable here as *the
actor on the event row*, never as a scope. Nothing in this design reads `created_by`.

## 1. Why in-app first, and what that buys

`docs/PRD.md` §8 records the split: in-app at Phase 2.3, email at Phase 2.4, and calls
this "sequenced, not resolved". In-app costs a table and a polled count and adds no
infrastructure and no egress path. Email costs an SMTP dependency, deliverability from
a box that is deliberately unreachable, and the §9 egress question.

What the split buys is a decision *informed*: by the time Phase 2.4 starts, the polled
unread count has been in real use and there is evidence about whether people actually
miss things. §8 states plainly that **Phase 2.4 may conclude in-app was enough**, and
that this is a legitimate outcome.

Two obligations follow for this document, and they are the reason the seams below are
specified so carefully:

- **Phase 2.4 must be additive.** It adds a sender and a delivery-state column or child
  table. It must not reshape `notification_events`, must not reshape `notifications`,
  and must not need a second recipient path.
- **Phase 2.4 must be droppable.** If the evidence says in-app was enough, nothing here
  becomes dead weight. The `email` preference column is the only artefact that would be
  left unused, which is one nullable boolean.

## 2. The tables

Three tables, one Alembic revision.

### 2.1 `notification_events` — one row per occurrence

| Column | Type | Notes |
| --- | --- | --- |
| `id` | `UUID` pk | |
| `event_type` | `String(64)` | A `NotificationType` value. Stored, and a wire contract |
| `actor_user_id` | `UUID` FK `users.id`, nullable | `NULL` for worker-originated outcomes |
| `project_id` | `UUID` FK `projects.id`, **not null** | Every event is project-scoped |
| `target_type` | `String(32)`, nullable | `project` or `checklist_module`. §3.4 |
| `target_id` | `UUID`, nullable | **Not** an FK |
| `details` | `JSONB`, not null, default `{}` | Per-event allowlist. §2.3 |
| `created_at` | `timestamptz`, not null | Declared explicitly |

Indexes on `project_id`, `created_at`, `event_type`.

**`actor_user_id` is nullable for the same reason `audit_events.actor_user_id` is.** A
finished index has no actor — nobody did it, a job did. That is `audit-trail.md`'s
fourth exemption stated as a column: fabricating an actor would record a lie.

**`target_id` is deliberately not a foreign key.** The row it points at may be deleted,
and an FK would either block that delete or cascade away the notification of it. Same
reasoning as `audit_events.target_id`.

**The table carries neither mixin**, for two of `audit_events`' three reasons and not
the third:

- **No `updated_at`.** An occurrence is never mutated. `TimestampMixin` ships
  `onupdate=func.now()`, which has no business on a row nothing updates.
- **No `deleted_at`.** There is no soft-delete path worth having: nobody deletes a
  notification, and `BaseRepository.active_select()` would be filtering a column that
  is always `NULL`.
- **Unlike `audit_events`, these rows are hard-deleted** — by retention, §7. Append-only
  is not a property of this table and must not be claimed for it. `audit_events` is
  append-only because it is *the record*; this is a nudge with a shelf life.

### 2.2 `notifications` — one row per recipient

This is §2.1's per-`(user, event)` row, and where read state lives.

| Column | Type | Notes |
| --- | --- | --- |
| `id` | `UUID` pk | |
| `event_id` | `UUID` FK `notification_events.id` **`ON DELETE CASCADE`** | §7 |
| `user_id` | `UUID` FK `users.id`, not null | |
| `in_app_visible` | `bool`, not null | Preference snapshot. §2.4 |
| `read_at` | `timestamptz`, nullable | |
| `created_at` | `timestamptz`, not null | Denormalized from the event |

- `UNIQUE (event_id, user_id)` — the deduplication boundary §2.1 names by hand.
- Partial index on `(user_id)` `WHERE read_at IS NULL AND in_app_visible` — the polled
  count reads nothing else.
- Index on `(user_id, created_at DESC)` — the list.

`created_at` is denormalized so neither the count nor the list joins to the event table
to order or bound itself. The cost is one duplicated timestamp on a row that is never
updated.

**No soft delete.** A user marks read; they do not delete. Retention is the only
remover, and it removes by age, not by anyone's request. If "dismiss" is ever wanted,
it is a second nullable timestamp on this row, not a `deleted_at`.

**The row is structured, and the frontend owns the sentence.** No `title`, no `body`.
Text frozen at write time describes a module that may since have been renamed, and puts
the app's wording in the worker rather than in the UI where every other string lives.
A renamed module reads correctly in a month-old notification because the notification
never claimed to know its name.

### 2.3 `details`, and the seam that Phase 2.4 must not cross

`details` is a `JSONB` envelope under a **per-event allowlist**, declared in
`app/core/notifications.py` beside the catalogue — the same shape and the same reason as
`app/core/audit.py`'s `CHANGED_FIELDS`. Keys are `camelCase` as stored, so `ApiModel`
has nothing to translate and the stored bytes match the wire. Capped at 2 KB; a payload
past it is replaced wholesale rather than truncated, so a reader never mistakes a
truncation for the record.

Per-event payloads are in §3.3. They are small: `projectName`, `moduleName`,
`pendingCount`, `itemCount`, `roleName`.

**Those are display names, and they are safe in-app precisely because they are not safe
in an email.** Every recipient of an in-app notification is, by construction, a member
of the project who can already read both names on the screen behind the bell. §2.1
states that an email carries the event type and a link and nothing else — never an
answer, an excerpt, an expected result, a checklist row, or anything derived from clone
output — because email is the instance's first path *out* of a network whose whole
posture is that nothing leaves.

So: **Phase 2.4's composer reads `event_type` and `target_id` and never touches
`details`.** Writing that down now costs one paragraph. Rediscovering it after a mail
host exists costs an argument about whether a project name is really repository content,
held at the worst possible time.

This is not a scrubbing obligation in disguise. Nothing on this path holds a secret:
the fan-out is handed plain scalars a service chose, never a clone URL or a PAT, and
`scrub` needs the secret in hand to replace it. The allowlist is the mechanism, exactly
as it is for `audit_events`, and `NotificationPayload.details()` raises `ValueError` on
a key nobody named.

### 2.4 `notification_preferences` — sparse, absence meaning on

| Column | Type | Notes |
| --- | --- | --- |
| `id` | `UUID` pk | |
| `user_id` | `UUID` FK `users.id`, not null | |
| `event_type` | `String(64)`, not null | |
| `in_app` | `bool`, not null, default `true` | |
| `email` | `bool`, not null, default `true` | Stored; read by nothing in 2.3 |

`UNIQUE (user_id, event_type)`. Carries `TimestampMixin` — a preference is mutated — and
no `SoftDeleteMixin`, because a preference is upserted, never deleted.

**Rows are sparse and absence means on.** No backfill migration for existing users, and
a seventh event type added later is on for everybody with no data migration. The failure
direction is "you were told about something new", not "the feature silently did nothing
for everyone who predates it".

**Preferences snapshot onto the delivery row; they do not gate its creation.** This is
the single most important consequence of the Phase 2.4 seam, and the obvious
implementation gets it backwards.

The `notifications` row *is* the per-`(user, event)` record, and §2.1 defines email as a
delivery attempt against that row. If `in_app: false` suppressed the row, then a user
who has muted in-app but wants email — the precise combination the preference screen
exists to offer — would have nothing to email against, and Phase 2.4 would be forced to
invent a parallel recipient path. That is the divergence "one record, two transports"
exists to prevent, arriving through the one door nobody was watching.

So a row is written for **every resolved recipient**, and `in_app` is copied onto it as
`notifications.in_app_visible` at fan-out time. Three consequences:

- The unread count and the list filter on that column, which is in the partial index.
  No read-time join to preferences on the polled path.
- Changing a preference does not retroactively reveal or hide what already happened,
  which is what people expect from a notification setting.
- Phase 2.4 reads `notification_preferences.email` at send time, against rows that
  already exist.

**The `email` column ships now and is honoured by nothing.** The alternative — adding it
at 2.4 — means 2.4 touches the schema, the settings screen and the mail path in one
change. Shipping the column now means 2.4 adds a sender. The UI renders the email
switches disabled with one line saying email delivery is not configured on this
instance, so the user sees the shape of the feature and is never told something untrue.

## 3. Events

### 3.1 The catalogue

`NotificationType`, a `StrEnum` in `app/core/notifications.py`, for the reason
`app/core/permissions.py` and `app/core/audit.py` both give: if existence lived in a
table, deleting a row would orphan every write site that names it. Values are stored
and are a wire contract — add members, never rename them.

```
PROJECT_READY                    = "project.ready"
PROJECT_FAILED                   = "project.failed"
PROJECT_REINDEX_FINISHED         = "project.reindex.finished"
PROJECT_REINDEX_FAILED           = "project.reindex.failed"
CHECKLIST_CHANGE_SET_PENDING     = "checklist_change_set.pending"
CHECKLIST_CHANGE_SET_APPLIED     = "checklist_change_set.applied"
CHECKLIST_CHANGE_SET_DISCARDED   = "checklist_change_set.discarded"
MOCK_DATA_CHANGE_SET_PENDING     = "mock_data_change_set.pending"
MOCK_DATA_CHANGE_SET_APPLIED     = "mock_data_change_set.applied"
MOCK_DATA_CHANGE_SET_DISCARDED   = "mock_data_change_set.discarded"
MEMBERSHIP_GRANTED               = "membership.granted"
```

Eleven members over the six categories §2.1 and §0.2 agree on. Checklist and mock data
are not collapsed: they carry different permissions, link to different screens, and
`CHANGESET_APPLY` gates both while `CHECKLIST_READ` and `MOCKDATA_READ` do not.

### 3.2 The recipient map

A literal in `app/core/notifications.py`, one entry per member above.

| Event | Recipients | Actor |
| --- | --- | --- |
| `project.ready` | members with `PROJECT_READ` | included |
| `project.failed` | members with `PROJECT_REINDEX` | included |
| `project.reindex.finished` | members with `PROJECT_READ` | included |
| `project.reindex.failed` | members with `PROJECT_REINDEX` | included |
| `checklist_change_set.pending` | members with `CHANGESET_APPLY` | n/a — no actor |
| `checklist_change_set.applied` | members with `CHECKLIST_READ` | **excluded** |
| `checklist_change_set.discarded` | members with `CHECKLIST_READ` | **excluded** |
| `mock_data_change_set.pending` | members with `CHANGESET_APPLY` | n/a — no actor |
| `mock_data_change_set.applied` | members with `MOCKDATA_READ` | **excluded** |
| `mock_data_change_set.discarded` | members with `MOCKDATA_READ` | **excluded** |
| `membership.granted` | **the grantee only** | n/a — §3.3 |

**Narrowing by permission is the product decision §2.1 hands to this phase**, and the
alternative was notifying every member. A viewer told about a change set they cannot
apply is noise, and noise is what trains people to stop reading the bell — which costs
the notifications that mattered. The failure mode of narrowing is milder and visible:
someone who wanted to know did not hear, and can say so.

**Actor exclusion is per-event, not global.** §2.1's wording is "a change set *someone
else* applied", and that is right for a synchronous action the actor just performed —
telling you about your own click is pure noise. It is wrong for an asynchronous outcome
the actor cannot otherwise know: the person who pressed Reindex twenty minutes ago is
exactly who wants to hear it finished. The rule is therefore *exclude the actor where
the notification would report something they just did*, and the `pending` events have no
actor at all because a worker raised them.

### 3.3 `membership.granted` is shaped differently, and it has to be

Its recipient is **the grantee**, who by construction was not a member when the event was
raised. It cannot go through the permission map: `recipients_for(project_id,
MEMBERSHIP_READ)` at the moment of the grant either misses them (resolved before the
flush) or sweeps in every other member too (resolved after).

So the fan-out call for this event passes an explicit recipient rather than a
permission. That is a special case, and the honest way to hold it is to make it
**structurally** special rather than a branch inside the general path:
`NotificationFanout` exposes `raise_event(...)` for the permission-resolved events and
`raise_direct(...)` for this one, and the recipient map has no entry that a reader could
mistake for a permission rule. A branch inside the general path is how "we already have
a recipient resolver" quietly becomes two.

### 3.4 Per-event `details` payloads

| Event | Keys |
| --- | --- |
| `project.ready` | `projectName`, `fileCount`, `chunkCount` |
| `project.failed` | `projectName` |
| `project.reindex.finished` | `projectName`, `fileCount`, `chunkCount` |
| `project.reindex.failed` | `projectName` |
| `checklist_change_set.pending` | `projectName`, `moduleName`, `operationCount` |
| `checklist_change_set.applied` | `projectName`, `moduleName`, `appliedCount` |
| `checklist_change_set.discarded` | `projectName`, `moduleName` |
| `mock_data_change_set.pending` | `projectName`, `moduleName`, `operationCount` |
| `mock_data_change_set.applied` | `projectName`, `moduleName`, `appliedCount` |
| `mock_data_change_set.discarded` | `projectName`, `moduleName` |
| `membership.granted` | `projectName`, `roleName` |

**`target_id` is the screen, not the row.** For both change-set families
`target_type` is `checklist_module` and `target_id` is the module id — `mock_data_records`
and `mock_data_change_sets` key directly to `checklist_modules.id`, and the Mock Data
tab is part of `/checklist/[moduleId]` rather than a route of its own. A change set's
own id names nothing a recipient can navigate to, and a notification's target is the
place the recipient has to go. §8.4 depends on this.

**`project.failed` carries no error text.** `Project.error` holds a scrubbed message and
the project screen renders it; copying it here would put a second copy of clone-derived
output in a second table, for no gain over a link.

## 4. Recipient resolution

### 4.1 The inverse query

`MembershipRepository` gains:

```python
async def recipients_for(
    self, project_id: uuid.UUID, permission: Permission
) -> Sequence[uuid.UUID]:
```

It is `load_grants`' two joins, flipped, plus a join to `users`:
`project_memberships ⋈ roles ⋈ role_permissions ⋈ users`, filtering
`project_id`, the permission value, and `deleted_at IS NULL` on all four.

It belongs on this repository, whose docstring already says it is "what *produces* the
scope" and is deliberately unscoped by `ProjectScope`. Scoping the producer of the scope
would be circular, in this direction as in the other.

**Deactivated accounts are excluded at fan-out**, via the join to `users`. Phase 2.1
leaves memberships intact when an account is deactivated so reactivation restores exact
access — which means a membership row can exist for someone who cannot log in. A
notification row for them is an unread count nobody will ever clear, and reactivating
someone should not drop a month of stale nudges on them.

The permission join is an **inner** join here, unlike `load_grants`' outerjoin. The
reason `load_grants` uses an outer join — a role with no permissions still grants access
to the project — does not apply: the question here is who holds a *specific*
permission, and a role with none holds none.

`ix_project_memberships_project_id` is required; `list_for_project` already depends on
it.

### 4.2 The one new function in `app/core/access.py`

```python
async def resolve_notification_recipients(
    memberships: MembershipRepository,
    project_id: uuid.UUID,
    permission: Permission,
    *,
    excluding: uuid.UUID | None,
) -> frozenset[uuid.UUID]:
```

It takes the **repository**, not a session, so `access.py` stays free of query
construction exactly as it is today. `excluding` is the actor, per §3.2.

**It is the file's first async function**, and that is a real wrinkle rather than a
detail to leave for the next reader to trip over. `resolve_project_scope` and
`require_permission` are synchronous because the grants are already in hand —
`AuthContextMiddleware` loaded them for this request's user. There is no equivalent here:
the caller is frequently a worker with no request and no `AuthenticatedUser`, and the
question is about users the caller has never seen. The file's docstring gains a
paragraph saying so.

The alternative — putting this function on the repository and leaving `access.py`
untouched — was rejected. The point of the rule is that *the decision about who may see
a project lives in one file*, and a recipient list is that decision read backwards. A
repository method named `recipients_for` is a query; `resolve_notification_recipients` is
a policy, and the policy is what §7 wants in one place.

### 4.3 An administrator with no membership receives nothing

`require_permission` lets an administrator pass every check. A fan-out that mirrored it
would notify every admin about every project on the instance, which is a firehose
nobody will read and — on an instance whose repository names are inventory of private
codebases — arguably worse than that.

**Permission to see a thing is not interest in hearing about it.** The resolver here
answers the second question, and it answers it from membership alone. Administrators are
notified about the projects they actually hold a membership on, like everyone else.

This asymmetry with `require_permission` is deliberate and is called out in
`.claude/rules/notifications.md`, because the natural "fix" — adding an admin branch for
symmetry — is the bug.

### 4.4 The enforcement

`tests/test_scoping_is_single_point.py` currently greps to prove that read scoping
happens in exactly one function. It gains `recipients_for`: the query may be called from
`app/core/access.py` and nowhere else.

That one line is what turns §2.1's "must not become a second access resolver" from a
warning into a build failure, and it is the cheapest thing in this sub-phase.

## 5. The write path

### 5.1 Approach A: fan-out inside the transaction that made the event true

`NotificationFanout` takes the **caller's session** and `flush`es rather than commits, so
the event row, the N recipient rows and the state change are one transaction. The
precedent is already in the tree: `MembershipRepository.grant` flushes for exactly this
reason, so a project and its owner membership cannot exist apart.

```python
class NotificationFanout:
    async def raise_event(
        self,
        *,
        event_type: NotificationType,
        project_id: uuid.UUID,
        actor_user_id: uuid.UUID | None,
        target_type: str | None,
        target_id: uuid.UUID | None,
        details: dict[str, object],
    ) -> None: ...

    async def raise_direct(self, *, recipient: uuid.UUID, ...) -> None: ...
```

`raise_event` resolves recipients through §4.2, reads their preferences in one query,
inserts the event row and the recipient rows with `in_app_visible` snapshotted, and
flushes. The caller commits.

**Why not an after-commit recorder mirroring `AuditRecorder`?** It would be the nearer
pattern — same file layout, 39 existing call sites, its own rule. It was rejected on the
one axis that matters. `AuditRecorder`'s accepted gap is stated plainly in
`audit-trail.md`: an action that commits and then crashes before its audit write leaves
no row, silently, and the trail is a strong record rather than a complete one. That is
tolerable for something an operator consults after the fact. It is not tolerable for the
one feature whose entire purpose is reaching a person who is not looking at the screen —
there, a missing row means the feature did not happen, and nobody will ever know it
should have. Copying a mechanism because it is adjacent is how an accepted cost gets
inherited by a feature it was never weighed against.

**The objection to approach A, answered.** "A Postgres hiccup during fan-out rolls back
a twenty-minute index." It is weaker than it sounds: the fan-out is a handful of inserts
on the very connection the status commit needs anyway, so a database that cannot take
the inserts was not going to take the commit either. What is bought in exchange is that
*"the generation finished and nobody was told"* is unrepresentable.

**N is small.** One organization, one box, tens of members per project. §2.1 says the
row-per-recipient storage "is affordable precisely because §2 targets one organization
on one box; it would not be at a different scale" — that applies to the write as much as
to the table, and an instance that outgrows it has outgrown §2 first.

### 5.2 Zero recipients still writes the event row

If everyone eligible has muted the event, or the only eligible member is the excluded
actor, the event row is written and no delivery rows are. The record is the record; a
transport having no audience for one occurrence is not a reason to lose it, and Phase
2.4 and any future digest read the event table.

### 5.3 The call sites

**`app/ingestion/pipeline.py`, success.** The path already reads
`released = await self.repository.release(...)` and *then* `await
self.session.commit()`. Fan-out goes in that gap, **guarded on `released`** — which is
exactly the right guard, for free: a lost lease or a project deleted mid-run leaves
`released` false, nothing is announced, and `_discard_unclaimed_generation` runs as it
does today. Whether the event is `project.ready` or `project.reindex.finished` follows
from the status the run started at, which `_advance_status` already distinguishes (a
reindex stays `ready` and is marked by `reindex_in_progress`).

**`app/ingestion/pipeline.py`, `TerminalIngestionError`.** Same shape, same guard,
`project.failed` or `project.reindex.failed`.

**`app/checklist/generator.py`.** The `ChecklistChangeSet` is added and the module moves
to `REVIEW`; `checklist_change_set.pending` goes beside them, before the commit.

**`app/mockdata/generator.py`.** The mirror.

**`app/services/checklist_change_set.py` `apply` and `discard`**, and the mock-data
twins.

**`app/services/membership.py` `grant`** — via `raise_direct`.

### 5.4 Notification before the commit, audit after it — both correct

At the service call sites the two writes straddle the commit in opposite directions,
and it will read as a mistake to anyone who does not know why:

```
… mutate …
await fanout.raise_event(...)      # before: a lost notification is the feature failing
await session.commit()
await recorder.record(...)         # after:  a failed audit must not fail the action
```

`AuditRecorder` runs after because an audit failure must not fail a user's action, and
it opens its own session to guarantee that. Fan-out runs before because a lost
notification is the feature not working. The two durability requirements genuinely point
in opposite directions, and the orderings follow. This is stated in
`.claude/rules/notifications.md` and cross-referenced from `audit-trail.md`.

### 5.5 Payloads are built from locals

As with audit: capture the scalars into plain locals before mutating, and hand the
fan-out a dict. Nothing on this path holds an ORM reference. A fan-out that cannot touch
a `Session` cannot be made to re-read a row that is mid-flush.

## 6. The fifth audit exemption

`.claude/rules/audit-trail.md` states: *"Every write, and every export, records an audit
event. No exceptions beyond the four named in this file."* Marking a notification read
is a write. Changing a notification preference is a write. Neither matches any of the
four.

Auditing them is clearly wrong. A bell clicked forty times a day would bury
`user.deactivated` under exactly the noise §2.5 refuses for the ask route — "one table
would bury 'an admin deactivated an account' under two hundred map calls". But the
correct response to a rule that produces a wrong answer is to amend the rule with its
reason, not to omit the call and leave a hole a future auditor reads as an oversight.

**Exemption 5 — a user's own notification state.** Marking a notification read, marking
all read, and changing notification preferences. Three reasons, and all three are needed:
the row is private to one user; it describes no shared resource and no change to one;
and its write rate is proportional to *attention* rather than to change, which is the
property that makes it a flooding risk rather than merely a low-value row.

Lands in: `.claude/rules/audit-trail.md`'s exemption list, `docs/PRD.md` §2.1 Phase
2.2's exemption bullet (which says "four exemptions are named"), and
`tests/test_audit_coverage.py`, which must be taught about it or it will demand events
for the new routes.

**What is *not* exempt:** nothing else here. There is no other write in this sub-phase —
fan-out is not a user action and has no actor for the events that matter, which is
exemption 4 already.

## 7. Retention

`NOTIFICATION_RETENTION_DAYS`, a new `Settings` field, pruned by the worker's existing
60-second tick beside the audit prune, through a single
`NotificationEventRepository.delete_older_than(cutoff)`. The `ON DELETE CASCADE` on
`notifications.event_id` takes the deliveries with it — the one place in this codebase
where a cascade is the right answer, because a delivery has no meaning without its event
and the two are deleted for the same reason at the same time.

Like `delete_older_than` on `audit_events`, it takes a cutoff and nothing else.

**It prunes by age regardless of read state.** A 90-day-old unread notification is not
going to be acted on; keeping it only inflates a count nobody will clear, and an unread
badge that can never reach zero is a badge people stop looking at.

**The default is 90, and that diverges from `AUDIT_RETENTION_DAYS`'s `0` deliberately.**
Audit defaults to keep-forever because a fresh instance must not silently start
discarding the one record whose purpose is being the record. A notification is a nudge,
not a record — its value is measured in days, and keep-forever would grow a table nobody
reads past a week. The two settings look parallel and are answering different questions;
`docs/configuration.md` says so where both are documented.

## 8. Frontend

### 8.1 The bell

`NotificationBell` in `components/layout/app-navbar.tsx`. A TanStack Query against
`/api/notifications/unread-count` with `refetchInterval: 60_000` and
`refetchIntervalInBackground: false`, so a tab left open overnight stops polling.

§2.1 settles the transport: *"In-app delivery starts as a polled unread count, not a
socket. The SSE machinery in §4.2 is built for the lifetime of one answer; a per-user
notification stream is a different connection lifecycle with different failure modes,
and polling an integer is honest at this scale."* Nothing in this design touches
`app/rag/answerer.py`, the SSE contract, or `SSE_EVENT_MODELS`.

The popover lists the most recent few with a mark-read affordance and a "See all" link.
It uses `popover.tsx` and `scroll-area.tsx`, both already installed.

### 8.2 `/notifications`

Under `app/(app)/notifications/`, paginated with the existing `pagination.tsx`, filtered
by project, type and unread. Breadcrumb entries in `lib/nav.ts`.

The dropdown serves the glance; the page serves the person who was away for a week and
has forty.

### 8.3 `/settings/notifications`

A new child in `lib/settings-nav.ts`: one row per event type, an in-app switch and an
email switch. The email switches render **disabled**, with one line stating that email
delivery is not configured on this instance.

**This is the settings group's first non-admin child.** `/settings` is not a screen — a
group's index route redirects to its first *reachable* child — and until now every child
(`users`, `roles`, `audit`) was admin-only, so a non-admin never reached the group at
all. Adding a child everyone can reach changes what `/settings` resolves to for a
non-admin from "nothing" to this page. `lib/nav.test.ts` covers the filter and must gain
a case for it; this is the kind of thing that works in every developer's admin session
and is broken for everyone else.

### 8.4 The deep-link mapper

`lib/notifications.ts` maps `(type, projectId, targetId)` to a route:
`project.*` → `/projects/{id}`, `checklist_change_set.*` → `/checklist/{moduleId}`,
`mock_data_change_set.*` → `/checklist/{moduleId}` (the Mock Data tab, not a route of its
own), `membership.granted` → `/projects/{id}`. Both change-set families carry the module
id as `target_id`, per §3.4, so the mapper never has to resolve a dataset to its screen.

It gets its own Vitest file. This is the shape the suite already covers deliberately —
`lib/status.ts`, `lib/can.ts`, `lib/nav.ts` — the pure functions that fail *silently*
rather than loudly.

### 8.5 Design system

The only new shadcn component is **`switch`**, installed by CLI into `components/ui/`
per `docs/design.md`. Composition uses `render={<Component />}`, never `asChild`. No
`dark:` utility and no palette utility anywhere: the unread badge is `bg-primary
text-primary-foreground`, not a named colour.

### 9.1 Ownership and status codes

Ownership resolves through a new `resolve_notification_owner(user) -> user.id` in
`access.py`, beside `resolve_conversation_owner` — not a `user_id ==` filter in the
service. Same argument as conversations, same file, and it is the one body someone
changes if notifications ever become shareable.

**Every miss is `404 NOTIFICATION_NOT_FOUND`**, including a row that exists and belongs
to someone else. A `403` would confirm the row exists, which is `response-api.md`'s
`403`/`404` distinction running backwards.

`is_admin` gates nothing under this router. There is no administrative view of anyone's
notifications, and nothing here needs one: the *events* are already visible to an
administrator through `/audit-events` wherever the underlying action was audited.

One new `ErrorCode` member: `NOTIFICATION_NOT_FOUND`. Members are added, never renamed.

### 9.2 Query shape

`NotificationListQuery(ListQuery)` adds `unreadOnly`, `projectId` and `type` **on the
subclass**. Per `.claude/rules/rag.md`'s note on FastAPI's flattening, a scalar query
parameter beside a model stops the flattening and every request then fails with
`{"request": "Field required"}`, naming nothing that appears in the signature.

### 9.3 `mark-all-read` is bounded by the same filters

`POST /notifications/mark-all-read` marks the caller's unread, visible rows read. It
takes no filter and no ids: "mark all read" means all, and a filtered variant is a
second semantics for one route. It returns the count it marked.

## 10. A new rule file

`.claude/rules/notifications.md` — the fifteenth. Every invariant here fails **silently**
when broken, which is CLAUDE.md's own bar for a rule rather than a preference:

1. Recipients resolve through `resolve_notification_recipients` and nowhere else.
2. Fan-out runs **before** the commit; audit runs after. Both orderings are load-bearing.
3. `details` is in-app only. Phase 2.4's email composes from `event_type` and
   `target_id`.
4. Preferences **snapshot** onto the delivery row; they never gate its creation.
5. An administrator with no membership receives nothing, and adding a branch for
   symmetry with `require_permission` is the bug, not the fix.
6. Actor exclusion is per-event: exclude for actions, include for outcomes.
7. `membership.granted` goes through `raise_direct`, never through the permission map.

`CLAUDE.md`'s rule table and its count go from fourteen to fifteen in the same change.

## 13. Out of scope, recorded so it is not rediscovered

- **Email.** Phase 2.4, against this record. §1.
- **A socket or SSE stream for notifications.** §2.1 rules it out by name; §8.1.
- **Digests and batching.** A property of email.
- **An administrative view of another user's notifications.** Nothing needs one; §9.1.
- **Dismissing a notification.** Read state plus retention is the whole lifecycle. If it
  is wanted later it is a second nullable timestamp, not a `deleted_at`. §2.2.
- **Notifications for the ask route.** It is not audited for §2.5's reason and it has no
  asynchronous outcome to announce — the answer streams to the person who asked.
