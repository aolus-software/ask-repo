# Phase 2.1 — Per-project RBAC: Design

**Status:** Complete draft, pending review. No open questions (§16.1).
**Date:** 2026-09-13
**Issue:** [#18](https://github.com/aolus-software/ask-repo/issues/18)

## 0. What this document covers

`docs/PRD.md` §2.1 defines **Phase 2.1** as the first sub-phase of phase 2, and nothing else in
phase 2 moves until it lands. Phase 1 shares every project with every authenticated user, which
is correct for the team that stood the instance up (§4.1) and wrong for the audience phase 1.1
opened the tool to: a contractor evaluating AskRepo currently lists and queries every repository
on the instance.

The PRD names three deliverables — a membership table, roles per project (viewer / editor /
owner), and swapping the body of the access resolver §2 built for this. This document specifies
those, plus the four decisions issue #18 requires be made explicitly rather than discovered in
review: the role-to-permission model, the `403`/`404` table, what happens to a departed user's
projects, and what the migration does with projects whose creator is already deactivated.

**Nothing here adds infrastructure.** No new service and no new datastore — the four stay four.
Redis does gain a **second** reader: the grant cache in §2.1, alongside the login rate limiter.
That edits a fact `CLAUDE.md` states outright and is tracked as a doc change (§13), not slipped
in. What is unchanged is the part of that sentence that matters most: Redis still does not back
the job queue. Kafka does.

### 0.1 The one property everything else serves

`docs/PRD.md` §2 states the phase-2 readiness goal and §7 makes it testable: **read scoping
happens in exactly one function, confirmed by grep.** The whole codebase was built against that
promise. `app/core/access.py:45` is the function, and it returns `ProjectScope.all()` today.

This design keeps the promise and extends it. After this change `app/core/access.py` holds
**four** functions and remains the only file that interprets membership. A route, service, or
query that decides access on its own is a defect even when its output is currently correct
(`.claude/rules/router.md`).

## 1. The access core

Four functions, one file, one import site per caller.

```python
# app/core/access.py

resolve_project_scope(user)                        # exists — body swapped
resolve_conversation_owner(user)                   # exists — UNCHANGED, see §10.1
require_permission(user, project_id, permission)   # new
permissions_for(user, project_id)                  # new — for the UI
```

`resolve_project_scope` answers **which projects**. `require_permission` answers **what may I do
to this one**. They read the same preloaded snapshot (§2), so there is still exactly one place
membership is interpreted — the grep criterion holds over four functions in one file instead of
two.

### 1.1 `resolve_project_scope`

```python
def resolve_project_scope(user: AuthenticatedUser) -> ProjectScope:
    if user.is_admin:
        return ProjectScope.all()
    return ProjectScope.of(grant.project_id for grant in user.grants)
```

`ProjectScope` is unchanged and stays exactly as it is: an explicit two-state value rather than
`list[UUID] | None`, because a `None` sentinel meaning "unrestricted" is fail-open and any
accidental `None` would read as full access. An empty `ids` set means **no access**, not all of
it — which is now a state that occurs in production rather than only in tests.

Every existing call site is untouched. There are 15 of them across `project.py`,
`conversation.py`, `checklist_module.py`, `checklist_item.py`, `checklist_change_set.py`,
`mock_data_dataset.py`, `mock_data_change_set.py` and `indexed_path.py`, and this change adds
zero diff to any of them.

### 1.2 `require_permission`

```python
def require_permission(
    user: AuthenticatedUser, project_id: uuid.UUID, permission: Permission
) -> None:
```

**Synchronous, for the same reason `resolve_project_scope` is** (§2): the grants are
already in hand when it is called, so it performs no I/O. An `async def` here would be
a lie about the cost and would force `await` into six service call sites that do not
need one.

Raises, or returns `None`. The status code it raises is the §7 table:

- no grant for this project, and not an admin → `404 PROJECT_NOT_FOUND`
- a grant whose role lacks the permission → `403 INSUFFICIENT_ROLE`
- `user.is_admin` → returns, always (§4.3)

It replaces **six** hand-written gates that currently re-derive the same policy inline and are
each free to drift:

| Site                                     | Today                                                  |
| ---------------------------------------- | ------------------------------------------------------ |
| `app/services/project.py:286`            | `actor.is_admin or project.created_by == actor.id`     |
| `app/services/checklist_module.py:437`   | `module.created_by != actor.id and not actor.is_admin` |
| `app/services/checklist_item.py:131`     | same shape                                             |
| `app/services/checklist_item.py:175`     | same shape                                             |
| `app/services/mock_data_dataset.py:226`  | `record.created_by != actor.id and not actor.is_admin` |
| `app/api/routes/mock_data_records.py:39` | same policy, documented in the docstring               |

All six are deleted. Consolidating them is not a side benefit of this change — it is the reason
per-project roles are expressible at all. Adding a role dimension to six independent
comparisons means editing six sites and hoping.

### 1.3 `created_by` finally becomes what §7 says it is

`docs/PRD.md` §5.1's "Attribution vs authorization" restricts `created_by` to attribution and
destructive gating, and §4.1:365 says outright that it does not scope reads. After this change
it does **only** attribution: the destructive gating moves to `require_permission`, and the
column's one remaining job in the access model is seeding the first membership row at project
creation (§6.3). It never scoped reads and still does not.

## 2. Why the resolver stays synchronous, and where the data comes from

`resolve_project_scope` is `def`, not `async def`, and takes no session. A membership lookup
needs the database, so the issue's promise of a one-body change does not survive contact unless
the data is already in hand when the function is called.

**It is.** `AuthContextMiddleware` already loads the user row on **every** authenticated request
— `app/core/middleware.py:147`, and the docstring explains why: `docs/PRD.md:101` requires
deactivating someone to end their sessions immediately, and a stateless 15-minute token cannot
deliver that. Membership joins onto that query.

```python
@dataclass(frozen=True, slots=True)
class ProjectGrant:
    """One project this caller may reach, and what they may do to it."""

    project_id: uuid.UUID
    role: str                        # the role's name, for display
    permissions: frozenset[str]      # expanded at load time


@dataclass(frozen=True, slots=True)
class AuthenticatedUser:
    id: uuid.UUID
    name: str
    email: str
    is_admin: bool
    must_change_password: bool
    grants: Mapping[uuid.UUID, ProjectGrant] = field(
        default_factory=dict, compare=False, hash=False
    )
```

`grants` is a `MappingProxyType` so lookup by project id is O(1) rather than a scan of a set,
and `compare=False, hash=False` because the frozen dataclass generates `__hash__` and a mapping
is not hashable. Nothing hashes `AuthenticatedUser` today; the annotation stops that from
becoming a runtime error if something ever does.

Three consequences worth stating:

- **The snapshot is request-scoped.** Revoking access takes effect on the revoked user's _next_
  request. That is exactly the freshness contract deactivation already has, so it introduces no
  new class of staleness.
- **The rejected alternative was an async resolver taking a session.** Truthful about the I/O
  and always fresh, but it changes all 15 call sites and threads a session into repositories
  that currently take a plain `ProjectScope` value. "No route changes" would survive; "one
  function body" would not.
- **The other rejected alternative was a lazy request-scoped cache** populated by a dependency.
  It avoids the query on requests that never scope, at the cost of an implicit ordering
  requirement: a caller that resolves before the cache is warm silently gets the wrong answer,
  and the failure is an empty project list rather than an exception.

### 2.1 The grant snapshot is cached in Redis

The expansion in §2 is a three-table join (`project_memberships` → `roles` → `role_permissions`)
executed on **every authenticated request**, alongside the user row that already loads there.
It is cached in Redis.

This is a **second** use of Redis, and it changes a fact `CLAUDE.md` currently states outright —
"Redis is read by the login rate limiter (`app/core/rate_limit.py`) and by nothing else". That
sentence is edited in this change (§13). What does **not** change is the sentence above it:
Redis still does not back the job queue. Kafka does, and nothing here reopens that.

#### What is cached, and what deliberately is not

```
key    askrepo:perm:v1:{epoch}:user:{user_id}
value  JSON — the grants map: {project_id: {role, permissions[]}}
ttl    300s, as a backstop against a missed invalidation, not as the mechanism
```

**Only the grants are cached. The user row is not.** That separation is load-bearing:
`docs/PRD.md:101` requires deactivating someone to end their sessions immediately, and the
middleware reads the user row every request to deliver it (`app/core/middleware.py`). Caching
that row would trade a documented security property for a query the request is making anyway.
Deactivation stays immediate; only the grants ride the cache.

`v1` is a schema version in the key prefix. A deploy that changes `ProjectGrant`'s shape bumps
it, so a rolling restart can never parse an old value into a new struct.

#### Invalidation

Two triggers, deliberately handled by two different mechanisms because they have different
blast radii.

**One user's membership changed** — granted, revoked, or role swapped. `DEL` that user's key.
Exact, O(1), and the only user affected is the one whose row changed.

**A role's permission set changed** — or a role was deleted. This affects *every user holding
that role on any project*, which is not knowable from the write itself without a reverse lookup.
Rather than enumerating and deleting N keys, the design bumps a global epoch:

```
INCR askrepo:perm:epoch      →  every existing key is now unreachable
```

Because the epoch is part of the key, one `INCR` invalidates the entire cache atomically, with
no enumeration, no partial failure, and no possibility of missing a user. The old keys are
orphaned and expire on their own TTL. Role edits are rare, admin-initiated, and instance-wide by
nature, so throwing the whole cache away is the proportionate response — and it is strictly more
correct than a reverse-lookup sweep that can fail halfway.

The epoch is read once per request from the same round trip as the grant fetch (a pipelined
`GET epoch` + `GET key`), so this costs one Redis call, not two.

| Write | Invalidation |
| --- | --- |
| `POST /projects/{id}/members` | `DEL` the granted user's key |
| `PATCH /projects/{id}/members/{userId}` | `DEL` that user's key |
| `DELETE /projects/{id}/members/{userId}` | `DEL` that user's key |
| `POST /projects` (creator gets owner) | `DEL` the creator's key |
| `PATCH /roles/{id}` | `INCR` epoch |
| `DELETE /roles/{id}` | `INCR` epoch |
| `restore-system-roles` (CLI) | `INCR` epoch |
| User deactivated | nothing — the user row is uncached, so the request fails on identity |
| Project soft-deleted | nothing — scoped queries already filter `deleted_at IS NULL`, so a stale grant naming a deleted project matches no rows |

**Invalidation happens after the transaction commits, never inside it.** A `DEL` issued before a
commit that then rolls back evicts a correct entry and repopulates it from the same database
state — harmless. The reverse order is not: evicting before the write lands can repopulate the
cache with the *pre-write* value and then leave it there for the full TTL. Commit, then evict.

#### The failure policy, and why it is not the footgun it looks like

**A Redis error falls back to the database query.** Not to "deny", and not to "allow" — to the
source of truth, which is the same query the uncached design would have run. Redis being down
makes AskRepo slower, not more permissive and not broken.

This is worth stating explicitly because `app/core/rate_limit.py:8` fails **open** on purpose
(D18): a Redis outage on a single-VPS box is one the operator is already fixing, and refusing
every login meanwhile turns a degraded control into an outage. Two Redis clients with different
failure behaviour is a genuine hazard for whoever reads them next, so the difference is named
rather than left to be inferred:

| Client | On Redis error | Why |
| --- | --- | --- |
| `rate_limit.py` | **skip the check** — the request proceeds | The check is the only thing Redis holds. Failing closed denies every login |
| the grant cache | **query Postgres instead** | Redis holds a copy, not the truth. Falling back is free correctness |

Both degrade rather than fail, but only one of them degrades by skipping a control. A permission
cache must never do that, and it never has to, because the authoritative answer is one join away.

`GET /health` reports Redis reachability so a silent permanent fallback — correct, and quietly
several times slower — is visible rather than discovered under load.

#### What the cache buys

Beyond the join itself: **it is what makes `--workers > 1` viable.** The API runs single-process
today (`infra/backend.prod.Dockerfile:68`), and an in-process cache would have had to be torn out
the first time that changed. A Redis-backed one is already correct across processes, and the
epoch makes cross-process invalidation of role edits a single integer rather than a
pub/sub fan-out.

### 2.2 The known bound

`ProjectScope.of(ids)` renders as a SQL `IN` clause. A user granted 500 projects produces 500
UUIDs in every scoped query. That is fine at the scale this instance is specified for (§5:
single-tenant, one organization, one box), and the escape hatch if it ever is not is to switch
`ProjectScope` to carry a subquery rather than a materialized set — a change inside
`app/repositories/`, still not at any call site. Recorded here so the next person does not have
to rediscover it.

## 3. Data model

Four tables' worth of concepts, three of them actual tables. Every one carries `TimestampMixin`
and `SoftDeleteMixin` like every other table in the schema (`docs/data.md`).

### 3.1 `Permission` — a code enum, not a table

```python
class Permission(StrEnum):
    """Source of truth for which permissions EXIST.

    `role_permissions` rows reference these values; they do not define them. See
    §3.2 for why existence is anchored in code.
    """

    PROJECT_READ      = "project.read"
    PROJECT_UPDATE    = "project.update"
    PROJECT_DELETE    = "project.delete"
    PROJECT_REINDEX   = "project.reindex"

    QUESTION_ASK      = "question.ask"

    CHECKLIST_READ    = "checklist.read"
    MODULE_CREATE     = "module.create"
    MODULE_EDIT       = "module.edit"
    MODULE_DELETE     = "module.delete"
    GENERATE_RUN      = "generate.run"
    CHANGESET_APPLY   = "changeset.apply"
    ITEM_EDIT         = "item.edit"
    RESULT_RECORD     = "result.record"

    MOCKDATA_READ     = "mockdata.read"
    MOCKDATA_EDIT     = "mockdata.edit"

    MEMBERSHIP_READ   = "membership.read"
    MEMBERSHIP_GRANT  = "membership.grant"
    MEMBERSHIP_REVOKE = "membership.revoke"
```

**There is no conversation permission, and its absence is load-bearing.** See §10.1.

### 3.2 `roles`

```python
class Role(Base, TimestampMixin, SoftDeleteMixin):
    """A named bundle of permissions. Defined instance-wide; assigned per project."""

    __tablename__ = "roles"

    id:          Mapped[uuid.UUID]   # PgUUID, pk, default uuid4
    name:        Mapped[str]         # String(64), not null
    description: Mapped[str | None]  # String(255)
    is_system:   Mapped[bool]        # Boolean, not null, server_default false

    __table_args__ = (
        Index("uq_roles_name", "name", unique=True,
              postgresql_where=text("deleted_at IS NULL")),
    )
```

Roles are instance-wide definitions. The _assignment_ is what carries the project (§3.4) —
the same separation Spatie's teams feature makes, so a "QA Lead" role defined once can be
granted on twelve projects without twelve role rows.

### 3.3 `role_permissions`

```python
class RolePermission(Base, TimestampMixin, SoftDeleteMixin):
    __tablename__ = "role_permissions"

    id:         Mapped[uuid.UUID]
    role_id:    Mapped[uuid.UUID]   # FK roles.id, not null
    permission: Mapped[str]         # String(64), not null — a Permission value

    __table_args__ = (
        Index("uq_role_permissions_role_id", "role_id", "permission", unique=True,
              postgresql_where=text("deleted_at IS NULL")),
    )
```

**`permission` is a validated string, not a foreign key to a `permissions` table.** This is the
one place this design departs from Spatie's schema on a correctness argument rather than a
simplicity one, and the reason matters:

A check site reads `require_permission(actor, project.id, Permission.PROJECT_DELETE)`. If
existence lived in a `permissions` table, deleting that row would make every such check ask for
something that does not exist. The fail-safe answer is to deny — which means one `DELETE` from
an admin UI can brick project deletion for everyone on the instance, including the admin who
did it, recoverable only by SQL. Anchoring existence in the enum makes that state
unrepresentable. The table's only job is answering "which roles hold it", never "does it
exist".

Writes validate against the enum and refuse an unknown value with `422`. A row whose permission
is no longer in the enum (a permission removed by a future release) is ignored at expansion
time and logged once at startup — it cannot grant anything, because nothing asks for it.

### 3.4 `project_memberships`

```python
class ProjectMembership(Base, TimestampMixin, SoftDeleteMixin):
    """Who may reach a project, and as what.

    Spatie's `model_has_roles` with its team scope, minus the polymorphism: only
    users hold roles here, so `model_type` would be the constant 'users' in every
    row.
    """

    __tablename__ = "project_memberships"

    id:         Mapped[uuid.UUID]
    user_id:    Mapped[uuid.UUID]          # FK users.id, not null
    project_id: Mapped[uuid.UUID]          # FK projects.id, not null
    role_id:    Mapped[uuid.UUID]          # FK roles.id, not null
    granted_by: Mapped[uuid.UUID | None]   # FK users.id — NULL for backfilled rows

    __table_args__ = (
        Index("uq_project_memberships_user_id", "user_id", "project_id", unique=True,
              postgresql_where=text("deleted_at IS NULL")),
        Index("ix_project_memberships_user_id", "user_id",
              postgresql_where=text("deleted_at IS NULL")),
        Index("ix_project_memberships_project_id", "project_id",
              postgresql_where=text("deleted_at IS NULL")),
    )
```

**Every unique index is partial on `deleted_at IS NULL`.** Soft delete means a revoked
membership stays as a row; without the `WHERE`, re-granting access to someone you previously
revoked collides on a row nobody can see, and the error names a constraint the admin cannot
observe.

`ix_project_memberships_user_id` is the middleware's hot path — it is read on every
authenticated request, so it is the one index whose absence would be felt immediately.

**No `model_has_permissions`.** Spatie's direct per-user grant is a second grant path every
check must consult, and it is the feature that makes "why can this person do that?"
unanswerable without reading two tables and knowing which wins. Custom roles cover the same
need: you define a role rather than special-casing a person. If a direct-grant requirement
appears later it is an additive change to `permissions_for`, not a schema this one has to
anticipate.

### 3.5 One user, one role, per project

The partial unique on `(user_id, project_id)` means a user holds exactly one role on a project,
not a set of them. This is deliberate: multiple simultaneous roles make the effective
permission set a union that no single row explains, which is the same "why can this person do
that?" problem as direct grants. Granting a broader role replaces the row rather than adding
one.

## 4. Roles, permissions, and admin

### 4.1 The three system roles

Seeded by migration with `is_system=true`:

| Permission          | viewer | editor | owner |
| ------------------- | :----: | :----: | :---: |
| `project.read`      |   ●    |   ●    |   ●   |
| `question.ask`      |   ●    |   ●    |   ●   |
| `checklist.read`    |   ●    |   ●    |   ●   |
| `mockdata.read`     |   ●    |   ●    |   ●   |
| `membership.read`   |   ●    |   ●    |   ●   |
| `result.record`     |   ●    |   ●    |   ●   |
| `module.create`     |        |   ●    |   ●   |
| `module.edit`       |        |   ●    |   ●   |
| `module.delete`     |        |   ●    |   ●   |
| `generate.run`      |        |   ●    |   ●   |
| `changeset.apply`   |        |   ●    |   ●   |
| `item.edit`         |        |   ●    |   ●   |
| `mockdata.edit`     |        |   ●    |   ●   |
| `project.update`    |        |        |   ●   |
| `project.delete`    |        |        |   ●   |
| `project.reindex`   |        |        |   ●   |
| `membership.grant`  |        |        |   ●   |
| `membership.revoke` |        |        |   ●   |

**Why a viewer may ask questions.** Asking writes only a private conversation row and is the
tool's entire purpose; a viewer who cannot ask is a viewer of a list. Everything `editor` adds
writes something the whole team reads — the checklist is a document several people are relied
on to test against (`docs/PRD.md` §4.3), so authoring it is the privileged act, not querying.

**Why `result.record` sits with viewer, and `item.edit` does not.** This is the asymmetry
`docs/PRD.md` §4.3:511 decided and argued, carried forward verbatim:

> **Editing a test is gated; recording a result is not.** … Recording `current_result` and
> `status` is open to every authenticated user — otherwise the cheapest way to make a failing
> test pass is to edit the expectation.

Post-RBAC the phrase "every authenticated user" no longer names a group that can reach the
project, so it translates to **every member**. A viewer is therefore a tester: they execute a
plan and record what they observed, but cannot change what the plan says. Splitting the pair the
other way would recreate exactly the incentive §4.3 wrote the decision to remove — a tester who
cannot record a `fail` reaches for the expectation instead, and the gated operation is the one
that corrupts the document.

The PRD line is amended in this change to say "every member of the project" (§13); the decision
and its reasoning are untouched.

An earlier draft of this spec placed `result.record` with `editor`, on the argument that a
recorded `pass` survives regeneration (`CLAUDE.md`, "The checklist is a diff, not a list") and is
therefore durable shared state. That is true and it is not sufficient: durability is why the
column matters, not a reason to narrow who may write it, and the PRD had already weighed the
trade in the opposite direction. Recorded here because the wrong answer is the intuitive one.

### 4.2 System roles are frozen

`is_system` roles cannot be renamed, deleted, or have their permission set edited. The API
refuses with `403 SYSTEM_ROLE_IMMUTABLE`. Custom roles are fully editable.

This is what makes the role table safe to expose. The failure mode it closes is concrete: an
admin unchecks `membership.grant` on `owner`, and now nobody on the instance can grant
membership on any project, including to fix it. Immutability makes that unrepresentable rather
than recoverable.

`python -m app.cli restore-system-roles` ships alongside, beside the existing `seed-admins`
(`app/cli.py:87`). Immutability covers the system roles; the CLI covers what it cannot — a
custom role that locked someone out, a partial restore, direct SQL against the box.

### 4.3 Admin bypasses every _project_ permission, and that is safe

`require_permission` returns immediately for `user.is_admin`, and `resolve_project_scope`
returns `ProjectScope.all()`. An administrator reads and administers every project on the
instance.

That is not the blanket `Gate::before` bypass Spatie offers, because the catalogue it applies
to contains no conversation permission (§3.1, §10.1). The bypass is total over a deliberately
bounded set. This is stronger than an allowlist: an allowlist has to be remembered when a
permission is added, whereas here the thing that would break conversation privacy cannot be
granted because it does not exist.

`tests/test_access.py` asserts the catalogue contains no permission whose value begins with
`conversation.`, so the guard fails CI rather than review.

## 5. Status codes

The table issue #18 requires be decided before coding and reproduced in the PR description:

| Caller            | `GET /projects/{id}`    | `DELETE /projects/{id}` | `POST .../messages` |
| ----------------- | ----------------------- | ----------------------- | ------------------- |
| id does not exist | `404 PROJECT_NOT_FOUND` | `404 PROJECT_NOT_FOUND` | `404`               |
| no membership     | `404 PROJECT_NOT_FOUND` | `404 PROJECT_NOT_FOUND` | `404`               |
| viewer            | `200`                   | `403 INSUFFICIENT_ROLE` | `200`               |
| editor            | `200`                   | `403 INSUFFICIENT_ROLE` | `200`               |
| owner             | `200`                   | `204`                   | `200`               |
| admin             | `200`                   | `204`                   | `200`               |

**This is a wire-contract change and belongs in `CHANGELOG.md` as one.** Today a forbidden
delete returns `403 NOT_PROJECT_OWNER` and project existence is deliberately public. Once
membership scopes reads, "you may not see this" and "this does not exist" are the same answer,
and a `403` to a non-member confirms a repository exists — repository names are inventory of
the organization's private codebases, which is the same reasoning `docs/PRD.md` §9 applies to
egress.

The `403` survives for the case that is genuinely not about existence: **a member whose role is
too low.** They can already see the project in their own list, so answering `404` would
contradict what the UI just rendered and generate bug reports about projects visibly on screen.
This is `.claude/rules/response-api.md`'s rule applied to the new access model, not a new rule:
`403` when the caller may see the resource but not do this to it, `404` when they should not
learn it exists.

`NOT_PROJECT_OWNER` is **not** removed — `ErrorCode` values are a wire contract and members are
added, never renamed (`CLAUDE.md`). It stops being raised by the project routes; whether it
remains in use elsewhere is settled during implementation, and if nothing raises it the member
stays with a comment saying so.

## 6. The migration

One Alembic revision, three steps, in order.

### 6.1 Create the tables

`roles`, `role_permissions`, `project_memberships`, with the partial indexes in §3. Nothing
else in the schema changes — `users.is_admin` stays, `projects.created_by` stays.

### 6.2 Seed the system roles

`viewer`, `editor`, `owner` with `is_system=true` and the §4.1 matrix. The seed data lives in a
module the migration imports and `restore-system-roles` reuses, so the two cannot disagree.

### 6.3 Backfill one owner per project

For every project with `deleted_at IS NULL`: one `project_memberships` row with
`role_id = owner`, `user_id = created_by`, `granted_by = NULL`, and `created_at` copied from the
project so the row is not retroactively dated today.

Soft-deleted projects are skipped. They are unreachable already, and seeding them would
resurrect membership for something nobody can list.

`granted_by` is NULL rather than pointing at some admin because nobody granted these — they are
derived. Phase 2.2's audit trail will read this column first, and a fabricated granter is a lie
recorded as fact in the one table whose whole purpose is being trustworthy.

### 6.4 What the backfill deliberately does not do

`docs/PRD.md` §3 says shared assets survive a soft-deleted user, so `created_by` may already
point at a deactivated account. Those projects get an owner membership for a user who cannot log
in — a project with an owner row and no _reachable_ owner.

**The migration does not fabricate a replacement.** It seeds `created_by` unconditionally,
preserving attribution. The alternatives were both worse: auto-granting an arbitrary admin
writes a grant nobody made (and picking _which_ admin has no principled answer when there are
four), and refusing to migrate is not an option a migration has.

The consequence is stated plainly rather than hidden: **§9's invariant is enforced going
forward, not retroactively.** A deactivation that already happened cannot be blocked now. Those
projects remain fully operable — admins bypass every project permission (§4.3) — and
`GET /projects?ownerless=true` lists them so an operator can clean up deliberately.

## 7. API surface

All new routes follow `.claude/rules/router.md` and `.claude/rules/response-api.md`: one service
call per route, `camelCase` on the wire via `ApiModel`, `snake_case` inside.

### 7.1 Roles — admin only

```
GET    /roles                     list roles, system first
POST   /roles                     create a custom role
GET    /roles/{id}                one role with its permissions
PATCH  /roles/{id}                rename / re-permission — 403 if is_system
DELETE /roles/{id}                soft delete — 403 if is_system, 409 if assigned
GET    /permissions               the Permission catalogue, grouped, for the editor UI
```

`DELETE /roles/{id}` refuses with `409 ROLE_IN_USE` when live memberships reference it, rather
than cascading. Silently revoking a dozen people's access as a side effect of tidying a role
list is not a thing an admin should be able to do without seeing it first; the error names the
projects.

### 7.2 Membership — scoped to a project

```
GET    /projects/{id}/members             MEMBERSHIP_READ
POST   /projects/{id}/members             MEMBERSHIP_GRANT
PATCH  /projects/{id}/members/{userId}    MEMBERSHIP_GRANT — change role
DELETE /projects/{id}/members/{userId}    MEMBERSHIP_REVOKE — 409 if last live owner
```

Every one resolves through `require_permission`, so the §5 table applies unchanged: a non-member
probing `GET /projects/{id}/members` gets `404`, not `403`.

### 7.3 Changed behaviour on existing routes

```
POST   /projects              unchanged; creator now also gets an owner membership
DELETE /users/{id}            now 409 LAST_OWNER when it would strand a project
GET    /projects             list is now membership-scoped (admins still see all)
GET    /projects?ownerless=true   admin only; the §6.4 cleanup list
```

`ProjectResponse` gains two fields: `role` (the caller's role name, `null` for an admin with no
membership) and `permissions` (the caller's effective set). The frontend uses them to hide
actions; the server refuses regardless, so hiding is cosmetic.

### 7.4 New `ErrorCode` members

Added, never renaming an existing member (`CLAUDE.md`):

```
INSUFFICIENT_ROLE
SYSTEM_ROLE_IMMUTABLE
ROLE_NOT_FOUND
ROLE_IN_USE
ROLE_NAME_EXISTS
LAST_OWNER
MEMBERSHIP_NOT_FOUND
MEMBERSHIP_EXISTS
```

`LAST_OWNER` mirrors the existing `LAST_ADMIN` (`app/core/errors.py:39`), which guards the same
class of mistake — an operation that would leave the instance with no way to recover except
manual SQL — and whose implementation in `UserRepository.count_active_admins` is the shape
`count_active_owners` follows.

## 8. Project creation

**Unchanged: every authenticated user may add a project**, and the creator receives an `owner`
membership in the same transaction as the project row.

Restricting who may add a repository is an instance-level permission question. Issue #18 does
not ask for one, `docs/PRD.md` §2.1 does not name one, and pulling it in would widen the
sub-phase that everything else in phase 2 is waiting on. If it is wanted it is additive later
and touches nothing here.

The membership write shares the project's transaction. A project that exists with no owner is
the §9 invariant broken at birth, and a second transaction is a window where exactly that is
true.

## 9. Deactivation and the last-owner guard

**Invariant: every live project has at least one live owner.**

`DELETE /users/{id}` refuses with `409 LAST_OWNER` when deactivating the user would leave any
project without a live owner. The response body names the projects, so the admin knows what to
transfer rather than being told "no".

```
DELETE /users/{id}
→ 409 { "detail": { "code": "LAST_OWNER",
                    "message": "…",
                    "projects": [{ "id": "…", "name": "payments-api" }] } }
```

`DELETE /projects/{id}/members/{userId}` refuses the same way when revoking would remove the
last live owner. Both read one repository method, `count_live_owners(project_id, excluding=…)`,
modelled on `UserRepository.count_active_admins` (`app/repositories/user.py:60`).

"Live owner" means a membership whose role is `owner`, `deleted_at IS NULL`, whose user is also
`deleted_at IS NULL`. A deactivated user's memberships are **not** soft-deleted by deactivation
— they are left intact, so reactivating an account restores exactly the access it had. The
liveness check reads through to the user row instead.

**This answers `docs/PRD.md` §8's open question** (`docs/PRD.md:821`) — _"What happens to a departed user's
projects? (Owned by Phase 2.1.)"_ — as: destructive rights do not fall to admins by default,
because offboarding cannot complete until a human names the successor. The PRD entry moves from
open to decided in this change.

The honest limit, restated from §6.4: this guard prevents new strandings and cannot repair old
ones.

## 10. What does not change

### 10.1 Conversations, and why the catalogue has no conversation permission

`resolve_conversation_owner` (`app/core/access.py:57`) is **not touched**. Conversations stay
scoped to their owner, with no admin bypass, on all four routes, `404` on every miss.

`docs/PRD.md` §4.2 states conversation privacy without qualification, and
`.claude/rules/rag.md` says `is_admin` is not consulted anywhere under `/conversations`. An
administrator who could read a colleague's conversation makes that sentence false.

**The enforcement is structural, not remembered.** §4.3 lets an admin bypass every permission in
the catalogue — which is safe precisely because the catalogue contains no `conversation.*`
member. There is nothing to bypass into. Adding one would be the change that breaks §4.2, and
`tests/test_access.py` fails if anyone does.

A member may ask questions about a project (`question.ask`); the resulting conversation is
theirs alone, and losing membership later stops new questions without exposing old
conversations to anyone.

### 10.2 Everything downstream of the resolver

Kafka, the lease, Qdrant collections, soft-delete-vs-Qdrant, the SSE contract, the change-set
apply path, the reindex generation swap — none of it changes. The worker has no actor and does
no authorization; ingestion, checklist generation and mock-data generation are unaffected.

Qdrant is worth stating explicitly because it looks like it should be involved: vector points
carry `project_id` and `generation`, and retrieval filters on both (`.claude/rules/rag.md`).
Membership is **not** a third filter. Retrieval is only ever reached for a project the caller
already resolved through the access core, which is the same reason a Cypher query in phase 3
must not scope itself (`docs/PRD.md` §2.1). A second enforcement point is the outcome this
sub-phase exists to prevent, including one in the vector store.

## 11. Frontend

Custom roles are an authoring surface, not a toggle, so this is a real slice of work rather than
a checkbox on an existing screen. Three new routes, one rewritten helper, and a pass over every
screen that currently renders a destructive action.

Everything below follows `.claude/rules/design-system.md` (semantic tokens only — no `dark:`
utilities, no palette utilities), `.claude/rules/forms.md`, `.claude/rules/navigation.md`, and
`.claude/rules/frontend-bff.md`. Components are shadcn on the Base UI base, composed with
`render={<Component />}`, never `asChild`.

### 11.1 `lib/can.ts` is rewritten, and it is the only place that decides

`frontend/lib/can.ts` today is a single function mirroring the backend's `created_by` gate:

```ts
export function canManageProject(user, project) {
  return user.isAdmin || project.createdBy === user.id;
}
```

That is the frontend's counterpart to the six inline gates §1.2 deletes, and it goes the same
way. It is replaced by a permission check reading the `permissions` array the API now returns on
`ProjectResponse` (§7.3):

```ts
export function can(project: { permissions: string[] }, permission: Permission): boolean {
  return project.permissions.includes(permission);
}
```

The client never recomputes a role's permissions from a role name, and never holds a copy of the
matrix. The server sends the caller's effective set per project; the client asks whether a string
is in it. **This mirrors §0.1's property on the frontend**: one place decides, and when roles
become editable at runtime the client needs no release to keep up — which is the whole point of
custom roles and would be defeated by a hardcoded mirror.

`lib/can.test.ts` is rewritten alongside. The header comment stays true and stays: this decides
what to *show*. A `403` still surfaces as an error, because hiding a button is not a control.

### 11.2 `/settings/roles` — the role list

New route under the existing Settings group. The nav entry is added to `lib/settings-nav.ts`
(`adminOnly: true`), which is the only place a destination may be declared —
`.claude/rules/navigation.md` §1, "never hardcode a nav label or href in a component". Today that
file holds one child; it will hold two.

`RoleTable` (`components/roles/role-table.tsx`), following `components/users/user-table.tsx`:

| Column | Notes |
| --- | --- |
| Name | `RoleBadge` marks system roles with a lock, mirroring `user-role-badge.tsx` |
| Description | Muted, truncated |
| Permissions | A count, e.g. "13 of 19" |
| Members | How many live memberships reference it — this is what a `409 ROLE_IN_USE` will be about, so it should be visible before the attempt |
| Actions | `RoleRowActions`, following `user-row-actions.tsx` |

System roles sort first and their row actions offer only **View** — no Edit, no Delete. A menu
item that opens a dialog which then refuses is worse than an absent menu item.

**Create is a `FormDialog`** — name and description, two inputs, which `.claude/rules/forms.md`
§1 puts in a dialog. On success it routes to the matrix page, because a role with no permissions
does nothing and the next step should not have to be found.

### 11.3 `/settings/roles/[id]` — the permission matrix

**A `FormPage`, not a dialog, and the rule decides this rather than taste.**
`.claude/rules/forms.md` §1: "5+ inputs, OR any checkbox picker, OR a repeatable/unbounded list"
→ `FormPage` on its own route, and "a checkbox picker counts as 'many' on its own, whatever the
field count, because it has no fixed height". Nineteen permissions is emphatically that.

The matrix groups by resource prefix, which is what the `Permission` values were named for
(§3.1):

```
Project        project.read  project.update  project.delete  project.reindex
Questions      question.ask
Checklist      checklist.read  module.create  module.edit  module.delete
               generate.run  changeset.apply  item.edit  result.record
Mock data      mockdata.read  mockdata.edit
Membership     membership.read  membership.grant  membership.revoke
```

Groups come from `GET /permissions`, which returns the catalogue grouped and labelled. The client
does not derive group names by splitting on `.` — a display label is a server concern here,
because the catalogue is the server's enum and a client-side split would need its own copy of the
human-readable names.

For a **system role** the page renders read-only: checkboxes disabled, a `lock` affordance and one
line of explanation ("viewer, editor and owner are built in and cannot be changed"), and no submit
row. Rendering an editable form that returns `403 SYSTEM_ROLE_IMMUTABLE` on submit is the failure
`.claude/rules/response-api.md` calls doing the check backwards — the UI knows before the user
types.

Saving a matrix is the write that bumps the cache epoch (§2.1), so the page states plainly that
the change applies to everyone holding the role.

### 11.4 `/projects/[id]` — Members

`app/(app)/projects/[id]/project-detail-screen.tsx` has **no tabs today** — `Tabs` currently
appears in exactly one screen, `app/(app)/checklist/[moduleId]/module-screen.tsx`. Members
therefore arrives as a `Tabs` pair (Overview / Members) on the project detail screen, following
that screen's precedent.

Worth being explicit about why this is not `.claude/rules/navigation.md` §3's "sub-navigation is a
collapsible sidebar group, not in-page tabs": that rule governs **nav destinations with
children** — things declared in `lib/nav.ts` and rendered by the sidebar. A detail view of one
resource showing two facets of that resource is what the module screen already does, and it is not
a nav group. If review disagrees, the fallback is `/projects/[id]/members` as a real route, which
costs a breadcrumb entry and nothing else.

- Tab visible with `membership.read`, so every member sees who else has access.
- `MemberTable`: user, role (a `Select` for someone with `membership.grant`, plain text
  otherwise), granted by, granted at.
- **Add member** is a `FormDialog`: a user `Combobox` and a role `Select`. Two inputs.
  `components/ui/combobox.tsx` already exists.
- Revoking is a `ConfirmDialog` — a destructive confirmation with no inputs, per `forms.md` §1.
- The last-owner refusal (§9) renders inline on the table row, naming the constraint rather than
  showing a generic error toast.

### 11.5 `/settings/users` — the last-owner refusal

`DELETE /users/{id}` can now return `409 LAST_OWNER` with a `projects` array. The existing
`user-row-actions.tsx` confirmation surfaces it as a list of blocking projects, each linking to
that project's Members tab, so the fix is one click from the refusal rather than a hunt.

This is the one place a backend error shapes a screen's layout rather than a toast, and the reason
is that "no" is not actionable here — "no, because these three projects would have no owner" is.

## 12. Testing

The suite has to cover the things that fail silently, which for access control is most of it.

- **`tests/test_access.py`** — the matrix, exhaustively: every role × every permission. The
  catalogue holds no `conversation.*` member. `ProjectScope.of([])` denies rather than allows.
  Admin bypass reaches every project permission and no conversation route.
- **`tests/test_membership_repository.py`** — partial-unique behaviour across a
  revoke-then-regrant cycle; `count_live_owners` ignoring memberships whose user row is
  soft-deleted.
- **`tests/test_project_access.py`** — the §5 status table, row by row, as request tests.
- **A grep test.** `docs/PRD.md` §7's criterion is "confirmed by grep", so it is a test rather
  than a habit: no file outside `app/core/access.py` references `project_memberships` or
  compares `created_by` to an actor id.
- **Migration test** — a project whose creator is deactivated is backfilled, is reachable by an
  admin, and appears in the ownerless list.
- **`tests/test_grant_cache.py`** — the §2.1 invalidation table, and the three properties that
  fail silently rather than loudly:
  - **A revoke is visible on the next request.** Grant, read (populating the cache), revoke, read
    again — the second read must not serve the cached grant. This is the test that would catch a
    missing `DEL`, and without it the failure is someone retaining access after being removed.
  - **A role edit invalidates every holder**, not just the editor. Two users on the same role, one
    `PATCH /roles/{id}`, both see the new set.
  - **Redis down falls back to Postgres and still answers correctly** — not deny, not allow. The
    same access assertions run with the cache client raising on every call.
  - Eviction happens **after** commit: a write that rolls back leaves the cache consistent with
    the database.
- **Frontend (vitest)** — §11.7.

- **Instance-level permissions.** `is_admin` stays a boolean. Restricting who may create a
  project, or who may see `/settings/users`, is a separate question (§8).
- **Direct per-user permission grants** (Spatie's `model_has_permissions`). §3.4.
- **Multiple roles per user per project.** §3.5.
- **Role assignment on anything but projects.** No role on a checklist module, a dataset, or a

## 15. Build order

Each step leaves the suite green.

1. **`Permission`, the role matrix, and the seed module.** Pure code, fully unit-testable, no
   schema. Includes the no-`conversation.*` test.
2. **Models and the migration**, with the backfill. Verified against a database that has
   projects, including one whose creator is deactivated.
3. **`AuthenticatedUser.grants` and the middleware join.** No behaviour change yet —
   `resolve_project_scope` still returns `all()`. The snapshot is populated and asserted before
   anything reads it.
4. **Swap `resolve_project_scope`'s body, add `require_permission` and `permissions_for`.** This
   is the step where access actually narrows; the grep test lands with it.
5. **Replace the six inline gates** (§1.2) with `require_permission`. One service at a time.
6. **The `403`/`404` change**, with the §5 table as request tests.
7. **Membership routes**, then the last-owner guard on `DELETE /users/{id}`.
8. **Role routes**, plus `restore-system-roles` in the CLI.
9. **The grant cache** (§2.1) — read-through, then the invalidation table, then the fallback path.
   Deliberately after steps 3–8 rather than with them: every access assertion in the suite is
   already green against Postgres, so a cache bug shows up as a test that passes uncached and
   fails cached, which localises it immediately. Building the cache and the policy together
   makes an invalidation bug look like a policy bug.
10. **Frontend**, in dependency order: `lib/can.ts` and the `permissions` field it reads (§11.1),
    then the Members tab (§11.4), then `/settings/roles` and the matrix page (§11.2–11.3), then
    the pass over existing screens (§11.6). Role management last of the three surfaces because it
    is the only one that is useless before membership exists.
11. **Docs** (§13), in the same PR.

Steps 1–3 are additive and independently reviewable. Step 4 is the one that changes what users
can see, and it is deliberately small enough to read in one sitting. Step 9 changes no behaviour
at all if it is correct, which is exactly why it is sequenced where a regression is easy to
attribute.

## 16. Resolved: `result.record` sits with `viewer`

**Resolved in favour of the PRD.** `result.record` is a `viewer` permission (§4.1), and
`item.edit` stays with `editor`.

An earlier draft placed both with `editor`. That contradicted `docs/PRD.md` §4.3:511 — a Decision
the PRD argued rather than assumed — and the PRD outranks this spec (`CLAUDE.md`). The
contradiction was between the draft and the source of truth, not between a request and the source
of truth, so resolving it toward the PRD corrects the spec rather than overriding anyone: amending
§4.3 instead would have been the change needing an explicit decision.

The reasoning now lives in §4.1 beside the matrix, where someone reading the roles will actually
encounter it. This section is kept rather than deleted because the wrong answer is the intuitive
one, and the next person to look at the matrix will have the same thought.

**What still moves in `docs/PRD.md`:** §4.3:511's phrase "open to every authenticated user"
becomes "open to every member of the project". The decision and its justification are untouched —
only the group name changes, because post-RBAC "every authenticated user" no longer describes a
group that can reach the project at all (§13).
