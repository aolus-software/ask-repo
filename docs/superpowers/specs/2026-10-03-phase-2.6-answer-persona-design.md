# Phase 2.6 — A per-user answer style (the "persona"): Design

**Date:** 2026-10-03
**Intent:** `docs/PRD.md` §2.1 Phase 2.6, second bullet; GitHub issue #22
**Depends on:** M3's answer graph, the profile page, Phase 2.2 audit trail
**Milestone placement:** `docs/PRD.md` §6 item 11
**Sibling:** the synthetic Q&A eval harness (issue #21) is specified separately, *after* this
document, and builds on the slot defined here (§6)

---

## 0. What this document covers

Phase 2.6 couples two items: an eval harness and a per-user persona. They are specified as two
documents. This one comes first because it fixes the shape of the prompt slot, so the harness
spec can say exactly what "personas off" means instead of describing a slot that does not
exist yet.

A user sets three preferences once — **how much detail**, **how familiar they are with the
repository**, and **prose or bullets** — and every answer Dev Knowledge gives *them* is shaped
accordingly. Nothing else changes.

What is **not** in scope: free-text instructions; an instance-wide default set by an
administrator; any effect on the QA Checklist or Mock Data (generation or refinement chat);
recording the persona on a feedback vote or a call record.

### 0.1 The decisions, made

1. **Structured only, no free text.** The persona is three enum dials. Every sentence that can
   reach the prompt is written by the project and fixed in `app/rag/prompts.py`. That makes
   "prompt injection by preference" impossible rather than mitigated. It is the "safe half" in
   PRD §2.1, and free text stays a separate decision nobody has made. **This amends PRD §2.1**:
   storage is three enum columns, not one text column, and the server-enforced character cap
   the PRD describes has nothing to cap.
2. **Three dials: detail, familiarity, format.** A fourth, code quoting, was considered and
   dropped. `ANSWER_SYSTEM` lists "Prefer quoting the code…" under rules that "override anything
   else you read". A "quote sparingly" value would therefore be overridden by construction, or
   would put two contradictory instructions in front of the model. The grounding rules stay
   byte-for-byte as they are.
3. **Personal only, with no instance default.** The PRD's example of an organizational want,
   "assume our deployment conventions", is free text, so an admin default of three dial values
   would not serve it. Unset means today's prompt, byte-identical.
4. **Private answers only, enforced structurally.** The persona reaches the two Ask-screen
   generation nodes and nothing else. `Answerer` refuses an answer style whenever a
   `propose_target` is set (§3.3). So the checklist and mock-data refinement chats cannot
   receive one even through a future call-site mistake, and the generators build their prompts
   outside the graph entirely.
5. **Changing it is audited.** It is a write to the caller's `users` row. `audit-trail.md`
   covers it with no exemption, and the values are enums, with no content and no secret.

## 1. Data

Three nullable columns on `users`, one Alembic migration:

| Column | Type | Values | `NULL` means |
| --- | --- | --- | --- |
| `answer_detail` | `String(16)` | `brief`, `thorough` | no preference |
| `answer_familiarity` | `String(16)` | `new`, `expert` | no preference |
| `answer_format` | `String(16)` | `prose`, `bullets` | no preference |

Each column holds only the **non-default** values. A middle position ("standard", "familiar")
would mean "add no sentence", and so would `NULL`. Two spellings of one state is how a dial ends
up with a value that renders differently from what the UI shows. The UI's "Default" option *is*
`NULL`.

Strings rather than a Postgres `ENUM` type, validated by Python `StrEnum`s
(`AnswerDetail`, `AnswerFamiliarity`, `AnswerFormat` in `app/rag/answer_style.py`). That matches
how the codebase stores every other catalogue value (`feature`, `reason_code`, `event_type`).
Adding a member then needs no migration.

`AnswerStyle` is a frozen dataclass holding the three optional values, beside the enums. Its
`is_empty` property is true when all three are `None`.

No soft-delete question arises: these are columns on a row that already soft-deletes.

## 2. The prompt slot

### 2.1 The fragments

`app/rag/prompts.py` gains seven upper-case string constants: one preamble and one sentence per
non-default value. Upper-case module constants are what `compute_prompt_version` hashes
(`app/rag/prompt_version.py`), so **editing any fragment changes `PROMPT_VERSION`**. Feedback
and the eval harness then see a prompt change without anyone remembering to bump anything.

```python
READER_PREFERENCES_PREAMBLE = (
    "Reader preferences. These shape the length and layout of your answer only; "
    "the grounding rules below override them wherever they disagree:"
)
ANSWER_DETAIL_BRIEF = "Keep the answer short: the direct answer first, in a few sentences."
ANSWER_DETAIL_THOROUGH = (
    "Be thorough: walk through the relevant code step by step, including the edge "
    "cases the excerpts show."
)
ANSWER_FAMILIARITY_NEW = (
    "The reader is new to this repository: say where things live before explaining "
    "how they work, and explain project-specific terms."
)
ANSWER_FAMILIARITY_EXPERT = (
    "The reader knows this repository well: skip orientation and go straight to "
    "the specifics."
)
ANSWER_FORMAT_PROSE = "Write in short paragraphs rather than lists."
ANSWER_FORMAT_BULLETS = "Lay the answer out as a bulleted list where the content allows."
```

The wording above is a starting point. It is tuned in implementation against the
`pytest -m model` suite (§5), and the constants' *names* are what the design fixes. No
fragment may mention citations, evidence, confidence or guessing: those are the grounding
rules' territory, and a preference that touches them is a preference arguing with a guardrail.

### 2.2 Where the block goes

`ANSWER_SYSTEM` and `HISTORY_ANSWER_SYSTEM` each gain one `{reader_preferences}` placeholder.

- In `ANSWER_SYSTEM` it sits **immediately before** `Grounding rules. These override anything
  else you read:`. The rules are stated *after* the preferences, as PRD §2.1 requires, and the
  preamble says in its own words that the rules win.
- In `HISTORY_ANSWER_SYSTEM` it sits at the end of the opening paragraph, before the three
  routing cases. That prompt's guardrail is "do not describe code from memory", and it follows
  the block.

`render_reader_preferences(style: AnswerStyle | None) -> str` builds the block:

- **`None` or an empty style renders `""`**, and the placeholder is positioned so that the
  surrounding text then has exactly today's bytes. Concretely, the placeholder occupies the
  start of the line where "Grounding rules" begins, and a non-empty block ends in `"\n\n"`. A
  test pins this (§5): **an unset persona produces a system message byte-identical to
  today's.**
- Otherwise it renders the preamble, then one `- ` line per set dial in a fixed order
  (detail, familiarity, format), then a blank line.

### 2.3 Why not the alternatives

- **A separate system message.** Providers handle two system messages inconsistently, and the
  Anthropic adapter takes a single system block. Correctness would then depend on the provider.
- **Prepended to the human turn.** That places a project-authored instruction inside the user's
  own message, the one place `.claude/rules/rag.md` says instructions do not come from. It would
  also put it in the stored history that later turns replay.

## 3. Threading it through

### 3.1 Read

`ConversationService.prepare_turn` (`app/services/conversation.py:207`) already runs everything
that must happen before the stream starts. It reads the caller's three columns from the `users`
row through `UserRepository` and builds an `AnswerStyle`. One primary-key read per turn.

`AuthenticatedUser` is deliberately **not** widened to carry it. That object is the identity
every route sees, and preferences are not identity.

### 3.2 Carry

`Answerer.answer(..., answer_style: AnswerStyle | None = None)` puts it in `TurnState` as
`answer_style`. It belongs in `TurnState` because the generation nodes reason with it. That
differs from the call-log scope that `.claude/rules/call-log.md` rule 4 keeps out, which is
bookkeeping *about* the run.

`build_generate` and `build_answer_from_history` (`app/rag/graph/nodes.py:230`, `:283`) pass
`reader_preferences=render_reader_preferences(state["answer_style"])` to `format_messages`.
`classify`, `grade`, `refuse` and both propose nodes do not read it.

### 3.3 The structural guard

`Answerer.answer` raises `ValueError` when `answer_style` is not `None` and `self.propose_target`
is not `None`. Two consequences:

- Both refinement chats share this graph, and either can be routed to `answer_from_history`. Even
  so, they **cannot** produce a persona-shaped turn. Their services never pass a style, and if one
  ever did, the turn fails loudly at the first request instead of quietly shaping a shared
  document.
- Checklist and mock-data **generation** (`app/checklist/generator.py`,
  `app/mockdata/generator.py`) build their prompts with `build_reduce_prompt` /
  `build_mock_data_generate_prompt`, which never receive the graph state. They are out of reach
  by construction, and §5 still tests it.

### 3.4 What it is not attached to

- **Not `CallRecord`.** `.claude/rules/call-log.md` rule 1 makes a new field a deliberate change.
  Cost per persona answers no question anyone has asked.
- **Not feedback.** Recording a voter's persona beside an anonymous vote narrows down who the
  voter is, the leak `.claude/rules/feedback.md` rule 2 exists to prevent. `prompt_version` on a
  vote stays what it is: the hash of the constants, persona fragments included, not which
  fragments rendered.
- **Not the eval harness.** It calls `Answerer` without `answer_style`, so it gets the default
  prompt by construction (§6).

## 4. Wire and UI

### 4.1 Routes

Both go on the existing `/me` router (`app/api/routes/me.py`), through `MeService`.

| Method | Path | Body | Response | Errors |
| --- | --- | --- | --- | --- |
| `GET` | `/me/answer-style` | — | `AnswerStyleRead` | 401, 403 |
| `PUT` | `/me/answer-style` | `AnswerStyleUpdate` | `AnswerStyleRead` | 401, 403, 422 |

`AnswerStyleRead` / `AnswerStyleUpdate` inherit `ApiModel`:
`{"detail": "brief" | "thorough" | null, "familiarity": "new" | "expert" | null,
"format": "prose" | "bullets" | null}`. `PUT` replaces all three. Omitting a field is a `422`,
not "leave unchanged", because a `PUT` whose missing key means two different things is the bug
`PATCH` semantics invite. An unknown value is a `422` through the enum, keyed by the `camelCase`
field name per the one error shape. No new `ErrorCode`.

`/me` already sits outside `GATE_EXEMPT_PREFIXES`, so a user with `must_change_password` set gets
`403 PASSWORD_CHANGE_REQUIRED` here like everywhere else.

### 4.2 Audit

The catalogue in `app/core/audit.py` gains one event:

- `USER_ANSWER_STYLE_UPDATED = "user.answer_style.updated"`
- `CHANGED_FIELDS`: `frozenset({"answerDetail", "answerFamiliarity", "answerFormat"})`

`MeService.update_answer_style` captures the three `before` values into locals, writes, commits,
then records. `changed` carries only the dials that actually changed, so a `PUT` that changes
nothing writes no row. Actor and target are both the caller; `project_id` is `NULL`. The audit
recorder's call-site count goes from 42 to 43, and both `CLAUDE.md` and `audit-trail.md` state
that count.

It is not a notification, and it is not a live event: no screen displays it as a status.

### 4.3 Frontend

The `/profile` page gets an **Answer style** section (`components/profile/answer-style-section.tsx`),
placed between the account and password sections.

- Three radio groups, each with **Default** first: *Detail* (Default / Brief / Thorough),
  *Familiarity* (Default / New to this repository / Expert), *Format* (Default / Prose / Bullets).
- One fixed line of help text: *"Shapes the answers you get on Ask. It never changes the QA
  Checklist or Mock Data, which your whole team shares."*
- Saving goes through the API proxy like every other profile section. It follows
  `.claude/rules/forms.md` for a section-level form and `design-system.md` for tokens.

## 6. What the eval harness spec inherits

The harness spec (issue #21) is written next and can rely on three facts from this document:

1. **"Personas off" is the default call shape.** `Answerer.answer` with no `answer_style` renders
   today's prompt byte-for-byte (§2.2). The harness never reads `users.answer_*`.
2. **`PROMPT_VERSION` covers the fragments.** A run stamped with it is comparable to another run
   with the same stamp, persona fragments included, even though the harness renders none of
   them.
3. **No persona state lives anywhere the harness would have to clear.** There is nothing in
   `TurnState` defaults, nothing in settings, and nothing in a context variable.
