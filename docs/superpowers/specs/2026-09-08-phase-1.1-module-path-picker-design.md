# Phase 1.1 — QA Checklist module path picker: Design

**Status:** Approved design.
**Date:** 2026-09-08

## 0. What this document covers

`docs/PRD.md` §2.1 defines **phase 1.1** as one thing: the same feature set as phase 1, opened
to people who never wrote the code and have never seen the repository's directory structure. It
names exactly one deliverable — the **QA Checklist module path picker** — and gives its reason.

`source_path` on a checklist module is a repository-relative path, and today it is a free-typed
text field:

- `frontend/components/checklist/create-module-dialog.tsx:156` — an `Input` with a placeholder.
- `frontend/components/checklist/module-row-actions.tsx:157` — the same, in the edit popover.
- `backend/app/services/checklist_module.py:141-152` — `create` checks that the *project* is
  indexed and writes whatever string it was given.

The consequence is the one §2.1 describes: a typo'd path returns `201`, and the mistake only
surfaces later and silently, when the background generation cannot match anything under it and
dead-ends at `MODULE_PATH_NOT_INDEXED`. Someone who already knows the tree recovers in seconds.
Someone whose first contact with the repository *is* AskRepo has no way to find the right
string, and no signal that the one they typed was wrong.

Two changes close that:

1. A **read of the project's own indexed file paths**, so a user browses or searches the real
   tree instead of guessing at it.
2. **Rejection at creation** rather than at generation time, so a path that matches nothing is
   a form error on the field the user just filled in.

This is **not a phase-2 item.** The access model does not change, the access resolver is not
touched, and nothing here filters projects on its own — the new read resolves scope through
`access.resolve_project_scope` like every other project read.

## 1. Where the data comes from

The working copy is deleted after indexing (`docs/PRD.md` §4.1), so there is no directory on
disk to walk. The only record of what the repository contains is the `file_path` payload
already sitting on every point in Qdrant, which is what §2.1 points at.

**This is a distinct read, and it is neither of the two that already exist.**

| Read | Filters | Payload | Used by |
| --- | --- | --- | --- |
| `search` | `project_id`, `generation`, vector | full | `CodeRetriever` — top-k similarity |
| `scroll` | `project_id`, `generation`, `file_path` prefix | full | checklist / mock-data generation |
| `list_file_paths` (new) | `project_id`, `generation` | `file_path` **only** | the path picker |

`with_payload=["file_path"]` is not an optimisation detail. The payload holds the chunk text
(`vector_store.py` header, point 3), so reusing `scroll` to enumerate a whole repository would
pull every byte of source in the index across the wire to derive a list of strings. It also
takes no path filter: the picker starts at the repository root, and `scroll`'s `MatchText`
condition has no meaningful empty-string form.

No vector search and no chat-model call, per §2.1. Nothing about this read embeds anything, so
the `EMBEDDING_MODEL_CHANGED` guard deliberately does not apply — the same reasoning that
exempts generation (`checklist_module.py:196-206`).

## 2. The wire shape is lazy, the cache is not

**The endpoint answers one directory at a time.**

```
GET /projects/{id}/indexed-paths?path=backend/app
```

```json
{
  "path": "backend/app",
  "generation": 3,
  "entries": [
    { "name": "api", "path": "backend/app/api", "kind": "dir", "fileCount": 14 },
    { "name": "core", "path": "backend/app/core", "kind": "dir", "fileCount": 9 },
    { "name": "config.py", "path": "backend/app/config.py", "kind": "file", "fileCount": null }
  ],
  "truncated": false
}
```

`?search=auth` switches it to a whole-tree match, returning matching directories and files with
their full paths and `path: ""`. A tree browser needs both: expanding is per-directory, and
searching is not.

**Behind that, one scroll builds the complete distinct path list and it is cached per
`(project_id, active_generation)`.** Serving a lazy wire shape from a full in-memory list looks
like a contradiction and is the point: a per-directory Qdrant read is not cheaper than a whole
one — Qdrant has no notion of a directory, so "the children of `backend/app`" is a prefix filter
over the same collection either way. Paying one scroll per picker session and slicing it in
memory is strictly less work than paying one per expand, while the lazy wire keeps the response
small for a repository with thousands of files.

**Invalidation is structural, not scheduled.** The generation is part of the key, and a reindex
increments `active_generation` (`.claude/rules/ingestion.md` → "Reindex is a generation swap"),
so a swapped index cannot be served from a stale entry — the key it would need does not exist
yet. This is the same mechanism every other generation-scoped read relies on, which is what
§2.1 asks for.

The cache is **in-process**, with a TTL and an entry cap. Two reasons it is not Redis. `CLAUDE.md`
records that Redis is read by the login rate limiter and by nothing else, and a derived,
rebuildable path list is a poor first reason to make that false. And §2's premise is one
organization on one box: a second process would rebuild its own copy in one scroll.

The TTL exists despite the generation key, for the case the key cannot see: a project whose
points were deleted and rewritten *within* one generation — a retried indexing batch — and the
plain fact that a bounded cache of a rebuildable list should not pin memory for a project nobody
has opened in an hour. The entry cap bounds the worst case at
`indexed_path_cache_max_projects` path lists.

## 3. Rejection at creation

`ChecklistModuleService.create` and `update` both check the submitted `source_path` against the
project's indexed paths and refuse with **`400 MODULE_PATH_NOT_INDEXED`** when nothing is under
it.

- **`400`, not `422`.** `response-api.md` reserves `422` for schema violations, which FastAPI
  raises and this codebase never hand-builds. A well-formed string that names nothing in the
  index is "semantically invalid input that passed schema validation", which is that document's
  definition of `400`.
- **`MODULE_PATH_NOT_INDEXED`, the code that already exists.** `ErrorCode` values are a wire
  contract and generation already reports this exact condition under this exact name. A second
  code for the same fact would make a frontend branch on two.
- **A path *matches* when it is an indexed file, or a directory prefix of one.** `backend/app`
  matches because `backend/app/config.py` is indexed; `backend/app/authz` does not, even though
  `backend/app/auth.py` is — the prefix must end at a path separator, or `auth` would claim
  `authz`. This is the same distinction the `scroll` implementation makes in `vector_store.py`
  for the same reason.

**The generate-time check stays.** It is not made redundant by this one: a reindex can drop the
files a module was pointed at, so a path that was valid at creation can stop being indexed while
the module still exists. Removing the later check would turn that into a run that scrolls
nothing and proposes an empty checklist.

**`update` requires an index only when it changes the path.** A rename must keep working on a
project that is somehow not `ready`; a re-point cannot be validated without an index to validate
against.

## 4. Failure modes and status codes

The route is a project read, so it traces the same statuses as `GET /projects/{id}`, plus two:

| Status | Cause |
| --- | --- |
| `401` | Standard, from `CurrentUser` |
| `404 PROJECT_NOT_FOUND` | Not in the caller's scope. Project existence *is* public in phase 1, but a project outside the resolver's scope is one the caller may not know about |
| `409 PROJECT_NOT_READY` | Never indexed. There is no path list to serve, and an empty one would read as "this repository has no files" |
| `422` | A malformed query param |
| `503 VECTOR_STORE_UNAVAILABLE` | Qdrant is unreachable. Someone else's outage, and the request can be retried unchanged (`response-api.md`) |

A reindex in flight is **not** refused. The live generation is still serving
(`.claude/rules/ingestion.md`), and this read records nothing, so it takes `_require_indexed`
and not `_require_a_stable_index` — the same split the chat and question paths make.

## 5. Frontend

One new component, `components/checklist/path-picker.tsx`, used from both places that currently
render a bare `Input` for `sourcePath`.

- **Browse and search in one panel.** A search box filters the whole tree; with it empty, a
  collapsible directory listing expands one level at a time. §2.1 asks for both, and either
  alone leaves a gap: search needs the user to guess a name, and browsing a deep tree to find
  `backend/app/api/routes` is a lot of clicks.
- **Directories and files are both selectable**, because `source_path` is documented as "a
  repo-relative dir or file" (`docs/PRD.md` §4.3 schema).
- **The selected path stays visible and typeable.** The picker is the friendly alternative §2.1
  asks for, not a replacement for knowing the answer — someone who can paste the right path
  should not have to click through to it.
- Fetching is disabled until a project is chosen, so the create dialog does not fire a request
  against an empty id.
- Pure path helpers live in `lib/checklist/paths.ts` and are unit-tested there, matching how
  `lib/checklist/operations.ts` is split out from the panel that uses it.

## 6. Out of scope

- **A file *preview*.** The chunk text is in the payload and could be shown, but choosing a path
  does not need it, and it would put untrusted repository content on a screen that currently
  renders none.
- **Any change to the access model.** Phase 1.1 shares what phase 1 shares.
- **Anything for the mock-data tab.** It reads the module's `source_path`; it has no path field
  of its own.

## 7. Build order

1. `VectorStore.list_file_paths` on the protocol, `QdrantVectorStore` and `InMemoryVectorStore`.
2. `app/services/path_tree.py` — pure functions over a sorted path tuple: `children_of`,
   `matching`, `covers`. No I/O, so they are tested directly.
3. `app/services/indexed_path.py` — the cache, the reader, and the service that resolves access
   and shapes the response.
4. Settings, `.env.example`, `docs/configuration.md`.
5. Schemas and the route on the projects router.
6. `ChecklistModuleService.create` / `update` validation, with the reader injected.
7. Frontend: endpoint, types, query key, hook, `lib/checklist/paths.ts`, the picker, and both
   call sites.
8. Docs: PRD §2.1 and §6, `backend/README.md`, `docs/rag.md`, `CHANGELOG.md`.
