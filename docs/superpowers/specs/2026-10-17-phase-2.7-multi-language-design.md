## 0. What this document covers

Everything is in English: every interface string, and every answer, whatever language the
question was asked in. This phase gives AskRepo a translated interface and answers in the
asker's language, while keeping retrieval against English source code working and **measured**.

The risk that makes this more than a translation task: the index holds code written in English.
A question embedded in another language lands in a different neighbourhood of the vector space
than the code that answers it, and recall drops with nothing reporting an error. That is the same
silent-quality failure the embedding-model guard (`docs/PRD.md` §4.2) exists to prevent, so this
phase builds the measurement before it ships the change it measures.

What is **not** in scope: right-to-left languages (none of the seven needs one); translating
existing checklist or mock-data rows; a per-question language override; a separate translation
model; translating stored conversations; an admin-set instance-wide default language
(`Accept-Language` covers first contact).

### 0.1 The decisions, made

1. **Seven languages:** `en`, `id` (Indonesian), `ja` (Japanese), `ms` (Malay), `zh-HK`
   (Traditional Chinese, Hong Kong), `zh-TW` (Traditional Chinese, Taiwan), `ko` (Korean).
   Stored as BCP-47 tags, because that is what `Intl`, `Accept-Language` and translation tooling
   expect.
2. **The answer follows the question's language; the interface language breaks ties.** When the
   question does not settle it — only code, an identifier, a path, an error message — the reply
   uses the tiebreak language. The tiebreak reaches the prompt as a fixed constant per language,
   never as user text (§4.2).
3. **Shared content follows a per-project `content_language`.** Checklist and mock-data
   generation, and both refinement chats, use the project's setting, never the requester's — a
   shared document must not depend on who pressed the button (`.claude/rules/rag.md`, the
   answer-style rule applied to language).
4. **The fixed refusals are translated**, one reviewed constant per language, chosen by the
   reply's tiebreak language. They remain fixed strings and are never generated (§4.5).
5. **A baseline per language is a release condition.** The eval harness gains a language, and the
   phase is not called shipped until one run per language against the same reference project is
   recorded, before and after the answer change (§3.6, §4.7).
6. **Email is sent in the recipient's language**, through a `language` enum added to both
   composers (§5.1).
7. **Three PRs, in order:** A — the interface; B — eval sets in other languages and the
   baselines; C — answers, refusals, shared content and email. B lands before C so C's PR carries
   a before/after table on identical questions.
8. **`next-intl` without locale-prefixed routes**, with the locale held in a cookie that mirrors
   the user row (§2.2).
9. **A non-English eval set is a translation of an English set**, pair for pair, so a gap
   between two runs is attributable to the language and nothing else (§3.1).

## 1. The language catalogue and where a language is stored

### 1.1 One catalogue, two copies, one test

`app/core/language.py` defines `Language(StrEnum)` with the seven members of §0.1 decision 1. Its
values are a wire contract like `ErrorCode`: add members, never rename them. It also carries
`LANGUAGE_NAMES: dict[Language, str]` — each language's English name, used only to fill prompt
constants (§4.2).

`frontend/lib/i18n/languages.ts` holds the same seven codes and each language's **endonym**
(Bahasa Indonesia, 日本語, Bahasa Melayu, 繁體中文（香港）, 繁體中文（台灣）, 한국어, English) —
what the switcher shows, so a user finds their language without reading the current one.

`tests/test_language_catalogue.py` reads the frontend file and fails if the two code lists
differ. A one-sided addition would otherwise ship a language the backend refuses or one the
frontend never offers.

### 1.2 Columns

All three are `String(8)`, not a Postgres enum, for the reason `app/models/user.py` gives for the
answer-style columns: a new member needs no migration. Every write validates against `Language`
and answers `422` otherwise.

| Column | Null / default | Written by | Read by |
| --- | --- | --- | --- |
| `users.language` | nullable, `NULL` | the user, `PUT /me/language` | interface locale, refusals, email, Ask tiebreak |
| `projects.content_language` | not null, `'en'` | `POST /projects`, `PATCH /projects/{id}` | generation, refinement chats, exports |
| `eval_sets.language` | not null, `'en'` | set creation | the eval runner |

**`users.language` is nullable on purpose.** `NULL` means "never chose", which is different from
"chose English": a user who never picks keeps following their browser's `Accept-Language`, while
one who picked English keeps English on every device. Where the backend needs one concrete value
and has no request header to consult (the mail loop), `NULL` resolves to `en`. Resolution is one
function, `resolve_language(stored, accept_language) -> Language`, in `app/core/language.py`.

An administrator cannot set another user's language. It is a personal preference, like the answer
style, and no admin route writes it.

### 1.3 Routes

- **`GET /me/language`** → `{ "language": "id" | null }`.
- **`PUT /me/language`** with `{ "language": "id" | null }` → the same shape. `null` clears the
  choice. Mirrors `PUT /me/answer-style`.
- **`PATCH /projects/{id}`** with `{ "contentLanguage": "id" }` — the first project update route.
  `Permission.PROJECT_UPDATE` already exists and nothing uses it; this route is gated by
  `require_permission(user, project_id, Permission.PROJECT_UPDATE)`, so a member without it gets
  `403 INSUFFICIENT_ROLE` and a non-member `404 PROJECT_NOT_FOUND`. The body carries
  `contentLanguage` and nothing else; widening it later is a separate change.
- **`POST /projects`** accepts an optional `contentLanguage`, default `en`.
- **Login and refresh responses** gain `language` (nullable), so the frontend can set its locale
  cookie without a second request (§2.2).

### 1.4 Audit

Both settable fields are writes (`.claude/rules/audit-trail.md`):

- **`user.language.updated`**, new, allowlisted `changed` field `{language}`. A language code is a
  choice from a fixed list and never content, so it is safe in the trail. It follows
  `user.answer_style.updated`.
- **`project.updated`**, new, allowlisted `changed` field `{contentLanguage}`. Recorded after the
  commit.
- **`project.created`** gains `contentLanguage` in its allowlisted `changed` fields.

`tests/test_audit_coverage.py` names both new operations.

### 1.5 Live events

`content_language` is not a status any screen polls for, so `.claude/rules/live-events.md` rule 3
does not apply; the project page refetches after its own `PATCH`.

## 2. The interface (PR A)

### 2.1 Library and messages

`next-intl` in its **without i18n routing** mode: URLs do not change. `proxy.ts`'s matching, the
redirects in `.claude/rules/navigation.md` and every link stay as they are. Locale-prefixed routes
(`/id/projects`) were rejected: they suit public sites, and here the language belongs to the user,
not the URL.

Messages live in `frontend/messages/{en,id,ja,ms,zh-HK,zh-TW,ko}.json`, one top-level namespace
per area: `nav`, `auth`, `projects`, `ask`, `checklist`, `mockData`, `eval`, `settings`,
`profile`, `notifications`, `feedback`, `audit`, `errors`, `forms`, `common`.

- **`en.json` is the source.** `next-intl`'s `AppConfig` typing makes a missing or misspelled key
  a type error, so `bun run build` catches it.
- **Parity is a test.** A Vitest test asserts every other file has exactly `en.json`'s keys and,
  per key, the same ICU placeholders. A translation that drops `{count}` fails the test, not a
  screen.
- **Plurals and relative time use ICU** through `next-intl`, which the Japanese, Korean and
  Chinese forms need.

### 2.2 Resolving the locale

`i18n/request.ts` resolves once per request, in order:

1. the `askrepo_locale` cookie,
2. `Accept-Language`, matched against the seven,
3. `en`.

**The cookie mirrors the row; it is never the source of truth.** `askrepo_locale` is httpOnly,
`Path=/`, like the other two cookies, and is written only by code that already writes cookies
(`.claude/rules/frontend-bff.md`):

- `/api/auth/login` and both refresh paths (the catch-all's refresh-and-retry and `proxy.ts`'s
  navigation refresh) set it from the response's `language`, and **clear** it when that is
  `null`, so `Accept-Language` decides.
- The catch-all proxy sets it after a successful `PUT /me/language`, from the response body. This
  is the one response the proxy reads rather than relays untouched, and only to set this cookie;
  the body is still relayed as received.
- `/api/auth/logout` and `unauthenticated()` clear it.

A new device picks the choice up at its first login, which is what the PRD's "a column on the user
row rather than a cookie" requires.

On signed-out pages (`/login`, `/forgot-password`, `/reset-password`) a small selector sets the
cookie for that browser only, through a new `/api/auth/locale` handler that writes nothing to the
backend: there is no account to store it on yet.

### 2.3 The switcher

On the profile page beside the Answer style tab, plus the signed-out selector above. Each option is
the language's endonym (§1.1).

### 2.4 Errors are translated by code

The frontend translates `detail.code`, never `detail.message`. `messages/*.json` carries
`errors.<ErrorCode>` for every code; `lib/api/errors.ts` looks it up and falls back to the
backend's English `message` when a key is missing. `ErrorCode` is already a wire contract
(`CLAUDE.md` → One error shape), so the backend sends nothing new. A Vitest test reads the
backend's `ErrorCode` values (exported to a JSON fixture by a backend test, the way the permission
catalogue is shared) and requires an `errors.*` key for each.

The `409 LAST_OWNER` body's `extra` (the project list) is interpolated into the translated
message; the project names themselves are admin-entered and stay as written.

### 2.5 Form field errors

`.claude/rules/forms.md`'s shells route field errors; they must be translated too, or the interface
is half-translated at exactly the moment a user is stuck.

- **Client-side rules** (zod) take their messages from the `forms` namespace.
- **Backend `422` `fields`** carry Pydantic's English text. The shell maps known validation types
  (`missing`, `string_too_short`, `string_too_long`, `value_error`, `enum`, `url_parsing`, …) to
  catalogue keys and falls back to the backend's text for anything unmapped. To make that
  possible, `ValidationErrorBody` gains a sibling map, `fieldTypes: dict[str, str]`, keyed like
  `fields` and carrying Pydantic's error `type`. `fields` itself stays `dict[str, str]`: changing
  its values to objects would break every existing client, and a sibling map is additive. Recorded
  in `CHANGELOG.md`.

### 2.6 Dates and numbers

`lib/dates.ts` stops hardcoding `"en"` and takes the active locale. Every date or number on screen
goes through `Intl` with it. A timestamp's `title` stays ISO.

### 2.7 What stays as written

Repository content (paths, identifiers, code, commit text); stored model output; admin-entered
names (projects, modules, roles, eval sets); audit event names, which are identifiers — the audit
screen shows a translated **label** beside each.

### 2.8 Fonts

The CJK languages need fallbacks. `frontend/app/globals.css` appends a system stack — `"PingFang
TC", "Hiragino Sans", "Noto Sans CJK TC", "Noto Sans CJK JP", "Noto Sans CJK KR", "Malgun
Gothic", "Microsoft JhengHei"` — after the current font. Nothing is downloaded, which keeps the
"nothing leaves the network" posture. Tokens and colours are unchanged; `docs/design.md` records
the stack.

### 2.9 Lint enforces coverage

`eslint-plugin-i18next`'s `no-literal-string`, restricted to JSX text and the `aria-label`,
`placeholder`, `title` and `alt` attributes, runs in `bun lint`. Without it the next component
reintroduces an English literal and nothing notices. `CLAUDE.md`: a rule lint can enforce is
enforced there.

### 2.10 Who translates

The first pass of the six non-English files is machine-assisted, and PR A says so. Every
non-English file carries `"_meta": { "reviewed": false }` until a native speaker signs it off; the
parity test ignores `_meta`. Reviewed status is a fact about the file, not a claim in a PR
description.

## 3. Eval sets in other languages (PR B)

### 3.1 A translated set is derived from an English set

A non-English set is a **translation** of a `ready` English set: the same pairs, the same source
files, the question text translated. Generating natively in the target language was rejected: each
language would sample different chunks, so its retrieval-hit rate would differ from English's for
two reasons at once and could not be attributed to either.

### 3.2 Data

- `eval_sets.language` (§1.2).
- `eval_sets.source_set_id` — nullable FK to `eval_sets.id`. `NULL` means generated natively, in
  English.
- `eval_pairs.source_pair_id` — nullable FK to `eval_pairs.id`. This is what pairs two runs in
  different languages question by question.
- `eval_pairs.exclusion_reason` — nullable `String(32)`; `'translation_unfaithful'` is its one
  value in this phase (§3.4). A hand exclusion leaves it `NULL`.

A translated set copies `source_path`, `requested_count`, `mix` and `indexed_generation` from its
source: it reads no index of its own, so it is exactly as stale as its source.

### 3.3 Request

`POST /projects/{id}/eval-sets` accepts, as an alternative to the existing generation body,
`{ "sourceSetId": "...", "language": "id" }`.

- Requires `eval.run`, like every set request.
- The source must be `ready`, `language = 'en'`, `source_set_id IS NULL`, in the same project.
  Otherwise `422`.
- `language` must not be `en`.
- At most one live translation per `(source_set_id, language)`; a second answers
  **`409 EVAL_TRANSLATION_EXISTS`**, a new `ErrorCode`.
- `_require_a_stable_index` applies unchanged: `409` while a reindex is in flight.

### 3.4 The job

The existing eval-set generation job, lease, reconcile sweep, live events and notifications
(`eval_set.ready` / `.failed`) are reused unchanged. Only the job body branches: with a
`source_set_id`, it translates instead of sampling.

- One model call per pair, tagged `config=call_config(CallFeature.EVAL_TRANSLATE)` — a new
  `CallFeature`, added to `CALL_PROMPT_VERSIONS` and to `tests/test_call_sites_tagged.py`.
- `EVAL_TRANSLATE_SYSTEM` in `app/rag/prompts.py`, whose rule that matters most is not fluency:
  **identifiers, file paths, symbols and anything in backticks are kept verbatim.** A translator
  that renames `validate_repo_url` removes the exact token retrieval depends on, and the measured
  gap becomes the translator's, not the language's.
- **Faithfulness is checked mechanically.** Every backticked span and every path-shaped token
  (the same pattern `app/rag/grounding.py` uses) in the English question must appear unchanged in
  the translation. A pair that fails is retried once; if it fails again it is written with
  `excluded_at` set and `exclusion_reason = 'translation_unfaithful'`. Never silently dropped: the
  set screen shows how many pairs could not be translated faithfully.
- `reference_answer`, `source_file`, `start_line`, `end_line`, `question_type` and `position` are
  copied unchanged.
- The source set's **current** exclusions are copied. From then on the two sets' exclusions are
  independent. Curation remains exclusion only.

### 3.5 Runs and the judge

The runner is unchanged in PR B: a run over an `id` set sends Indonesian questions through
today's answer graph. That is the baseline — what an Indonesian speaker gets before PR C.

`EVAL_JUDGE_SYSTEM` gains one sentence: the answer may be in a different language from the
reference, and language alone is no reason to mark it `partial` or `wrong`. That bumps
`EVAL_JUDGE`'s prompt version, which a run already records. PR B therefore re-runs the English
baseline too, so every number in its table comes from the same judge.

### 3.6 Comparing across languages

The comparison screen gains **compare with source**: a run on a translated set paired with a run
on its source set through `source_pair_id`, over the pairs both answered. Retrieval hit side by
side first, then the verdict split, never blended — the Phase 2.6 rule. When the two runs' chat
models, judge models or prompt versions differ, the screen says so, as it already does within one
set.

### 3.7 Audit

`eval_set.generation.requested` gains two context keys, `sourceSetId` and `language`. It is the
same kind of action — asking for an expensive set to be built — so it is not a new event name.

### 3.8 What PR B must show

For one reference project: one English set, its six translations, and one run of each, on one chat
model, with a retrieval-hit and verdict table in the PR description. That table is the "before"
half of PR C's evidence. A language whose hit rate falls well below English's is named there, not
averaged away.

## 4. Answers in the asker's language (PR C)

### 4.1 The search query is English — both places one is written

- **`CLASSIFY_SYSTEM`**: `search_query` is written in English whatever the question's language,
  keeping identifiers, paths and quoted code exactly as typed. For `conversational` and
  `out_of_scope` the question is still repeated unchanged; nothing searches with it.
- **`GRADE_SYSTEM`**'s `better_query`, the re-retrieval query, carries the same rule.
  Constraining `classify` alone would send the second search in the original language, on
  exactly the turns that were already struggling.

**How it degrades.** If `classify` fails, the fallback is unchanged: `codebase_question` plus the
raw question (`.claude/rules/rag.md`, "The graph degrades"). Retrieval then searches in the
original language and recall drops, but the turn is answered — a helper node is never the reason a
question goes unanswered. Nothing reports this per turn: knowing a query "should have been"
English would take another model call. The signals are the eval baselines and the existing
feedback reason `wrong_language_or_tone`, and this document says so rather than pretending a
per-turn check exists.

### 4.2 The reply-language slot

`ANSWER_SYSTEM`, `HISTORY_ANSWER_SYSTEM` and the conversational reply prompt gain a
`{reply_language}` slot, filled from a constant in `app/rag/prompts.py`:

> Reply in the language the question is written in. When the question does not settle it — it is
> only code, an identifier, a path or an error message — reply in {name}. Code, identifiers, file
> paths, quoted excerpts and `[n]` labels stay exactly as they appear in the excerpts.

`{name}` comes from `LANGUAGE_NAMES`, never from user input.

- **The slot sits beside `{reader_preferences}`, before the grounding rules,** and like it never
  mentions citing, evidence, confidence or guessing. `tests/test_answer_style_prompt.py` extends
  to this slot.
- **Unlike answer style it is always rendered**, `en` included. The default prompt therefore
  changes and the answer prompt version bumps. That is intended, and it is what §3.8's baseline
  exists to measure.

### 4.3 Whose language breaks the tie

`Answerer.answer` gains a required `reply_language: Language`. It is not a style, so
`.claude/rules/rag.md`'s "style only on Ask" check does not apply to it.

| Caller | Tiebreak | Why |
| --- | --- | --- |
| Ask — `app/services/conversation.py` | the asker's `language`; if `NULL`, the request's `Accept-Language`; then `en` | A private conversation: one user's preference is correct |
| Checklist and mock-data refinement chats | the project's `content_language` | Those replies are shared documents (`.claude/rules/feedback.md` rule 5); who pressed Send must not decide them |
| Eval runner | the set's `language` | A run must not depend on who requested it |

`prepare_turn` resolves the language (it already has the request), so the stream needs nothing
new.

### 4.4 Shared content follows `content_language`

- `TESTER_LANGUAGE` (appended to reduce and propose) and the mock-data generation prompt gain one
  sentence: write test names, expected results and generated values in `{content_language}`;
  field names, keys and anything that is code stay as written.
- `MAP_FILE_SYSTEM`'s per-file summaries are intermediate and stay English.
- **Changing `content_language` never rewrites rows.** Existing rows stay as they are, and the
  propose prompt is told existing rows may be in another language and **must not** propose an
  `update` only to translate one. Otherwise one setting change would raise a change set touching
  every row and bury the real changes in it. Translating existing content is a separate feature.
- **Exports** (checklist spreadsheet, mock data) translate their column headers by the project's
  `content_language` — an export is a shared document — from a fixed table in the export code.

### 4.5 Refusals

`NO_CONTEXT_ANSWER` and `OUT_OF_SCOPE_ANSWER` in `app/rag/grounding.py` become
`dict[Language, str]`, each value a reviewed constant, chosen by `reply_language`. They remain
fixed strings, streamed as ordinary `token` events and never generated, so "no evidence, no
generation" (`.claude/rules/rag.md`) holds unchanged. `groundingWarnings` and `intent` in `done`
are unchanged. A test requires both tables to cover every `Language`.

The stored `Message.content` holds the refusal in the language it was streamed in; a later change
of preference does not rewrite it, as with any other stored answer.

### 4.6 Grounding checks still work, because paths stay verbatim

`unknown_paths` and `uncited_answer` keep working in every language only because §4.2 keeps paths
and `[n]` labels as written. The model-backed suite checks it (§4.7).

### 4.7 What PR C must show

- **Before/after.** Re-run PR B's seven sets on the same chat model and report retrieval hit and
  verdict per language, before (PR B's runs) and after. This is the decision point per language.
- **`uv run pytest -m model`** gains non-English cases: an Indonesian and a Korean question each
  produce an English `search_query` that keeps the named identifier, and an answer in that
  language carrying at least one `[n]`. That suite needs a served model and is run by the
  maintainer on their own machine; the PR records the run.

**Prompt versions that bump in PR C:** `classify`, `grade`, `answer`, `history_answer`, `reduce`,
`propose_checklist`, `propose_mock_data`, `generate_mock_data`.

## 5. Email and the remaining surfaces

### 5.1 Email (PR C)

- `compose_notification(*, event_type, target_type, target_id, project_id, to, settings,
  language)` and `compose_password_reset(*, raw_token, to, settings, language)`: one keyword-only
  `language: Language` each. An enum cannot carry content. `tests/test_mail_compose.py` is updated
  to pin the new signatures — the change `.claude/rules/mail.md` requires before any addition.
- `MESSAGES` becomes `dict[Language, dict[NotificationType, tuple[str, str]]]`; `RESET_MESSAGE`
  becomes per-language. A test requires every `Language` × every `NotificationType`, so a new
  event without its translations fails the test rather than the email.
- The templates' fixed chrome comes from the same per-language table and is passed to Jinja as
  fixed strings. `autoescape=True` and `StrictUndefined` are unchanged; `<html lang>` is set. No
  asset is added.
- **Which language:** notification email uses the recipient's `users.language` read at send time
  — `mail_loop` already loads the recipient to check for deactivation, so no query is added. This
  is not a visibility decision, so the fan-out snapshot rule (`.claude/rules/notifications.md`
  rule 4) does not apply. A password reset uses the account's language, else the `Accept-Language`
  of the request that asked for it, else `en`. An unknown address still sends nothing.
- `[{APP_ENV}]` and `MAIL_APP_NAME` in the subject are unchanged.

### 5.2 Deliberately English

Backend `message` text (the frontend translates by `code`); logs; audit event names; `ErrorCode`
values; `/docs`; repository content; admin-entered names; stored model output.
