# Phase 2.4 — The mail provider: self-service password reset, and email delivery: Design

**Date:** 2026-09-26
**Intent:** `docs/PRD.md` §2.1, Phase 2.4; §8's two open questions owned by this phase; §9's egress bullet
**Depends on:** Phase 2.3 (the notification record this phase delivers against)
**Followed by:** Phase 2.5 (measurement)

---

## 0. What this document covers

AskRepo has never sent anything out of the network it runs in. That absence has been
load-bearing: it is why there is no email verification, no invitation flow, no
self-service password reset, and no outbound queue to operate (`docs/PRD.md` §4.0). Two
features want to end it. A user who forgot their password needs a link to reach them
without an administrator in the loop; and Phase 2.3's notification record needs to reach
someone who is not currently looking at AskRepo — the entire point for a generation that
takes twenty minutes.

This sub-phase ships **one mail provider, used by both**, and ships it **off**.

What is in scope: an SMTP sender, an `MAIL_ENABLED` switch and its settings, three
`/auth/password-reset/*` routes, one table (`password_reset_tokens`), four delivery-state
columns on `notifications`, a worker `mail_loop`, a plain-text composer, two public
frontend pages, and one new rule file.

What is deliberately **not** in scope: HTML email, digests or batching, a
`List-Unsubscribe` endpoint, email verification, invitations, a Kafka mail topic, bounce
processing, and any per-instance policy overriding a user's own email preference.

### 0.1 The decisions, made

1. **§8's "is email worth a mail provider?" is decided per instance, not per codebase.**
   The code ships; `MAIL_ENABLED` defaults to `false`; an operator who concludes in-app
   is enough never turns it on, and that instance's egress posture is exactly what it
   was before this phase. §1.
2. **One master switch.** `MAIL_ENABLED` gates password reset and notification email
   together. A user who wants no notification email mutes it per event through the
   `email` preference column Phase 2.3 already shipped. §2.
3. **Immediate, one email per event; the recipient owns the preference.** This closes
   §8's "immediate or digested, and who decides?". §5.
4. **Notification email is an outbox, drained by the worker.** Delivery state lives on
   the `notifications` row that represents the delivery, and a worker loop claims, sends
   and marks. No Kafka topic, no new infrastructure. §4.
5. **A reset email is sent once, immediately, and never retried.** Only the token's hash
   is ever stored, so nothing could reconstruct the link for a retry; a user whose email
   did not arrive requests another. §6.2.
6. **An email carries a fixed message and a link, and nothing else.** Enforced by the
   composer's signature, not by review. §3.
7. **Email delivery is a sixth audit exemption.** The password-reset *request* and
   *completion* are audited; the sends are not. §7.

### 0.2 Amendments to `docs/PRD.md` and the rules, made in the implementation change

`.claude/rules/documentation.md` requires a decision that changes a documented fact to
update the doc in the same change. The implementation change makes these:

1. **§4.0's out-of-scope list loses "email-based password reset"**, and gains the
   self-service flow beside the admin one, which stays.
2. **§8's two open questions are closed**: the in-app-vs-email question as "decided per
   instance, via `MAIL_ENABLED`, default off"; the digest question as "immediate, per
   event, preference owned by the recipient".
3. **§9's egress bullet** is reworded from "if notifications ship" to what shipped: the
   content rule, the composer that enforces it, the fragment-carried reset token, and
   `SMTP_PASSWORD` as a secret.
4. **A sixth audit exemption** in §2.2 and `.claude/rules/audit-trail.md`. §7.
5. **"No mail provider anywhere in the stack"** in `CLAUDE.md` becomes "an optional mail
   provider, off by default".

### 0.3 The two constraints that are not negotiable

**Nothing derived from an indexed repository leaves the network.** Repository names,
module names and file paths are inventory of the organization's private codebases
(`docs/PRD.md` §9). An email's subject and body are built from `event_type`,
`target_type`, `target_id` and `project_id`, and never from
`notification_events.details` — the seam Phase 2.3 drew in advance
(`.claude/rules/notifications.md` rule 3).

**Email adds no second recipient path.** It is a delivery attempt against a
`notifications` row the fan-out already wrote. It never calls
`resolve_notification_recipients`, never queries memberships, and never decides who
hears about something. `tests/test_scoping_is_single_point.py` is unchanged and still
passes.

## 1. Why the switch, rather than an answer

`docs/PRD.md` §8 left the in-app/email question "sequenced, not resolved", and forbade
Phase 2.4 from paying for a mail provider without weighing it. The weighing is real and
the answer differs by deployment: an organization with an internal mail relay and a team
that walks away from twenty-minute jobs gets a great deal from email; an organization
whose security review treats any outbound path as a finding gets nothing but a new
question to answer.

So the cost is paid in code once and in posture only by the operator who chooses it.
With `MAIL_ENABLED=false`:

- no row is ever marked `email_state = 'pending'`,
- `mail_loop` is not started,
- `POST /auth/password-reset/request` refuses with `409 PASSWORD_RESET_UNAVAILABLE` and
  writes nothing,
- no SMTP connection is ever opened.

That is the pre-2.4 instance, byte for byte on the wire, plus four nullable columns and
an empty table. Phase 2.3's droppability obligation ("nothing here becomes dead weight")
holds in the weaker form it has to: what is unused is inert and cheap, not absent.

## 2. Configuration

Every field lands in `app/config.py`, `backend/.env.example` (names and defaults only)
and `docs/configuration.md` in the same change.

| Setting | Type / default | Meaning |
| --- | --- | --- |
| `MAIL_ENABLED` | `bool`, `false` | The one switch for all egress. §1 |
| `SMTP_HOST` | `str`, `""` | The organization's mail relay |
| `SMTP_PORT` | `int`, `587` | |
| `SMTP_SECURITY` | `"starttls" \| "tls" \| "none"`, `"starttls"` | `tls` is implicit TLS (typically 465). Cleartext is a choice an operator makes by name, never a default |
| `SMTP_USERNAME` | `str`, `""` | Empty means no `AUTH` |
| `SMTP_PASSWORD` | `SecretStr`, `""` | Never logged, never serialized. Joins the PAT encryption key and the chat API key in `SECURITY.md` |
| `SMTP_FROM` | `str`, `""` | The envelope and header sender |
| `MAIL_APP_NAME` | `str`, `"AskRepo"` | The trailing title of every subject. Separate from `APP_NAME` (`"AskRepo API"`), which names the API docs |
| `APP_BASE_URL` | `str`, `""` | The frontend's public origin, used to build every link. `CORS_ORIGINS` is a list and is not reused |
| `PASSWORD_RESET_TOKEN_TTL_MINUTES` | `int`, `30`, `ge=5` | |
| `PASSWORD_RESET_RATE_PER_HOUR_IP` | `int`, `10` | |
| `PASSWORD_RESET_RATE_PER_HOUR_EMAIL` | `int`, `3` | |

**Fail fast on configuration, not on the relay.** A `model_validator` on `Settings`
refuses `MAIL_ENABLED=true` with an empty `SMTP_HOST`, `SMTP_FROM` or `APP_BASE_URL`,
and refuses an `APP_BASE_URL` that is not an absolute `http(s)` URL. This runs in both
the API and the worker, beside the existing production checks. There is deliberately
**no SMTP connectivity probe at startup**: a relay that is down for maintenance must not
stop the instance booting, and a pending row simply waits for it.

**One new dependency:** `aiosmtplib`. Nothing is added to either Compose file; the
operator points the instance at a relay they already run. `docs/deployment.md` records
that obligation.

## 3. The composer, and what leaves the network

`app/mail/compose.py` is the only code that turns a delivery into an email, and its
signatures are the enforcement of §0.3:

```python
def compose_subject(message: str, *, settings: Settings) -> str: ...

def compose_notification(
    *,
    event_type: NotificationType,
    target_type: str | None,
    target_id: uuid.UUID | None,
    project_id: uuid.UUID,
    to: str,
    settings: Settings,
) -> OutboundEmail: ...

def compose_password_reset(*, raw_token: str, to: str, settings: Settings) -> OutboundEmail: ...
```

There is no parameter through which `details`, a project name, a module name or a path
could arrive. Adding a "helpful preview" means changing a tested signature, which is a
reviewable event rather than a quiet one. A test asserts the parameter set.

### 3.1 Subject

```
[{APP_ENV}] {message} | {MAIL_APP_NAME}
```

The `[{APP_ENV}] ` prefix is omitted exactly when `APP_ENV == "production"`, the same
comparison `config.py` already uses for its production checks.

```
development:  [development] Index finished | AskRepo
staging:      [staging] Change set awaiting review | AskRepo
production:   Index finished | AskRepo
```

`{message}` is a **fixed string per event type** (§5.3) or `Reset your password`. The
subject is the most visible part of an email and is covered by the same content ban as
the body.

### 3.2 Body

**Plain text only.** No HTML means no remote images, no tracking pixels, and no rendered
markup whose construction someone could later feed a value into. A body is one sentence,
one link, and a footer:

```
A project you are a member of finished indexing.

Open: https://askrepo.internal/projects/7f3c…

—
You are receiving this because email notifications are on for this event.
Manage them: https://askrepo.internal/settings/notifications
```

The link carries an id and nothing else. It passes through login and the ordinary
`404 PROJECT_NOT_FOUND` rules like any other page, so a forwarded email reveals an id
to someone who can do nothing with it.

## 4. Delivery: the outbox and `mail_loop`

This section covers notification email only. A reset email is sent once from the
request's background task and never enters this path (§6.2).

### 4.1 The claim

The outbox uses the lease pattern ingestion already relies on:

```sql
UPDATE notifications
   SET email_claimed_until = now() + interval '2 minutes',
       email_attempts      = email_attempts + 1
 WHERE id IN (SELECT id FROM notifications
               WHERE email_state = 'pending'
                 AND (email_claimed_until IS NULL OR email_claimed_until < now())
               ORDER BY created_at LIMIT 50 FOR UPDATE SKIP LOCKED)
RETURNING …
```

Whoever holds the claim sends and then marks the row. Two processes can never send the
same row at the same time.

**Delivery is at-least-once, and this document does not claim otherwise.** A process
that crashes after the relay accepts a message and before the row is marked will send it
again when the lease expires. For a nudge, a rare duplicate is the correct side of the
trade.

### 4.2 `mail_loop` is a sibling of `reconcile_loop`, not a step inside it

`reconcile_loop` recovers stranded indexes and generations. A slow relay — a 10-second
SMTP timeout across 50 rows — must never delay that. So `app/worker.py` starts
`mail_loop` as its own task, on its own 60-second cadence, **only when `MAIL_ENABLED`**.
Each tick:

1. Claims up to 50 pending notification rows.
2. Reads the recipient's user row. A user whose row is soft-deleted (deactivated) is
   marked `skipped`. The address is read at send time, so an address changed since the
   event is honoured.
3. Marks a notification row `skipped` instead of sending it when its event is older than
   **24 hours**. Without this, turning mail off for a week and back on would deliver a
   week of "Index finished" about indexes long since superseded.
4. Composes, sends, and marks `sent` with `sent_at = now()`.

### 4.3 Failure classification

Following the queue's existing split between retryable and terminal:

| Failure | Class | Result |
| --- | --- | --- |
| Connection refused, timeout, TLS handshake failure, SMTP `4xx` | retryable | stays pending; the lease expiry spaces the next attempt |
| SMTP `5xx` (recipient rejected, relay refused sender), authentication failure | terminal | `failed` immediately |
| Fifth attempt fails retryably | terminal | `failed` |

The attempt limit is a module constant (`MAX_EMAIL_ATTEMPTS = 5`), not a setting — no
operator decision turns on it. The SMTP error is logged at `WARNING` with the row id and
event type; it is never stored in a column any screen renders.

## 5. Notification email

### 5.1 The decision is made at fan-out, inside the transaction

`NotificationFanout._write` already snapshots the in-app preference onto each row
(`in_app_visible`). It snapshots the email preference the same way:

```
email_state = 'pending'  when settings.mail_enabled and the recipient's email preference is on
              NULL       otherwise — email was never in play for this row
```

`NotificationPreferenceRepository` gains `muted_email(event_type, recipients)` beside
`muted_in_app`, with the same sparse, absence-means-on semantics.

This keeps every Phase 2.3 rule intact:

- **Rule 1** — recipients are the rows the fan-out wrote; nothing new resolves anyone.
- **Rule 2** — the decision commits with the state change, ahead of the commit.
- **Rule 4** — a row is still written for every recipient; the email preference is a
  snapshot, like the in-app one. A user who muted in-app but wants email gets
  `in_app_visible = false, email_state = 'pending'` — the exact combination rule 4 was
  written to keep possible. Changing a preference later neither cancels a queued email
  nor sends an old one.
- **Rule 6** — actor exclusion already happened when the recipient set was built;
  email inherits it.

### 5.2 Four columns on `notifications`, no table

| Column | Type | Purpose |
| --- | --- | --- |
| `email_state` | `varchar(16)`, null | `pending` \| `sent` \| `failed` \| `skipped` |
| `email_attempts` | `smallint`, not null, default `0` | |
| `email_claimed_until` | `timestamptz`, null | §4.1 |
| `email_sent_at` | `timestamptz`, null | |

Plus a partial index `ON notifications (created_at) WHERE email_state = 'pending'`, so
the sender's scan stays proportional to the backlog rather than the table.

`docs/PRD.md` §2.1 says email adds "no table and no read state"; Phase 2.3's design
anticipated "a delivery-state column or child table". Four columns is more than "a
column", and the claim PRD §2.1 protects — no second table, no read state, no reshaping
of `notification_events` — holds exactly. No existing column changes meaning.

**No pruning is added.** Email state lives on the row, so
`NOTIFICATION_RETENTION_DAYS`'s existing prune removes it with the row.

### 5.3 Messages and links

| Event | `{message}` | Link |
| --- | --- | --- |
| `project.ready` | Index finished | `/projects/{project_id}` |
| `project.failed` | Index failed | `/projects/{project_id}` |
| `project.reindex.finished` | Reindex finished | `/projects/{project_id}` |
| `project.reindex.failed` | Reindex failed | `/projects/{project_id}` |
| `checklist_change_set.pending` | Checklist change set awaiting review | `/checklist/{target_id}` |
| `checklist_change_set.applied` | Checklist change set applied | `/checklist/{target_id}` |
| `checklist_change_set.discarded` | Checklist change set discarded | `/checklist/{target_id}` |
| `mock_data_change_set.pending` | Mock data change set awaiting review | `/checklist/{target_id}` |
| `mock_data_change_set.applied` | Mock data change set applied | `/checklist/{target_id}` |
| `mock_data_change_set.discarded` | Mock data change set discarded | `/checklist/{target_id}` |
| `membership.granted` | You were added to a project | `/projects/{project_id}` |

The mock-data rows link to the module page because the Mock Data tab lives there, not on
a route of its own. Each message has a one-sentence body counterpart in the same table in
code. A test walks `NotificationType` and fails if any member lacks a message, a body
sentence or a link rule, so a twelfth event cannot ship silently unmailable.

### 5.4 Frontend

`NotificationPreferencesRead.email_enabled` becomes `settings.mail_enabled`. When true,
the email switches on `/settings/notifications` are live and the "not configured on this
instance" line is not rendered. No other screen changes.

## 6. Self-service password reset

### 6.1 Routes

All three live under `/auth`, which `GATE_EXEMPT_PREFIXES` already exempts from the
forced-password-change gate, and none requires authentication.

| Route | Body | Success | Refusals |
| --- | --- | --- | --- |
| `GET /auth/password-reset/availability` | — | `200 {enabled: bool}` | — |
| `POST /auth/password-reset/request` | `{email}` | `202`, empty | `409 PASSWORD_RESET_UNAVAILABLE` (mail off), `429` (rate limit), `422` |
| `POST /auth/password-reset/confirm` | `{token, newPassword}` | `204` | `400 PASSWORD_RESET_TOKEN_INVALID`, `400 WEAK_PASSWORD` (password policy), `422` (malformed body) |

**`request` returns the same `202` for every input** — unknown address, deactivated
account, live account. The `409` reveals nothing about any account: it is the same answer
for every caller on the instance.

**`confirm` has one refusal for every bad token** — unknown, expired, used or revoked
all return `400 PASSWORD_RESET_TOKEN_INVALID`, so the response never says which.

### 6.2 `request`

When the normalized address matches a live user row:

1. Revoke that user's unused, unexpired tokens (`revoked_at = now()`). One live token per
   user; an earlier email's link stops working.
2. Mint 32 random bytes, URL-safe encoded. Store only `sha256(token)`, with
   `expires_at = now() + PASSWORD_RESET_TOKEN_TTL_MINUTES`.
3. Commit, and return `202`.
4. **After the response is sent**, deliver once through FastAPI's `BackgroundTasks`:
   compose, send, set `sent_at`. The raw token is handed to the task as an argument and
   lives nowhere else. On any failure — relay down, `4xx`, `5xx` — log at `WARNING` with
   the token row id (never the token) and stop. **There is no retry.**

Step 4 is after the response, not before it, because sending before responding makes a
live account measurably slower than an unknown one — an enumeration oracle by timing.
This is the first use of FastAPI's `BackgroundTasks` in the codebase; nothing else needs
"after the response" semantics, and the worker is the wrong place for a send whose raw
token only ever exists in the request's memory.

**Why no retry.** The raw token exists only in memory between step 2 and the send. It
is never logged, never stored, and never returned in a response — only its hash is
written, exactly the refresh-token shape `docs/PRD.md` §2.1 asks for. A hash cannot be
turned back into a link, so no later process *could* retry, and making one able to would
mean storing a recoverable secret: a database dump plus the key would then expose every
live reset link. The alternative costs almost nothing, because the person the email is
for is actively waiting for it: `/forgot-password` tells them to request another if it
does not arrive, and the one-live-token rule means the new request revokes the old
token whether or not its email ever left. Notification email keeps its outbox (§4)
because nobody is waiting for it.

A process that dies between the commit and the send leaves a token that nobody can use
and that expires on its own; the prune in §6.6 removes it.

### 6.3 `confirm`

Looks up `sha256(token)`; requires `used_at IS NULL`, `revoked_at IS NULL`,
`expires_at > now()`, and a live user row. Then, in one transaction:

- set the new password (same policy and bcrypt cost as everywhere else,
  `app/core/passwords.py`),
- set `used_at = now()`,
- **clear `must_change_password`** — the user chose this password themselves; forcing a
  second change would be incoherent,
- **revoke every refresh token** for the user — every session ends, the same as an admin
  reset.

It does not log the user in. The frontend sends them to `/login`.

The admin reset route (`POST /users/{id}/reset-password`) is unchanged and works whether
or not mail is enabled.

### 6.4 The token rides in the fragment

The emailed link is `APP_BASE_URL/reset-password#token=…`. A browser never sends a
fragment to any server, so the token stays out of Next's request logs, a reverse proxy's
access log, and any `Referer` header. The page reads it client-side and posts it in the
request body. It cannot go through the generic API proxy (`app/api/[...path]/route.ts`),
which answers `401` before forwarding when the browser holds no session cookie — and a
user resetting a forgotten password holds none. So the three reset routes and `GET
/auth/password-policy` (which the new-password field's live checklist reads) each get a
dedicated `app/api/auth/*` route that forwards without a cookie, beside the existing
`app/api/auth/login` route. Next resolves a specific route ahead of the catch-all, so
`apiFetch("/auth/password-reset/confirm")` reaches the dedicated route with no client
change.

### 6.5 Rate limits

Built on the existing `RateLimiter`:

- `PASSWORD_RESET_RATE_PER_HOUR_IP`, keyed on the relayed client address
  (`TRUSTED_PROXY_HOPS` applies unchanged).
- `PASSWORD_RESET_RATE_PER_HOUR_EMAIL`, counted for **every** submitted address, live or
  not — so hitting it reveals nothing about existence.

`confirm` is not rate limited: a 256-bit token is not guessable.

**On a Redis error both checks are skipped**, matching the login limiter. The accepted
consequence: while Redis is down, someone who knows a colleague's address can flood that
inbox with reset emails. It cannot take over the account — each email holds a token only
its recipient can read — and the one-live-token rule means only the newest link works.

### 6.6 `password_reset_tokens`

| Column | Type | Notes |
| --- | --- | --- |
| `id` | `uuid` pk | |
| `user_id` | `uuid` fk → `users.id` | indexed |
| `token_hash` | `varchar(64)`, unique | sha256 hex — the only form of the token ever stored |
| `created_at` | `timestamptz` | |
| `expires_at` | `timestamptz` | |
| `used_at` | `timestamptz`, null | |
| `revoked_at` | `timestamptz`, null | |
| `sent_at` | `timestamptz`, null | set when the single send succeeds; `NULL` means it failed or never ran |

No claim, attempt or state columns: nothing but the request's own background task ever
sends from this table (§6.2).

**Hard-deleted, not soft-deleted**, following the `refresh_tokens` precedent: a dead
token is not a record anybody needs, and a `deleted_at` would only keep hashes around
longer. The worker's existing tick deletes rows expired more than a day ago, beside the
refresh-token prune. `docs/data.md` records this as the second table under that
exception.

### 6.7 Frontend

- `/forgot-password` — an email field. On submit, always shows "If that account exists,
  a reset link is on its way. If it does not arrive within a few minutes, request
  another." — the second sentence is the retry path (§6.2). It renders the same message on `202` and on `429` —
  distinguishing them would tell a caller something the backend was careful not to.
- `/reset-password` — reads `#token` from `window.location.hash`, never from
  `searchParams`; a new-password field with confirmation; on `204` routes to `/login`
  with a success notice; on `400` explains the link is invalid or expired and links to
  `/forgot-password`.
- `/login` shows "Forgot password?" only when `availability.enabled`. The check runs in the
  login page's Server Component through `serverFetch`, which calls the API directly and does
  not require a cookie, and is passed to the client screen as a prop; a failed check hides
  the link.
- `proxy.ts` treats `/forgot-password` and `/reset-password` as public routes, the way
  it treats `/login`. Both are pages, not dialogs (`.claude/rules/forms.md`).

## 7. Audit

### 7.1 Two new events

| Event | Actor | `details` |
| --- | --- | --- |
| `auth.password_reset.requested` | the matched user; or `NULL` with `{unknownAccount: true}` | — |
| `auth.password_reset.completed` | the user | `{revokedCount}` |

`requested` follows the failed-login rule exactly: the submitted address is stored only
when it matches a live user row, because people paste passwords into email fields. It is
recorded for every accepted request, not for the `409` or `429`, which wrote nothing.

A bad token on `confirm` records nothing: there is no actor to attribute it to, and with
a 256-bit token a failed confirm is a stale link, not an attack.

Neither event carries the token, its hash, or anything derived from it. Both are recorded
after their commit (`.claude/rules/audit-trail.md`), declared in `app/core/audit.py` with
their allowlists, and named in `tests/test_audit_coverage.py`.

### 7.2 The sixth exemption: email delivery

The audit rule says moving data out records an event. Email delivery does not, and the
exemption is named rather than left as a gap:

> **6. Email delivery.** A notification email or reset email is a transport of something
> already recorded — the notification event, or the `auth.password_reset.requested`
> row — and no human performs the send; a background task or the worker does. The
> delivery-state columns (`notifications.email_state`/`email_sent_at`,
> `password_reset_tokens.sent_at`) are its record. Auditing each send would write one row per recipient per
> event and bury `user.deactivated` under the same noise §2.5 refuses for the ask route.

This lands in `docs/PRD.md` §2.2 and `.claude/rules/audit-trail.md` ("five exemptions"
becomes "six") in the implementation change.

## 9. Testing

No test needs a real SMTP server. A `RecordingMailSender` implements the sender protocol
and records what would have been sent, the way `InMemoryIngestionQueue` stands in for
Kafka.

**Reset** — known and unknown addresses produce byte-identical `202` responses; the
immediate send is scheduled as a background task, not awaited in the handler; a second
request revokes the first token; `confirm` succeeds once and then `400`s; expired,
revoked and unknown tokens return the same `400`; `confirm` clears
`must_change_password` and revokes every refresh token; no column of
`password_reset_tokens` holds anything but the hash (the raw token appears only in the
recorded email); a failed send sets no `sent_at` and schedules nothing further; `409`
with mail off; both rate limits, including the
per-email limit on an unknown address.

**Fan-out** — `email_state = 'pending'` only when mail is on and the email preference is
on; `NULL` otherwise; the row is written when in-app is muted and email is on.

**Sender** — two concurrent claims never return the same row; `4xx` stays pending, `5xx`
goes `failed`; `failed` after five attempts; a notification older than 24 hours is
`skipped`; `mail_loop` never reads `password_reset_tokens`; a deactivated
recipient is `skipped`; `mail_loop` is not started with mail off.

**What leaves the network** — the composer's parameter set contains no `details`; every
`NotificationType` has a message, a body sentence and a link rule; the subject carries
the `[env]` prefix outside production and omits it in production; bodies are
`text/plain`.

**Existing guards extended** — `tests/test_audit_coverage.py` (two events),

## 11. Out of scope, and where it would go

- **HTML email.** A template engine and a rendering surface for a benefit the plain-text
  body does not need.
- **Digests.** §8 is closed as "immediate"; a digest would read `notifications` rows
  with `email_state = 'pending'` over a window and needs no schema change beyond this
  one.
- **`List-Unsubscribe`.** Needs an unauthenticated, tokenized endpoint; the settings link
  suffices for an internal tool.
- **Bounce handling.** A relay's asynchronous bounce is invisible to SMTP submission; a
  `failed` state here means the relay refused at submission time, nothing more.
- **An instance-wide policy overriding user preferences** (e.g. "never email about
  discards"). A setting, if ever wanted; not a schema change.
- **A Kafka mail topic.** The outbox would remain the source of truth either way; a topic
  would only shorten latency, which nothing here needs.
