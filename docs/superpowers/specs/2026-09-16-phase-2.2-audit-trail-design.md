# Phase 2.2 — Append-only audit trail: Design

**Status:** Complete draft, pending review. No open questions (§12).
**Date:** 2026-09-16
**Issue:** [#23](https://github.com/aolus-software/ask-repo/issues/23)

## 0. What this document covers

`docs/PRD.md` §2.1 puts **Phase 2.2** directly after RBAC, and gives the reason in one sentence:
the moment access stops being uniform, *who granted whom access to what* becomes a question with
no answer anywhere. It also makes `docs/PRD.md` §7's destructive-gating criterion checkable on a live instance
rather than only by automated test.

Phase 1 has attribution and no history. `created_by` is the whole record, so a **deleted project
takes its `created_by` with it** and nothing anywhere records who deleted it. If a shared index
disappears on a Tuesday, there is no way to find out what happened. Logins, failed logins,
deactivations and role edits are equally invisible.

This document specifies an `audit_events` table, the thirty-seven event types written to it, the
payload each one carries, two admin-only read routes, a retention sweep, two screens, and the
seven decisions issue #23 and the PRD leave to whoever specifies this.

**The coverage rule outranks the catalogue.** `.claude/rules/audit-trail.md` states the standing
obligation — *every write, and every export, records an audit event* — and §1.1's list is that rule
applied to the routes that exist on 2026-09-16. A list goes stale the moment someone adds a route
and the failure is silent: the route works, the tests pass, and the trail has a hole nobody finds
until the day it is needed. The rule and §8.3's two-directional coverage test are what close that;
this document's list is a snapshot, not the authority.

**Nothing here adds infrastructure.** No new service, no new datastore, no egress. The four stores
stay four and Postgres gains one table.

### 0.1 The seven decisions, made

| Decision | Answer | Where |
| --- | --- | --- |
| Postgres table or structured log stream? (`docs/PRD.md:112`, issue #23's open box) | **Table.** Queryable from the product, covered by the Postgres backup `docs/PRD.md` §9 already requires, no new operator tooling | §2 |
| Does the trail cover RBAC events, which §2.2's bullet list omits? | **Yes.** §2.2's own rationale asks for exactly them, and they became possible only after Phase 2.1 | §1.1, §9 |
| A fixed event list, or a standing obligation? | **A rule, in `.claude/rules/audit-trail.md`.** Every write and every export records an event; a list cannot survive the next route | §0, §1.1, §8.3 |
| How wide is "every write"? | **Writes and exports across every resource** — CRUD, destructive bulk operations, change-set applies, generation requests, exports. Ordinary reads are exempt, and the exemption is named rather than left as a gap | §1.3, §11 |
| Do conversation writes audit, given `docs/PRD.md` §4.2's unqualified privacy? | **Yes — metadata only, and §4.2/§7 are amended in this change.** Actor, project and timing; never the title, never a message, and the ask route stays unaudited | §1.4, §9 |
| Who may read it? | **Admins, instance-wide.** Not a narrower project scope — a different axis | §5 |
| When is the row written relative to the action? | **After the commit, best-effort.** An audit failure never fails a user's action. The gap this accepts is stated in §4.2 and not hidden | §4 |
| Retention | **`AUDIT_RETENTION_DAYS`, default `0` = keep forever.** Pruned by the worker's existing 60-second tick when set | §6 |

### 0.2 The two constraints that are not negotiable

Both come from `docs/PRD.md` §9 via its §2.2 bullet, and both are structural in this design rather than
conventions a write site has to remember.

**It records that an action happened and by whom, never the secret involved.** No passwords, no
tokens, no PATs, and no clone URLs with credentials embedded. That section's requirement is that a token
must not survive into anything an operator can read, and an audit log is by definition something
an operator reads — so the trail is one more destination on the `scrub` path, not an exception to
it. §3.2's field allowlist is the mechanism; §8.4 is the test.

**It is append-only.** A user cannot erase their own entries, and that includes not being
reachable by the soft-delete path every other table uses. §2.1 is the mechanism.

## 1. Events

### 1.1 The catalogue

Thirty-seven names, anchored in `app/core/audit.py` as a validated string set — **not a table and
not a foreign key**. This is the reasoning `docs/data.md:85-88` gives for
`role_permissions.permission` and it applies unchanged: if existence lived in a table, deleting a
row would orphan every write site that names it.

| Group | Events | Written by |
| --- | --- | --- |
| **auth** (5) | `auth.login.succeeded`, `auth.login.failed`, `auth.logout`, `auth.password.changed`, `auth.refresh.replayed` | `app/services/auth.py` |
| **accounts** (4) | `user.created`, `user.updated`, `user.deactivated`, `user.password.reset` | `app/services/user.py`, plus the `seed-admins` CLI for `user.created` |
| **projects** (3) | `project.created`, `project.reindex.requested`, `project.deleted` | `app/services/project.py` |
| **RBAC** (6) | `membership.granted`, `membership.role_changed`, `membership.revoked`, `role.created`, `role.updated`, `role.deleted` | `app/services/membership.py`, `app/services/role.py` |
| **checklist modules** (4) | `checklist_module.created`, `checklist_module.updated`, `checklist_module.deleted`, `checklist_module.generation.requested` | `app/services/checklist_module.py` |
| **checklist items** (5) | `checklist_item.created`, `checklist_item.updated`, `checklist_item.result_recorded`, `checklist_item.deleted`, `checklist_item.results_cleared` | `app/services/checklist_item.py` |
| **checklist change sets** (2) | `checklist_change_set.applied`, `checklist_change_set.discarded` | `app/services/checklist_change_set.py` |
| **mock data** (5) | `mock_data.generation.requested`, `mock_data_change_set.applied`, `mock_data_change_set.discarded`, `mock_data_record.deleted`, `mock_data.exported` | `app/services/mock_data_dataset.py`, `mock_data_change_set.py` |
| **exports** (1) | `checklist.exported` | `app/services/checklist_item.py` |
| **conversations** (2) | `conversation.created`, `conversation.deleted` — metadata only (§1.4) | `app/services/conversation.py` |

`auth.refresh.replayed` is not in §2.2's list and is included because the detection already
exists: refresh tokens rotate on use and `family_id` ties a chain together, which is what makes
replay of a spent token detectable (`docs/data.md:62-65`). Today that detection only logs.

**`checklist_item.results_cleared` is the highest-value row in the table**, and the 18-event
catalogue this design started from missed it entirely — which is the argument for the rule.
`DELETE /checklist-items` with a filter ("Clear the recorded results the filter selects",
`app/api/routes/checklist_items.py:89`) can erase a week of a tester's recorded observations
**without deleting a single row**. It is the only write in the app that destroys human-recorded
work that way, and `docs/PRD.md` §4.3's promise that a regeneration cannot destroy a recorded
result says nothing about it, because it is not a regeneration.

`checklist.exported` and `mock_data.exported` are audited even though they change nothing. An
export is the one action that takes a private repository's derived content out of the instance, and
`docs/PRD.md` §9 treats egress as a category of its own. Both carry a `format` context key
(`xlsx`, `json`) and the filter that selected the rows.

### 1.2 Two events §2.2 names that have no write site of their own

**"PAT changes."** There is no project-update route. `app/api/routes/projects.py` has three `GET`s,
two `POST`s and one `DELETE` — no `PATCH` — and a PAT is supplied only at `POST /projects`
(`app/services/project.py:104-115`). So a PAT change is not an event that can happen; it collapses
into `project.created` carrying a `patSupplied` boolean. **If a project-update route is ever added,
`project.updated` with a `patChanged` flag is the event to add with it**, and §8.3's coverage test
is what will make the omission obvious rather than silent.

**"Password resets."** Both halves exist — `AuthService.change_password` (the user's own, including
the forced first-login change) and `UserService.reset_password` (an admin's). They are two events,
`auth.password.changed` and `user.password.reset`, because the actor differs and so does the
question being asked of the trail.

### 1.3 The four exemptions, each with its reason

Recorded here and in `.claude/rules/audit-trail.md` so a later reader finds a **decision** rather
than what looks like an oversight. Changing one is a PRD change first.

1. **Ordinary reads** — listing, getting, browsing indexed paths. The trail records what changed;
   a read log on the hot path is a different feature with a different write rate.
2. **Refinement-chat turns** — `POST /checklist-modules/{id}/messages` and its mock-data twin write
   a message and a *pending change set*, and `docs/data.md`'s third storage rule is that a proposal
   is not a row. The audited event is the `apply`, where content of record changes. Auditing the
   turn as well records an intention twice and makes the trail noisier than what it describes.
3. **The ask route** — `POST /conversations/{id}/messages` is not audited, and this is the PRD's own
   line rather than a preference: `docs/PRD.md` §2.5 rules out folding per-model-call records into
   this table **by name**, because "one table would bury 'an admin deactivated an account' under
   two hundred map calls". Tokens, timing and outcome per call belong to Phase 2.5's record.
4. **Ingestion outcomes** — §4.5. No actor exists, and `projects.status` and `projects.error`
   already hold the result.

### 1.4 Conversations: metadata only, and §4.2 is amended to say so

`conversation.created` and `conversation.deleted` are audited with `actor_user_id`, `target_id` and
`project_id` set and **`target_label` `NULL`**.

`docs/PRD.md` §4.2 and §7 currently state conversation privacy **without qualification**, and
`.claude/rules/rag.md` records that `is_admin` is not consulted anywhere under `/conversations`. An
admin-readable row saying *"someone opened a conversation against this project at 14:02"* is
metadata about a private resource reaching an administrator through a route that is not
`/conversations`, so those sentences stop being literally true. **They are amended in this change
(§9)** rather than left to contradict the code — the trade-off was put on the table and taken
deliberately.

What is *not* amended, and what the `NULL` label protects:

- **No administrator bypass anywhere under `/conversations`**, and every miss there is still `404`.
  The access rule is untouched; only the existence metadata is now recorded elsewhere.
- **No title.** A conversation's title derives from the user's first question, and `docs/PRD.md`
  §2.5's ban on storing a prompt applies verbatim — it carries the question and retrieved private
  source. Every other resource's `target_label` is a name a human chose for a shared thing; a
  conversation has no such name.
- **No message content, and no per-question row** (§1.3, exemption 3).

So an administrator can see *who, which project, when*. Never *what about*.

## 2. The table

### 2.1 `audit_events` carries neither mixin, and that is the append-only mechanism

This is the first table in the app outside both `TimestampMixin` and `SoftDeleteMixin`
(`app/models/base.py`), and both omissions are load-bearing.

**No `deleted_at`.** `BaseRepository.active_select()` applies its filter only when the model
carries `SoftDeleteMixin`, so not carrying it means there is no soft-delete path to reach these
rows through at all. "Append-only" stops being a convention every future repository method has to
respect and becomes a property of the model.

**No `updated_at`.** `TimestampMixin` ships `onupdate=func.now()`, and a column recording a
mutation has no business on a row that is never mutated. `created_at` is declared explicitly on
the model instead.

`docs/data.md:31-32` currently states that every table except `refresh_tokens` and `messages`
carries all three timestamps. That sentence stops being true in this change and moves with it
(§9).

### 2.2 Columns

| Column | Type | Why it exists |
| --- | --- | --- |
| `id` | UUID, pk | |
| `created_at` | timestamptz, `server_default=now()`, indexed | The only ordering this table has a meaningful answer for (§5.2) |
| `event_type` | str | One of §1.1. Validated against the catalogue in code |
| `actor_user_id` | UUID FK `users`, **nullable** | `NULL` means *no authenticated actor* — a failed login against an unknown address, or the `seed-admins` CLI. Nullable for the reason `docs/data.md:90-92` gives for `granted_by`: fabricating an actor would record a lie in the one table whose purpose is being trustworthy |
| `actor_email` | str, nullable | A **snapshot**, not a join. `users.email` is unique only *where not deleted*, so deactivating an account frees the address for reuse — resolving at read time would eventually attribute an old event to a new person |
| `target_type` | str, nullable | `user` \| `project` \| `role` \| `membership` |
| `target_id` | UUID, nullable | Not an FK: the row it points at may be gone, and an FK would either block the delete or cascade away the record |
| `target_label` | str, nullable | A snapshot of what was acted on. **This is the core of the sub-phase** — a deleted project takes its name with it, so "who deleted it" is only answerable if the row already holds *what* was deleted |
| `project_id` | UUID FK `projects`, nullable | The axis a future per-project read would scope on (§5.3). Unused by the routes this design ships |
| `outcome` | str | `success` \| `failure`. A failed login is an event, so outcome cannot be implied by the row existing |
| `ip_address` | str, nullable | The source host, on the auth events. The only field that turns failed logins from forensic into useful. No user-agent |
| `details` | JSONB | §3. Capped at 8 KB; everything entering it passes `scrub` |

Indexes on `created_at`, `actor_user_id`, `event_type` and `project_id`. **None of them partial**,
because there is no `deleted_at` to filter — which is the one place this table diverges from the
pattern `docs/data.md:94-99` describes for every other group.

### 2.3 `details`, not `metadata`

`metadata` is unusable as a column attribute name: it collides with `Base.metadata` on every
Declarative model. The column is `details`.

## 3. What `details` holds

### 3.1 One envelope for all thirty-seven events

```json
{
  "changed": { "<field>": { "before": "<scalar|list|null>", "after": "<scalar|list|null>" } },
  "<contextKey>": "<scalar>"
}
```

- `changed` carries **only the fields that actually changed**, never a snapshot of the row.
- A create writes `"before": null` across the board; a delete writes `"after": null`. One renderer
  in the admin UI therefore handles all three shapes (§7.2).
- Flat keys beside it carry **immutable context that is not a change** — `patSupplied`, `forced`,
  `unknownAccount`, `source`, counts.
- Keys are `camelCase` **at the point they are stored**, so `ApiModel`'s alias generator has
  nothing to translate on the way out and the stored bytes match the wire exactly.

### 3.2 The field list is an allowlist, never a diff of dirty attributes

Per event type, `app/core/audit.py` names the fields that may appear in `changed`. A generic
"diff whatever changed on the model" helper is the defect to avoid, and the reasoning is the
checklist apply path's (`docs/data.md:214-216`) with a sharper consequence: such a helper would
start writing `password_hash` and `encrypted_pat` into an operator-readable table the moment
someone adds a column to `users` or `projects`. The allowlist means **a new column is invisible to
the audit trail until someone names it**, which is the failure direction to prefer.

Nine notes on that table.

**`auth.password.changed` and `user.password.reset` carry no `changed` block at all.** Both sides
of that diff are the thing §0.2 forbids storing. The event type is the whole record.

**`project.deleted` carries the blast radius, not just the name.** `docs/data.md:166-167` says
deleting a project sweeps every member's conversations, its checklist and its mock data — so "a
shared index disappeared on Tuesday" wants to know how much went with it, and the counts are only
knowable at delete time.

**`role.updated`'s `permissions` before/after is the most valuable diff in the table.** It is the
one write in the app that can widen what every holder of a role may do, across every project, and
nothing else records it. `roles` is instance-wide while the assignment carries the project
(`docs/data.md:79-80`), so this event has no `project_id`.

**`project.reindex.requested` records the generation being superseded, not the new one.** The new
generation does not exist at request time: the worker increments it, and `ProjectService.reindex`
only raises `reindex_in_progress` and publishes (`docs/rag.md`, `docs/PRD.md` §7's fixed-bug
record).

**`checklist_item.result_recorded` is separated from `checklist_item.updated`** even though both
are a `PATCH`. `status` and `current_result` are the two columns the change-set apply path is
forbidden to write (`docs/data.md:214-216`) because they claim a human observation — so the trail
keeps the event that legitimately writes them distinct from the one that edits what a test
expects. Conflating them would make "who recorded this pass?" unanswerable without reading the
payload of every update.

**`checklist_item.results_cleared` carries `clearedCount` and the filter, not the rows.** The rows
are what was destroyed, and copying them in would put generated test content in the trail against
the content ban (§0.2). The count plus the filter is enough to say what was lost and to whom to
talk; the rows themselves are gone by design.

**Both `*_change_set.applied` events carry `operationsProposed` alongside `operationsApplied`.**
A human ticks a subset, and the gap between the two numbers is the record that they reviewed rather
than accepted wholesale. Neither carries the operations themselves — those are model-authored
content naming files and test cases (§0.2).

**The two export events carry the filter and the row count, never the exported bytes.** The point
is that content left the instance and roughly how much, not a second copy of it.

**`membership.*` targets the grantee, not the membership row.** `target_type` is `user`,
`target_id` and `target_label` are the affected user's id and email, and `project_id` is set. That
is what makes the row read as *"X granted alice@example.com `owner` on askrepo"* rather than
requiring a join through a membership id that a revocation has since soft-deleted.

### 3.4 The submitted address on a failed login is not stored verbatim

People paste passwords into the email field. Since §4 writes this row from raw request input,
storing the submitted value blind would eventually put a password in the one table an operator is
guaranteed to read — which is §0.2 failing, quietly, through no fault of the code.

So: if the address matches a live `users` row, `actor_user_id` and `actor_email` come **from that
row**. If it does not, both stay `NULL` and `details` carries `{"unknownAccount": true}`.

What that gives up is address-enumeration detail — the trail can say *someone tried an account
that does not exist* but not which string they tried. What it buys is that §0.2 holds without
depending on users typing carefully. `ip_address` is still recorded, so the enumeration attempt is
still visible as a pattern from one host.

## 4. The write path

### 4.1 Two objects, because they have different sessions and different failure rules

**`app/core/audit.py`** sits beside `grant_cache.py`: like the grant cache, this is cross-cutting
infrastructure that services call, not a resource with routes. It holds the §1.1 catalogue, the
§3.2 allowlist, a frozen `AuditEntry` value object — plain data, no ORM — and:

```python
async def record(self, entry: AuditEntry) -> None: ...
```

**`AuditEntry`, not `AuditEvent`.** `AuditEvent` is the ORM model in `app/models/audit.py`; the
value object handed to the recorder is deliberately a different type with a different name, and
§4.3 depends on the distinction — nothing in the audit path holds an ORM reference.

`AuditRecorder` takes the **sessionmaker**, not a session, and opens its own. The precedent is
`AuthContextMiddleware`, and `app/db/session.py:1-8` already explains why that factory is lazy: a
settings override has to reach both the `Depends` path and the direct one. It inserts, commits,
and on any `Exception` logs the whole event at `WARNING` and returns.

**It never raises.** That is what makes "an audit failure cannot fail a user's action" structural
rather than a convention each of the 39 call sites has to remember (38 across the services, plus
the `seed-admins` CLI).

It is injected as `Annotated[AuditRecorder, Depends(get_audit_recorder)]` into the service
factories that record — eleven of them.

**Tests use a real `AuditRecorder` and read the rows back**, through the `audit_rows` fixture in
`tests/conftest.py`. An earlier draft of this section proposed an in-memory recorder, the role
`InMemoryIngestionQueue` plays for the queue; it was never built, and what shipped is stronger.
An in-memory double would assert that a service *called* the recorder; reading the row asserts
what actually landed in the column, which is where the two content bans are either kept or
broken.

**`app/services/audit.py`** holds `AuditService.list(query)` and `AuditService.get(event_id)`,
taking the **request** session like every other service. There is no `record` on it, and no write
method anywhere in the service layer.

### 4.2 After the commit, best-effort — and the gap that accepts

Each audited service method commits its own work, then awaits `recorder.record(...)`. The user's
action can never fail because of auditing, which is the property this was chosen for: a login
should not fail because a log write did.

**The accepted consequence, stated rather than discovered:** an action that commits and then
crashes — or is cancelled — before its audit write leaves **no row, silently**. The trail is a
strong record, not a guaranteed-complete one, and `docs/PRD.md` §2.2 must not claim otherwise.

Two mitigations narrow the window without changing the guarantee:

- The recorder uses its **own session from the sessionmaker**, not the request-scoped one, so the
  write does not depend on when FastAPI closes the request's `AsyncExitStack` — the same reasoning
  `.claude/rules/rag.md` gives for the shielded termination write.
- A failed audit write **logs the full event at `WARNING`** through `app/core/logging.py`, so a
  lost row still leaves something an operator can grep. The structured log is the fallback record,
  not the record.

The alternative considered and rejected was writing the row inside the action's transaction, which
would make the trail exactly as trustworthy as the data it describes and would fail the request on
an audit-write failure. Rejected deliberately: never break a user's login for a log line.

### 4.3 The payload is built from locals, not from ORM objects

Every write site captures the `before` scalars into locals *before* it mutates and the `after`
scalars before it commits, then hands a plain dict to the recorder. **Nothing in the audit path
holds an ORM reference.**

This is a boundary choice rather than a bug being dodged: the sessionmaker sets
`expire_on_commit=False` (`app/db/session.py:38`), so instances are not expired after commit and
reading `project.name` afterwards would not issue a refresh. The rule still stands, because a
recorder that cannot touch a `Session` cannot be made to re-read a row that is now soft-deleted,
and cannot hold one open past the request.

### 4.4 `project.deleted`'s ordering

`docs/data.md:162-164` requires the Qdrant hard delete to run *before* the commit, so the sequence
is: capture the label and counts → hard-delete the points → commit the soft delete → record the
event. If Qdrant refuses, nothing commits and nothing is recorded, which is correct — no deletion
happened.

### 4.5 The worker prunes and never records

A finished index has no actor. Nobody did it, a job did — and `NULL` actor is reserved for the two
cases where a human acted without an authenticated identity (§2.2). Ingestion outcomes belong to
`projects.status` and `projects.error`, which already hold them.

The one exception is the `seed-admins` CLI, which does create accounts and runs on every production
deploy (`docs/data.md:284-287` chains it before `uvicorn`). It records `user.created` with a `NULL`
actor and `"source": "cli"`, rather than attributing the seed to the account it just created.

## 5. Reading it

### 5.1 Two routes, both reads

```
GET /audit-events        →  PaginatedResponse[AuditEventSummary]    AdminUser
GET /audit-events/{id}   →  AuditEventResponse                      AdminUser
```

There is no `POST`, `PATCH` or `DELETE` on this router at all, which is how §0.2's append-only
constraint shows up on the wire and not only in the schema.

### 5.2 Query shape

Filters live on **`AuditEventListQuery(ListQuery)`** — `event_type`, `actor_user_id`, `project_id`,
`outcome`, `occurred_from`, `occurred_to` — as a subclass, **never as scalars beside the model**.
`.claude/rules/rag.md` records why: FastAPI flattens an `Annotated[Model, Query()]` only while it
is the sole query parameter, and a scalar beside it makes every request fail with
`{"request": "Field required"}`, naming nothing that appears in the signature.

`search` matches `actor_email` and `target_label`. `sort` narrows to `Literal["created_at"]`.

### 5.3 Why admin-only is an access decision, and where it would change

The auth events, the account events and the PAT flag span no project at all, so a per-project
scope does not describe this read — it is a read on a different axis, not a narrower project
scope. It goes behind the existing `AdminUser` dependency (`app/api/deps.py:44`), the same
machinery `/users` and `/roles` already use.

The row still carries `project_id`, so the per-project read that was considered and deferred — a
member holding an `audit.read` permission seeing their own project's events — is later **one
permission plus a `require_permission` call**, not a migration. Issue #23 is explicit that such a
read must not be answered by adding a filter beside the access resolver, and `docs/PRD.md` §7's
one-enforcement-point criterion is what holds that.

### 5.4 Status codes

`AUDIT_EVENT_NOT_FOUND` at `404` is the one new `ErrorCode`. `ErrorCode` values are a wire
contract — members are added, never renamed (`.claude/rules/response-api.md`).

**The `403`/`404` split has no security dimension here, and that is worth recording because it
will change.** The route is `AdminUser`-only and the table has no per-project scope, so a miss is
genuinely "no such row" rather than "not yours". The moment §5.3's per-project read is added, that
sentence stops being true and this route needs the `require_permission` treatment the project
routes already have.

A non-admin gets `403 ADMIN_REQUIRED` from `require_admin`. No new code, no widened body, no
`extra`.

### 5.5 Two response schemas

`details` is capped at 8 KB and a `role.updated` row carries two full permission lists; shipping
25 of those to render a scannable table is a lot of wire for content the table cannot show.

| | `AuditEventSummary` (list) | `AuditEventResponse` (detail) |
| --- | --- | --- |
| `id`, `createdAt`, `eventType`, `outcome` | ✓ | ✓ |
| `actorUserId`, `actorEmail` | ✓ | ✓ |
| `targetType`, `targetId`, `targetLabel`, `projectId` | ✓ | ✓ |
| `changedFields` — names only, e.g. `["permissions"]` | ✓ | — |
| `details` — full `changed` plus context keys | — | ✓ |
| `ipAddress` | — | ✓ |
| `current` — live lookups (§5.6) | — | ✓ |

Both inherit `ApiModel`. `changedFields` is **derived at read time** from `details.changed` keys
and is never a stored column — a second copy is the kind of derived state `.claude/rules/rag.md`
refuses for grounding warnings, for the same reason: it can drift from the row it describes.

**No SSE event is added, so `SSE_EVENT_MODELS` is untouched.** Stated because that tuple is the
only enforcement an SSE payload gets and a reviewer will check.

### 5.6 `current`: live lookups, fenced off from the record

The detail response carries a `current` object with `actorStillActive` and `targetStillExists`,
because the first question on a `project.deleted` page is "is that project back?" and on a
`membership.revoked` page "does that person still have an account?".

It sits under its own key precisely so a live lookup cannot be mistaken for part of the record.
**What `current` deliberately does not do** is resolve `role.updated`'s stored permission list
against the role's present one and render a three-way diff — that reads as if the audit row knows
something it does not. The row is a snapshot, full stop.

## 6. Retention

`audit_retention_days: int = Field(default=0, ge=0)` in `app/config.py`, `0` meaning keep forever.

Default-off is the right default here because **this table's write rate stays bounded by human
action** — logins, destructive operations and QA activity, not Phase 2.5's 201 rows per generation
— so a small instance never needs to lose history, and a fresh instance must not silently start
discarding the one record whose purpose is being the record.

**§1.1's widening does move this number, and honestly it is the one estimate here to revisit after
a month of real use.** `checklist_item.result_recorded` fires once per test a tester ticks, so an
active QA pass writes hundreds of rows in a day where the original 18-event catalogue would have
written none. That is still two orders of magnitude below a generation's call log and it is still
proportional to work a person actually did — but SECURITY.md should tell operators to consider a
window rather than implying the default suits every instance (§9).

The prune lands **inside the existing tick**, not beside it. `app/worker.py:164-186` already opens
one session per 60 seconds, runs its three reconciles plus
`RefreshTokenRepository.delete_expired_and_revoked()`, and commits once:

```python
if settings.audit_retention_days > 0:
    pruned_events = await AuditEventRepository(session).delete_older_than(cutoff)
```

It logs at `INFO` like the token prune. The tick is already wrapped in
`except Exception: logger.exception("reconcile tick failed")`, so a prune failure costs one tick
rather than the sweep.

`delete_older_than` is a **hard delete and takes a cutoff and nothing else** — no actor filter, no
event-type filter — so the one delete path in the codebase that touches this table cannot be aimed
at anyone's entries. That is what keeps §0.2's append-only claim true in the presence of a prune:
an operator sets a window; nobody erases a row.

SECURITY.md gains the operator obligation (§9).

## 8. Testing

### 8.1 `tests/test_audit_events_api.py`

Non-admin gets `403 ADMIN_REQUIRED`; pagination; each filter in §5.2; `404
AUDIT_EVENT_NOT_FOUND`; and that the summary omits `details` while the detail carries it.

### 8.2 `tests/test_audit_recorder.py`

A recorder whose session raises still returns cleanly, logs at `WARNING`, and leaves the action's
own commit intact. **This is the test that proves §4.2's trade-off behaves as chosen** rather than
as an accident.

### 8.3 `tests/test_audit_coverage.py` — the forgetting guard

A table of the audited operations, each driven through an in-memory recorder, asserting exactly
one event of the expected type with the expected `changed` keys — **plus the reverse direction:
every name in the §1.1 catalogue must have at least one recording site**, so a catalogue entry
cannot exist unwritten and a write site cannot invent a name.

Same shape as `tests/test_scoping_is_single_point.py`, and the reason a destructive route added
later fails a test rather than silently auditing nothing (§1.2).

**A third direction makes the coverage rule itself testable**, rather than only the catalogue: a
grep-style assertion that every mutating route — every `@router.post`, `.patch`, `.put`, `.delete`
and every export route across `app/api/routes/` — resolves to a service method that records, with
the §1.3 exemptions named in the test as an explicit allowlist. This is the test that fails when
someone adds a route and forgets, which is the failure `.claude/rules/audit-trail.md` exists to
prevent and the one no per-event test can catch.

### 8.4 `tests/test_audit_scrubbing.py`

A project created from a PAT-bearing clone URL stores neither the token nor a credentialed URL,
and `repoUrlHost` is host-only. A failed login against an unknown address stores no email at all
(§3.4). This is §0.2 as a test.

Three more assertions belong here, because each guards a ban that is invisible at the call site:

- **`conversation.created` and `conversation.deleted` carry `target_label IS NULL`** and no
  message content anywhere in `details` (§1.4). This is the test that keeps the §4.2 amendment
  narrow — the thing that was conceded is existence metadata, and this asserts nothing wider
  followed it in.
- **`checklist_item.results_cleared` carries a count and a filter, never the cleared rows**, and
  the two change-set applies carry counts, never the operations.
- **No event's `details` contains a key outside its declared allowlist** (§3.2), asserted by
  walking the catalogue rather than per event, so a new event type cannot ship with an
  undeclared field.

### 8.5 `tests/test_audit_retention.py`

`audit_retention_days=0` deletes nothing; a window deletes only rows past it; `delete_older_than`
takes no filter but the cutoff.

### 8.6 Frontend vitest

The nav filter hides both routes for a non-admin. The before/after renderer handles `before: null`
and `after: null` without printing "null".

### 8.7 `tests/test_api_model.py`

No change needed beyond the two new schemas inheriting `ApiModel`, which the existing walk covers.

## 10. Build order

1. `app/core/audit.py` — catalogue, `AuditEvent`, the §3.2 allowlist, `AuditRecorder`. Tests
   §8.2 first.
2. Model, migration, `AuditEventRepository`. `docs/data.md`.
3. `.claude/rules/audit-trail.md`, and §8.3's route-coverage assertion with every service still on
   the exemption list. The rule and its test land **before** the write sites, so each service is
   ticked off a failing test rather than added to a list from memory.
4. Write sites, service by service, removing each from the exemption list as it lands: `auth`,
   `user`, `project`, `membership`, `role`, `checklist_module`, `checklist_item`,
   `checklist_change_set`, `mock_data_dataset`, `mock_data_change_set`, `mock_data_record`, the two
   export services, `conversation`, then the CLI. §8.3 grows with each.
5. `AuditService`, the two routes, the schemas, `AUDIT_EVENT_NOT_FOUND`. §8.1.
6. §8.4's scrubbing and content-ban tests, against the real project-create, export and
   conversation paths.
7. `AUDIT_RETENTION_DAYS`, the sweep, §8.5.
8. The two screens, §8.6.
9. §9's docs — including the `docs/PRD.md` §4.2/§7 amendment and `.claude/rules/rag.md`, which are
   the two that must not be left for a follow-up.

Steps 1-4 are useful on their own: the trail is recording before anything can read it, which is the
right order for a record whose value is retrospective. **Step 3 before step 4 is the load-bearing
part of this order** — thirteen write sites added against a failing test is a different activity
from thirteen added against a checklist, and it is the one that cannot quietly miss one.

## 11. Out of scope

- **A per-project audit read.** Deferred with a clear path (§5.3). The column is there; the
  permission and the `require_permission` call are not.
- **Mirroring events to the structured log as a second destination.** Considered; rejected for now
  because two destinations means two places a new event type can be forgotten, and the `WARNING`
  fallback in §4.2 already puts lost events in the log where it matters.
- **The four exemptions in §1.3** — ordinary reads, refinement-chat turns, the ask route, and
  ingestion outcomes. Each is a decision with a stated reason, not a gap, and each is repeated in
  `.claude/rules/audit-trail.md` so it is not "fixed" later by someone applying the coverage rule
  literally.
- **A read log.** Distinct from exemption 1 and worth separating: recording that someone *viewed*
  a checklist or listed projects would make the write rate a function of browsing rather than of
  change. Exports are audited because content leaves the instance; looking at a screen is not an
  export.
- **Exporting the trail itself.** No CSV or JSON download of `audit_events`. `GET /audit-events`
  paginates; an operator who needs bulk has `psql`. Note the asymmetry is deliberate — the trail
  audits other resources' exports and offers none of its own, because an export route here would
  be the one feature that hands an operator a detachable copy of the record.
- **Tamper evidence.** No hash chain, no signature, no append-only Postgres role. A database
  superuser can still edit rows directly, and this design does not claim otherwise: §0.2's
  append-only guarantee is about what the *application* can do, since `docs/PRD.md` §9's threat
  model excludes malicious authenticated users and the operator is the trusted party.
